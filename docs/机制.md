# 伤害机制

> 返回 [项目首页](../README.md) · [文档索引](README.md)

一发炮弹命中载具时：

1. 按基础模组的方式重新追踪弹道，求出命中点与命中的 OBB 面。
2. 判断命中的是**炮塔**还是**车体**。
3. 按命中部位依次判优先级更高的特殊区域：
   - 炮塔正面 → 命中点是否落在**炮根弱点区**圆盘内
   - 车体正面 / 后面 → 是否落在**履带区**（外侧两条）
   - 车体侧面 → 是否落在**爆炸反应装甲覆盖区**（见下文）
   - 车体正面 → **首上 / 首下**按命中高度切分
4. 用炮弹穿深减去该处装甲厚度得到**剩余穿深**。
5. 剩余穿深 ≤ 0 → 未击穿，不掉血；> 0 → 造成 `剩余穿深 × 该处倍率` 的伤害。
6. 如果这发弹药配了**溅射**（只有破甲弹配了），额外结算（见下文）。

此外，**武器自身的部件血量被打到 0 后，该武器无法再开火**（详见下文）。

### 弹药可以自带一套装甲数值

穿甲弹和破甲弹打同一块装甲，结果完全不同：钢针靠动能硬顶，倾斜的厚钢板对它最有效；破甲弹
靠金属射流烧穿，钢板倾斜与否影响小得多，反而被反应装甲克制。所以**同一辆 T-64 对这两种弹
有两套厚度**。

实现上是在载具下加 `overrides`，按名字（`profile`）索引。弹药在 `ammo_penetration` 里写
`"profile": "heat"` 就会去查这一套；**没写的弹药（含所有机枪）继续用载具自己的那套**。

只有**数值**会被覆盖 —— 炮根圆盘在哪、首上分界在哪、履带条多宽，这些是坦克的几何，永远取自
载具本身，不会因为换了弹种而漂移。

倍率按部位区分：正面装甲厚，能被打穿说明弹丸还有余力，倍率给得高；薄板（首下、侧后、炮根）
穿深减去薄板后剩余数值天然很大，倍率必须压低，否则一打就秒。履带是行走机构不是装甲，
打穿了对车体几乎没影响，所以倍率最低。

### 高爆弹（HE）

2A46M-1 125mm 高爆弹（`vvp_ywzj:2a46m1_125mm_he`）**穿深只有 60mm**，用 `he` 这一套厚度。

它和破甲弹的**唯一区别**是三个薄板：**炮塔顶部、车体顶部、车体底部对高爆弹是 60mm**（破甲弹是
200mm）。其余部位两套完全一致。

> **注意：炮塔底部没有改**，还是 200mm —— 你只点名了「炮塔顶部、车体顶部、车体底部」三处。
> 要一起改成 60mm 就改 `overrides.he.turret.floor`。

#### 按命中面判定

**打中哪块板，就按哪块板算。** 打首上就是 840，打顶部才是 60。

| 命中部位 | 厚度 | 结果 |
|---|---|---|
| **炮塔顶部 / 车体顶部 / 车体底部** | **60** | **击穿 → 2000** |
| 车体首下 | 120 | 未击穿 → 溅射 950 |
| 车体侧面（无反应装甲）/ 后部 / 履带 / 炮塔后部 | 200 | 未击穿 → 溅射 883 |
| 车体侧面（有反应装甲） | 500 | 未击穿 → 溅射 633 |
| 炮根 / 炮塔侧面 | 300 | 未击穿 → 溅射 800 |
| 车体首上 | 840 | 未击穿 → 溅射 350 |
| 炮塔正面 | 880 | 未击穿 → 溅射 317 |

两条分支：

- **击穿 → 固定 2000 伤害**。不是"剩余穿深 × 倍率"，是平伤 —— 战斗部在车里炸开，进去多少
  都一样。**这时候不再叠加溅射**（`spall_on_penetration: false`）。
- **未击穿 → 300~1000 的溅射**，从"差一点就能打穿"的 1000 一路降到"根本啃不动"的 300。曲线是
  线性插值：厚度 ≤ 穿深（60mm）取最大值，厚度 ≥ `spall_falloff_to`（900mm）取最小值。
- 两种情况都上 **1 秒失明**。

> #### 曾经做过的「半径 4 格球面爆炸」，已移除
>
> 试过一版：命中后以命中点为心、半径 4 格向**所有方向**找装甲，用**能找到的最薄那块**判定，
> 也就是想让火球绕上去够到车顶。**已经删掉了**，原因是它有必然的副作用：
>
> **车顶就在首上正上方 0.93 格**（`FaceProbe` 实测：车体半高 0.97 格；最坏情况是首下底缘到车顶
> 1.93 格，炮塔只有 0.56 格）。所以只要半径 ≥ 1 格、顶部是 60mm，**打首上就一定会被车顶盖掉**，
> 结果首上按 60mm 算 → 每次都是 2000。半径调小也救不了 —— 车顶和首上属于**同一个装甲盒**，
> 共享同一片投影，任何半径都够得着。
>
> 结论是「球面」和「首上保持 840」**无法共存**，只能二选一。选了保住首上，于是球面连同
> `blast_radius` 配置项一起删掉了，没有留成"设了也没用"的空键。
>
> 顺带确认过：**首上的面判定本身没问题**。车体上盖着两个前表面共面的盒子（`main_structure`
> 和更宽的 `vehicle_body`），但从 −20° 到 +30° 各种俯仰角打过去，模组自己的
> `hitOBB` + `embeddingFace` 都稳定判成 `face +3 (FRONT)`（见 `FaceProbe`）。

#### 几个说明

- **顶部/底部是 60、穿深也是 60，正好相等**。判定规则是「剩余穿深 ≥ 0 算击穿」，所以相等算打穿、
  伤害为 0 剩余 —— 否则 60 对 60 会判成未击穿，2000 那条永远触发不了。（穿甲弹走的是
  `剩余 × 倍率`，相等时伤害是 0，所以这条改动对它没有可见影响。）
- **`spall_falloff_to` 的 900 是我定的**：你只说了「随等效厚度的提高而降低」，没说降到哪。
  取 900 是为了让 T-64 整个厚度区间（60~880mm）刚好铺满 300~1000 —— 实际生效范围是
  **317~950**。想让落差更陡就把它调小，比如 300 → 那 300mm 以上全是 300 保底。
- **`he` 和 `heat` 在配置文件里是两张独立的完整表**。默认值是同一个方法生成、保证同步，但
  **一旦写进文件就各走各的**。改破甲弹数值时记得同步改高爆弹，只有顶部/底部那三个数应该不同。

### 近炸引信榴弹（HE-VT）

T-64 的第二门 125mm 榴弹：`vvp_ywzj:2a46m1_125mm_he_vt`。用**同一套 `he` 装甲表**，穿深也是
60mm，和普通榴弹的区别只有两点 —— **引信**和**战斗部**。

#### 引信是基础模组自带的，本模组没写一行检测代码

载具包里的武器文件开了这个：

```json
"explosion": {
  "explode": true, "damage": 1500, "radius": 4, "destroy_block": true,
  "proximity_fuze": true, "proximity_radius": 4
}
```

`AmmoEntity` 里本来就有这段逻辑：弹丸飞行时，每 tick 在**弹丸周围一个球**（半径
`proximity_radius`）**再沿飞行方向往回拉长**的范围内找实体，找到就引爆并消失；条件是**飞行超过
5 tick**（差不多是出膛保险）且**这一 tick 没有直接命中实体**（直接命中就按命中处理）。

> **这和「前方半径 4 格的半球」有细微差别**：它是「以弹丸为心的球 + 拖在后面的航迹」。因为弹丸
> 一直在往前飞，正前方 4 格内的目标必然在射线上被扫到，所以实战效果和前方半球一致；多出来的
> 那截"球的后半"只在弹丸掠过目标之后才有意义，而那时它早就已经引爆了。
>
> 另外包里的`aim9`/`aim120`/`r73` 用的也是这个机制，`proximity_radius` 同样是 4 —— 这是这个包里
> 的既有参数，不是我为这门炮编的。

#### 战斗部：高爆弹去掉击穿伤害

| 项 | 普通榴弹 HE | 近炸榴弹 HE-VT |
|---|---|---|
| 穿深 | 60mm | 60mm |
| 装甲表 | `he` | `he`（同一套） |
| **击穿伤害** | **2000** | **0（去掉）** |
| 原版爆炸 | **被顶掉** | **保留**（载具包的 1500 / 半径 4） |
| 溅射 | 300~1000，**仅未击穿时** | 300~1000，**任何情况都结算** |
| 失明 | 1 秒 | 1 秒 |

两处是我按效果推的，都说明一下：

- **`penetration_damage` 填 0 而不是不填。** 不填会退回「剩余穿深 × 倍率」公式 —— 那就是击穿伤害
  换了个名字，而这门弹要的正是没有它。填 0 才是真的没有。
- **溅射改成任何情况都结算。** 普通榴弹的溅射是"击穿伤害的替代品"，所以只在未击穿时生效。这门弹
  没有击穿伤害了，再按装甲卡一次只会让**打中薄顶**（也就是它最该打中的地方）什么都不发生。去掉
  击穿伤害的本意就是让它不再关心穿没穿，所以溅射也跟着变成无条件的。

于是它的账面就是：**原版 1500 爆炸 + 300~1000 溅射（按找到的装甲厚度递减）+ 1 秒失明**，
不分穿没穿。工具里的伤害表可以直接看到：打 60mm 的顶部是 `0.0 blast 1000`，打 880mm 的炮塔
正面是 `no pen blast 317`。

### 多用途破甲弹（MP-HEAT，可切换引信）

M1A1 的第三门弹：`vvp_ywzj:m256_120mm_heat_mp`。**左方向键**切引信，**右方向键**调延时档位。

| 引信 | 效果 |
|---|---|
| **碰炸** | 和 120mm HEAT-FS **完全一致** |
| **近炸** | 同 HE-VT（保留原版爆炸 + 300~1000 溅射 + 1 秒失明），但**半径 3 格** |
| **延迟** | 先**打碎一层**软方块，在其后方**继续飞**，到设定时间起爆，爆炸效果同近炸 |

延时 **0.5 ~ 5 秒**，每 0.5 秒一档（10 ~ 100 tick，步进 10 tick），到顶后绕回最短。
**穿过之后会减速到 0.25 格/tick**，所以时间直接对应距离：0.5 秒 ≈ 墙后两三格，5 秒 ≈ 二十五格。

> **装甲表仍是破甲弹那一套。** 近炸和延迟用的是弹药自己的 `heat` 表和 **480mm 穿深**，
> 只是把引信换成了基础模组的近炸引信。这是它和 125mm HE-VT 唯一的区别 —— HE-VT 用的是 `he` 表。

#### 状态归本模组自己管

基础模组**没有任何方式让一颗弹在飞行中改变行为**：武器数据的每个字段都是共享的
（`VehicleData.explosion` 是全车共用的那一个对象），所以近炸和延迟只能靠**弹丸自己记住**。

- **不新增弹种**，而是给这颗弹加 `"multi_purpose": true`，并带一套自己的第二伤害模型 `proximity`。
- **服务端按玩家存设置**：本模组新建了一条 `SimpleChannel`。客户端按键只发"我按了哪个键"，
  服务端改完**回发当前状态**，客户端拿它显示。状态**不需要同步给客户端做判定** ——
  炮弹的 `tickHit()` 本来就只在服务端跑。
- **炮弹自己认领**：`BulletEntity.shoot` 会把**射手**设成弹丸的 owner，所以每颗弹在**第一 tick**
  用 `getWeaponId()` + `getOwner()` 查自己的设置即可。**两台坦克同时开炮不会串号**，也不需要
  "暂存上一发"这种一步错步步错的设计。
- 玩家登出时清除记录，免得下次进游戏带着上次的选择。
- 服务端没装本模组时，客户端收不到状态消息，按键会**明确提示**「服务端未安装 ywzj_vehicle_armor」
  而不是静默无效。

#### ⚠️ 「按了没反应」是怎么发生的（已修）

第一版有**两道客户端自己拍板的关卡**，两道都可能**判错并把功能关死**：

1. 客户端**自己判断**当前武器是不是多用途弹 —— 用的是 `getOwnOperatorUnit` → `getCurrentWeapon`
   → `getSelectedWeapon`。这条链在客户端本来就可能慢一帧或解析不出来，一旦解析失败，
   按键直接被丢掉。
2. 客户端在**收到过服务端的消息之前拒绝发送**任何东西（为了给"服务端没装模组"一个提示）。
   这就成了死循环：**证明服务端存在的那条回包，恰恰需要先发一条包出去。**

结果是：**炮手按左方向键，什么都没发生，服务端一次都没收到过按键，日志里也一个字都没有。**
炮弹永远用默认的碰炸引信 —— 于是「延迟引信」看起来就是**打中泥土墙直接炸开，根本没穿过去**。

现在改成：

- **客户端只判断一件事**：玩家是不是坐在载具上。是就发包，不猜武器。
- **服务端说了算**：`OperatedRound.operatingRound(player)` 用服务端自己的座位表查"这个人此刻操作的
  武器是不是多用途弹"，不是就不改。
- **按键不再等"服务端先打招呼"**：发出去，**回包本身就是"服务端有本模组"的证据**。
  1.5 秒没回音才提示「服务端未安装 ywzj_vehicle_armor」（5 秒内不重复）。
- 登录时那声招呼从 `PlayerLoggedInEvent` 挪到了**玩家进入世界后的第一个 tick** —— 登录事件触发时
  连接还没完全就绪，那时候发的包可能被丢掉，而丢掉之后再也没有第二次机会。

> 代价是：坐在直升机里按方向键也会发一个包。基础模组本来就把这两个键当 `functionalLeft/Right`
> 用，而本模组**从不取消事件、也不消费按键**，所以直升机的操作一点没变，服务端查一下发现不是
> 多用途弹就丢掉。两字节的代价换"永远不会静默失效"，值。
>
> 服务端只在**车上确实带着多用途弹**的时候才记录一条"这一下被忽略了"，否则直升机的方向键会把
> 日志刷满。

#### 延迟引信：打碎、减速、起爆

- **打碎**用 Mixin `@Redirect` 掉 `AmmoEntity.tickHit()` 里**唯一那次方块射线检测**。命中软方块时
  把它**炸掉**（`Level.destroyBlock`，`dropBlock = false`），然后**返回一个 MISS** —— 基础模组的
  整个方块分支（粒子、爆炸、`discard`）就被整段跳过了。
  **不留掉落物**：这是一发炮弹打了个洞，不是玩家在挖矿；每打一层土就掉一组物品只会污染世界。
  后面那发爆炸该掉的还是会掉。
- **方块被真的移除**，所以弹丸不可能再被"刚钻进去那格的远端面"点着 —— 那里已经没有方块了。
  也正因为如此，代码里**不再记录打碎过的坐标**（早期版本要记，因为方块还在，同一格方块有近端面
  和远端面两次命中）。
- **只打碎一层**：第二层土墙、或者石头，照常起爆。
- 软方块用**原版标签**判定：`#minecraft:dirt`、`#minecraft:sand`、`#minecraft:mineable/shovel`
  （砂砾不在 `sand` 里，是这条兜住的）、`#minecraft:logs`、`#minecraft:planks`、
  `#minecraft:leaves`、`#minecraft:mineable/axe`。用标签而不是方块清单，是为了让"能用锹挖的"
  和"木头做的"跟着游戏自己的定义走，模组方块也能自动算进来。
  > 这些标签在 SRG jar 里是 `f_144274_` / `f_13029_` 这类编号，**和源码声明顺序无关**，
  > 所以是从 `BlockTags` 静态初始化的字节码里逐条读出来的（名字 → 字段号），不是猜的。
- **减速不是衰减系数**，而是**每 tick 把速度重设成「穿透瞬间的方向 × 0.25 格/tick」**。
  衰减（速度乘以一个系数）会让位移在几 tick 内饱和，0.5 秒和 5 秒的档位又会变得几乎一样；
  而且 `tickMove` 每 tick 还会往速度上叠摩擦和重力，**只有每 tick 重设方向和大小**才能让弹道
  保持成一条直线。位置更新用的是 `tickMove` 开头读到的速度，而注入点在它之前，所以这一 tick
  就按新速度走。
- 起爆是自己造的 `VehicleExplosion`，参数照抄基础模组命中时那一份（owner 当 source、弹丸当
  direct entity），这样 `ArmorSystem` 才会把它认成**这颗弹的爆炸**，按近炸那套模型结算。

#### 三种引信分别用哪套伤害模型

`ArmorConfig.Ammo.damageModel(fuze)`：碰炸返回自己，近炸/延迟返回 `proximity` 子项。
`ArmorSystem` 通过 `ShellState`（由 Mixin 挂在 `AmmoEntity` 上）从弹丸读引信，然后
**穿深、装甲表、溅射、以及是否顶掉原版爆炸，全部跟着换**。非 MP 弹一律落到「碰炸 = 自己」，
其它弹种行为零变化。

> **`proximity` 是一个完整的嵌套条目，不是几个覆盖字段**：它有自己的 `profile`（这里是 `heat`，
> 不是 `he`）、自己的穿深、自己的溅射。
>
> 这也是**风险最高的一处**：序列化漏写会让 `proximity` 变回 `null`，然后**近炸和延迟静默退回
> 碰炸**，一个字都不会报。所以 `UpgradeCheck` 里专门有一条**写出去再读回来**的往返断言，加上
> 启动时日志会报「几发弹有可切换引信」—— 数字变成 0 就说明配置里的武器 id 和载具包对不上了。

#### 客户端按键

左/右方向键**只在玩家坐在载具上时才发送**，是不是这颗弹**由服务端判断**（原因见上一节）。

新语言键：`fuze.ywzj_vehicle_armor.impact` / `.proximity` / `.delay`，以及
`message.ywzj_vehicle_armor.no_server_mod`。

#### 怎么确认引信真的生效了

每次开炮都会打一行，写明这颗弹用的是哪档引信；没选过引信时会**明说**：

```
[Vehicle Armor] vvp_ywzj:m256_120mm_heat_mp fired with the DELAY fuze (delay 50 ticks)
[Vehicle Armor] vvp_ywzj:m256_120mm_heat_mp fired with the IMPACT fuze - no fuze was ever selected for <uuid>
```

第二行就是上面那个 bug 的样子 —— **"引信是碰炸"和"按键根本没送到服务端"在别的日志里长得一模一样**，
所以这两句必须分开写。

按键被服务端接受、穿过软方块时也各有一行：

```
[Vehicle Armor] <player> fuze is now DELAY (delay 50 ticks)
[Vehicle Armor] delay fuze broke through Block{minecraft:dirt} at BlockPos{x=..., y=..., z=...}; 50 ticks to burst
```

### 炮根弱点区

炮根是炮塔正面为容纳炮管而留的开口，是薄弱处。模组碰撞体里炮管从炮塔正面**几何中心**穿出
（炮管轴心 X=0.386 / Y=33.955，正面中心 X=−1.88 / Y=34.945，偏差都在 0.15 格以内），
所以弱点区建模为**正面中心的一个圆盘**，只需一个 `radius`。

有个坑：炮管伸出装甲板之外，只做距离判定的话**打中炮管本身也会算成弱点区**。所以额外要求
命中点必须落在正面装甲板上。默认半径 0.4 格，占 T-64 炮塔正面（3.40×1.11 格）的 13% 面积。

### 履带区

> **注意：这一块是几何近似，不是按履带部件判定的。**

模组里 T-64 的履带部件（`track` / `track_other_side`）碰撞体是**每侧 9 个 0.125 格的定位
方块**（负重轮位置），根本没有有效碰撞体积 —— 按部件 ID 判断「打中履带」在游戏里几乎永远
触发不了。而车体碰撞盒完整覆盖履带位置，所以打在履带上的炮弹实际命中车体正面/后面。

因此履带区改用几何划定：**车体正面 / 后面靠外侧的两条竖带，且低于车体高度中线**。
参数按 T-64 模型实测：履带中心线在 |X|≈1.69 格，车体半宽 2.20 格 → 归一化 0.77；
履带内缘约 1.42 格 → `inner_edge` 默认 **0.64**。

履带区优先级高于首上/首下 —— 它们占的是同一个面的不同位置（履带在最外侧，首下在中间下部）。

### 轮胎区（轮式车辆）

T-64 和 M1A1 是履带车，BTR-3 是八轮车。轮胎区和履带区**目的相同、做法不同**：履带条在车体的
**正面/后面**外侧，轮胎在车体的**侧面下半段**。

#### 为什么不能用部件 ID 判定

T-64 的履带没法按部件判定，是因为它的履带碰撞体是每侧 9 个 0.125 格的定位块，根本没有体积。
BTR-3 **不一样**：它的八个轮子每个都有实打实的 `6.04 × 18 × 18`（1/16 格）碰撞盒。所以"按部件
ID 认轮胎"看上去可行 —— 但**实测不行**：

```
main_structure   x  -1.44..  1.45      <- 车体盒
wheelR0          x  -1.44.. -1.06      <- 轮子
```

车体盒的侧面在 **1.44375 格**，轮子最外侧在 **1.43897 格** —— 车体比轮子**靠外 5 毫米**，而伤害
系统是把模型里所有盒子放在**同一个列表**里做射线检测、取最先进入的那个。所以从任何角度打过来，
射线永远先进入车体盒，**轮子一次都不会成为被命中的那个盒子**。

这不是推理，是量的：`WheelProbe` 用模组自己的 `VectorUtil.hitOBB` 从侧面朝八个轮子的高度各打
一发，**每一次都返回 `main_structure`**；把车体盒去掉再打，才每次都命中轮子。这个工具留在
`verify.ps1` 里，改动模型或改动判定逻辑时它会立刻说出来。

#### 于是改成几何划定

轮胎区 = **车体侧面的下半段**，分界线由 `road_wheels.top` 控制（和 `split`、`track_ends.top`
同一套归一化尺度）。BTR-3 的值是 **`0.04`** —— 也是量出来的：八个轮子盒在车体归一化坐标里占
**y −1.030 ~ +0.042**，也就是车体中线往下那一半，占侧面高度的 **52%**。

- 优先级在**反应装甲区之前**，理由和履带条先于首上一样：行走机构是侧面最外层的部件，
  打在那个高度上，碰到的是它。
- 只对**侧面**（`|face| == 1`）生效。正/后面不用管 —— 轮子在车体正后方的盒子里，从正前方打是
  打不到轮子的。
- **轮子之间的空隙也算轮胎**。这是唯一的近似：BTR-3 的八个轮子覆盖约六分之五的长度、分四段，
  空隙约占六分之一。要精确到分段需要在配置里给每个轮子一段 Z 区间，代价大而收益小 ——
  履带条也是这么取舍的。

> **T-64 / M1A1 没有 `road_wheels`**，它们的侧面就是一整块板，行为一点没变。

### 车辆自己的倍率表

目前为止倍率只有两个来源：弹药自带的（机枪那种固定倍率），以及**全局默认**（正面 ×50、其余 ×5）。
T-64 和 M1A1 正面倍率正好都是 ×50，所以一直没暴露问题。

BTR-3 不行 —— 它是铝合金薄壳，**五面全都一样容易被穿透**，正面不该用坦克首上的 ×50。所以
`VehicleArmor` 新增了可选的 `damage_multiplier`，优先级是：

**弹药自带 → 车辆自己的 → 全局默认**

不写这一项的载具（T-64、M1A1，以及所有旧配置文件）拿到的还是全局值，**行为和以前一模一样**。

### 机枪的剩余穿深

两辆车的机枪都走这套机制，而且**数值一一对应** —— 口径相同，就是同一种武器换了个名字：

| | 7.62mm | 12.7mm |
|---|---|---|
| T-64 | `vvp_ywzj:pkt_7_62mm` | `vvp_ywzj:nsvt_12_7mm` |
| M1A1 | `vvp_ywzj:m240_7_62mm` | `vvp_ywzj:m2_50cal` |
| BTR-3 | `vvp_ywzj:kt_7_62_7_62mm` | — |
| 穿深 | **15mm** | **30mm** |
| 倍率 | **×3** | **×5** |

载具包里 M240 的 `damage` 是 10、M2HB 是 20，和 PKT / NSVT 的 10 / 20 完全一样，所以"效果一致"
不是近似，是同一个数。

这些用的是**弹药自带倍率**，不按命中部位区分 —— 机枪穿深太低，打在哪个部位并没有区别。

> **M240 在 M1A1 上出现两次**（同轴一个、装填手一个，在 `turret_machine_gun` 和 `turret_mg2`
> 两个部件上），但那是**同一个武器 id**，所以配置里也只有一条。M2HB 是车长那门。

### 裙板能做的两件装甲板做不到的事

一块板除了"多厚"和"多致命"，还能做两件厚度表达不了的事。两件都加上了，**T-90M 三兄弟是目前
唯一用上它们的车**（见「T-90M」那一节）。

#### 一、穿深削减 `penetration_loss`

**加厚度只有两种结局**：挡住，或者放过去而且**毫发无伤**。中间没有东西。但裙板、间隙装甲、
反应装甲真正干的不是这个 —— 它们不管弹有没有过去，它们管的是**过去的那个已经不是原来那个了**：
杆芯被打断、射流被吹散，于是它对着后面的主装甲是一发弱得多的弹。

```
剩余穿深 = 穿深 − 削减 − 板厚
```

削减**加在板厚之外**，不是替代。所以一块真实的裙板会写成「几毫米钢 + 一个远大于它的削减值」——
钢板本身拦不住什么，起作用的是它造成的那点破坏。

**表现**：对**普通弹**，削减和加厚在算术上是同一件事（见下）—— 一发弹打到第一个区域就停下，
不会带着削减继续去撞后面的主装甲，所以"打穿裙板之后主装甲更弱"这个中间态**还没有发生的机会**。

**爆反是另一条路**：`era_hp` 不是 `penetration_loss`，它是一层**先于主装甲结算的独立评级**。
任何弹打上未消耗的爆反，先扣掉这个评级对应的毫米数，板报废，剩下的穿深再去撞后面的主装甲。
2.0.16 起 VT-4 的 FY-4E 把评级拆成 `era_ce`（射流 300）/ `era_ke`（长杆 150），并带角度衰减；
其它车的面板仍用 `era_hp` 同时充当两者、无衰减。见下面「爆反血量 `era_hp`」。

> 按弹种分开是现成的：写在 `overrides.heat` 里的 `hull_side_era` 就是**只对破甲弹**生效。

#### ⚠️ 对普通弹，它和"加厚"算出来是同一个数

单区域判定下 `穿深 − 削减 − 板厚` 和把板写成 `板厚 + 削减` 得到的**完全一样**。想让两者分开，
只有两条路：

- 打开 `angle_normalization` —— 板厚随入射角变、削减不随，
- 或者让削减**只作用于伤害、不作用于穿深判定**（"它挡不住你，但它把你打残了"）——
  更贴近格栅打破甲弹的真实行为：射流从缝里过去了，但被掐散了。**这条没做。**

写在这里而不是含糊过去，因为"削减"这个名字天然让人以为它已经在做后面那件事。

> **串联战斗部（2.0.16 起）。** 前驱装药把面板引爆、面板报废，主射流只付化学评级的
> **10%** 就继续去撞后面的主装甲。之前"串联弹完全无视爆反、面板也不消耗"的写法是错的：
> 现实中串联弹存在的意义正是先打掉爆反，但爆反确实被消耗了。`GP125`、`BTM1-105`、
> `RK-2S` 这些 `tandem: true` 的弹现在都走这条路径。

#### 二、入射角门槛 `hull_side_era_min_angle`

格栅/栅栏装甲靠的是**把破甲弹的射流横着掐断**，而不是让它从缝里穿过去。所以它**斜着擦进来很有用、
正对着打等于不存在**。这条写成**门槛**而不是曲线，因为门槛是可读的：角度不到，**那些板就等于不在**，
这一发按后面的车体侧面算 —— 这也正是一块有洞的网的诚实描述。

- **`0`（默认）＝ 永远算数**，也就是现有那几辆车的行为。
- 门槛**跟载具走**，不跟弹走 —— 板子的角度是车怎么造的。它对某种弹值多少才写在 `overrides` 里。
- **装甲探测仪会跟着你的视线算**：站在正对面读屏板，读到的是"这块板不会用"的数字。

#### 这两个是怎么验的

规则本身仍然是在一辆**假车**上测的（两块显然编出来的数字）——测的是规则，不是谁的装甲，
而且以后改规则时这组断言还在：

```
=== screens: penetration loss and arrival angle ===
  ok   square on, the screen is skipped
  ok     and nothing is taken off the round
  ok   at 60 degrees the screen counts
  ok     and takes 200mm off the round
  ok   exactly at the threshold it still counts
  ok   a tenth below it, it does not
  ok   the loss is subtracted before the plate is compared
```

伤害表也多了一列 `screen`，普通装甲一律是 0。**T-90M 的侧裙板现在会在表里单独占一行**，
带角度标签，方方正正那一行是它不在的时候：

```
face    zone                      armor  screen  residual   mult    damage    shots
side@30 hull side (reactive)         30     400      50.0    4.0     200.0   blast 2
side    hull                         80       0     400.0    4.0    1600.0   blast 2
```

> ⚠️ 这一行是**差点没打出来**的：表原本只读载具自己身上的 `hull_side_era`，而 T-90M 的裙板写在
> `overrides.heat` 里（因为它只对破甲弹有效），于是"这个机制唯一的用户"在每一张表里都不出现，
> 连覆盖范围那段都整个跳过了。**机制没坏，工具没看**——和本模组那一串「UI、按键、日志都正常，
> 只有效果不对」是同一类。

> 顺带把 `resolveZone` 的参数收成了一个 `Hit` 记录。它原本是一个越来越长的位置参数表 ——
> 机枪口要车体盒尺寸，裙板要入射角 —— 而其中**两个都是 `double[]`**，位置写反了编译器不会拦。
> 每加一个区域就多一个参数，迟早会写反。

### 飞机：蒙皮与内装甲（`aircraft`）

坦克的防护是一块板：打哪一面、多厚、弹能穿多少，三个数就完了。飞机不是——最外面是一层
1.5–3mm 的铝板/胶合板/蒙皮，几乎什么都挡不住；真正决定后果的是弹丸进到机体里面打到了什么：
飞行员、发动机、油箱，还是两层蒙皮之间的一段空机身。所以飞机有自己的一套：

- **蒙皮 `skin`（前/侧/后/顶/底，mm）**：第一层。穿深不到蒙皮厚度就是跳弹/擦伤，零伤害。
- **机翼 `wing`（厚度 + 倍率）**：命中点所在碰撞盒的中心到主碰撞盒中心、沿机体横轴超过
  `wing_from`（格）时按机翼/尾翼处理。也是薄蒙皮，但结构倍率更低，而且机翼里没有可打的部件。
  `wing_from` 量的是机身半宽——`AircraftCheck` 会把它夹在机身半宽和机翼方块中心之间。
- **部件 `components`**：机内长方体，**按弹道先后顺序**测试（不是按命中面）：
  - `armor`：到这部件之前要先打穿的 mm；打不穿就停在这层，只按剩余穿深算机身伤害。
  - `damage_multiplier` / `damage`：到达后对载具的伤害。
  - `crew_damage` + `crew_damage_per_mm`：对 `part_id` 座位上乘员的伤害，上限 20。
  - `part_id` 指向的部件如果没人坐，也会掉血；座椅本身不因为乘员挨枪而掉血。
  - 纯装甲层（座椅靠背、风挡）就是 `armor` 有值、其余全 0 的部件——打不穿就停，
    打穿了继续往后走。
- **机身倍率 `frame_multiplier`（每面）**：穿透蒙皮又没碰到任何部件时，剩余穿深 × 这个倍率。

**与坦克表的区别**

- `hull` / `turret` 仍然写在配置里，值等于蒙皮，**只作删掉 `aircraft` 块时的兜底**；
  `turret_part_ids` 是空数组。装甲探测仪对着飞机时显示「蒙皮 / 机翼蒙皮 + 朝向」。
- **飞机的爆炸不吞**：基础模组的爆炸（含 20mm 的 20 点、破甲弹的近失、TACZ 爆炸弹）照常
  落在飞机上。直击已经由蒙皮模型算过一次，多出来的爆炸是「弹在蒙皮上炸开」那一半，
  对飞机来说不是重复计算；坦克那套「破甲弹自带爆炸」的规则不变。
- **机枪的固定倍率（`multiplier`）在飞机分支里不生效**：飞机必须区分机翼、机身、飞行员，
  一个全局倍率会把三者抹平。穿甲弹/高爆弹自己的平伤（`penetration_damage`）仍然生效。

**三架飞机**（几何量自包里的 `*.structure.json`；数值是公开资料量级的估算，不是逐项档案）：

| | Bf 109E-4 | Fw 190A-5 | P-51D-20 |
|---|---|---|---|
| 生命 | 250 | 280 | 320 |
| 发动机 / 功重比 | 1100 PS / 407.4 hp/t | 1700 PS / 425 hp/t | 1490 PS / 430 hp/t |
| 功重比倍率（参考 420） | ×0.97 | ×1.01 | ×1.02 |
| 蒙皮 前/侧/后/顶/底 | 2 / 2 / 2 / 2 / 3 | 2.5 / 2 / 2 / 2 / 3 | 同左 |
| 机身倍率 | 2 / 2 / 2 / 1.5 / 2.5 | 同左 | 同左 |
| 机翼 | 1.5mm ×1.5 | 同左 | 同左 |
| 发动机 | 装甲 6，×5，+30 | 装甲 8，×5，+30 | 装甲 6，×5，+30 |
| 飞行员 | ×8，+25，乘员 4 + 0.25/mm | 同左 | 同左 |
| 座椅靠背 | 12mm | 14mm | 13mm |
| 风挡 | 40mm | 50mm | 40mm |
| 油箱 | ×4，+60 | ×4，+60 | ×4，+60 |

四种子弹：`tank_assault:gun_mg17`（12mm，×3）、`gun_m2_browning`（30mm，×5）、
`auto_cannon_mg151`（25mm，平伤 45，20mm 高爆）、`auto_cannon_mgffm`（22mm，平伤 40）。
后两种的 25/22mm 是「能穿过 12–14mm 座椅装甲、打不到 40–50mm 风挡」的量级，伤害是战斗部，
不是剩余穿深。`AircraftCheck` / `PenetrationTable` 会打印每架飞机对四种枪的击落发数
（机身/机翼走 `frame`，飞行员走 `pilot`，后者已扣座椅靠背）。

**打一架飞机是什么感觉**（默认数值）：7.92mm 从正后方打座舱被座椅靠背挡住；.50 从同一方向
2–3 发打伤飞行员；20mm 高爆打发动机 2–3 发、打机身 6–8 发；坦克 7.62 同轴机枪打机身约
10–13 发；125mm 主炮一发。机翼命中只算蒙皮 + 结构，不碰机内部件。

**功重比（hp/t）与推力倍率** —— 和地面载具同一套概念，作用点不同：

- `engine_horsepower` / `horsepower_per_ton`：和坦克是同一对字段。Bf 109E-4 用 DB 601A-1 的
  **1100 PS / 407.4 hp/t**，Fw 190A-5 用 BMW 801D-2 的 **1700 / 425**，P-51D-20 用
  Packard V-1650-7 的 **1490 / 430**。hp/t 不写就按包里的 `physics_info.mass` 推。
- `aircraft.engine_reference_hp_per_ton`：**每架飞机自己的参考功重比**，出厂 **420 hp/t**。
  为什么不复用坦克的 25：400 hp/t 的战斗机在 25 的参考下会一直顶到 ×2.0 的上限；而且重型
  轰炸机和战斗机不该共用一个参考，所以这个旋钮在 `aircraft` 块里，不在 Profile 根上。
- `aircraft.engine_power_exponent`：1 是物理规律（加速度 ∝ 功重比），0 关掉；和地面的一样。
- 倍率 = `clamp((hp/t ÷ 参考)^指数, 0.2, 2.0)`，**服务器端**乘在
  `FixedWingVehicle.tickMove` 的 `this.thrust` 上（新 `FixedWingVehiclePowerMixin`；javap 确认
  0.6.3 的 `tickMove` 里只有一处 `thrust` 字段读取）。包的推力曲线、阻力、升力和气动转速上限
  都不动；速度、爬升和能量通过同一个推力项跟着变——和地面「包的自带加速 × 功重比倍率」是
  同一个形状，不是另一套物理。
- 出厂参考 420 是三架战斗机的平均值，所以默认倍率是 **×0.97 / ×1.01 / ×1.02**：HUD 左上角
  会出现「1100 PS · 407.4 hp/t」和「加速 ×0.97」两行，但三架的飞行手感基本不变。把参考调低、
  或把某架的 hp/t 改成实际值，倍率就跟着变。
- **倍率只作用于推力**，不直接乘 `xTurnRate` / `yTurnRate`（那是气动上限，不是功率）；转弯的
  收益来自速度和能量，和真飞机一样。

**适配下一架飞机**：加一个 `vehicles` 条目，设 `aircraft`（skin/frame/wing/wing_from +
components），`hull`/`turret` 抄蒙皮，`turret_part_ids` 空。部件盒以主碰撞盒中心为原点、
components），`hull`/`turret` 抄蒙皮，`turret_part_ids` 空。部件盒以主碰撞盒中心为原点、
沿它的轴量（x 右、y 上、z 机头），可以直接从结构模型的 `main_structure` 和部件骨骼量出来；
`pilot` / `fuel_tank` 这种部件可以用 `part_id` 让检查工具去核对盒子包不包住包里的部件方块。
`AircraftCheck` 会读安装目录里的 `tank_assault` 包，量机身半宽、机翼、部件盒，并且要求
座椅靠背挡得住 MG17、挡不住 .50 和 20mm；包更新挪了骨骼，它先红。功重比那一侧也要填：
`engine_horsepower` / `horsepower_per_ton` 是发动机的额定功率和按包内质量算出的比值，参考值
默认 420——如果新飞机不属于战斗机量级，把 `aircraft.engine_reference_hp_per_ton` 改成它的
同级平均，否则倍率会一直贴在 0.2 或 2.0 的夹子上。

> 量的时候注意两件事：**P-51 的 `main_structure` 是一个很小的座舱盒**（发动机在它前面、
> 飞行员头顶在它上面），部件盒可以超出主盒；**Fw 190 的 `fuel_tank` part 在 JSON 里有、
> 结构模型里没有骨骼**，油箱盒只能从机体量，检查工具会跳过它的 containment 并打印说明。

### 爆反血量 `era_hp`

反应装甲是一层**一次性**的穿深扣除，不再是"轻型 / 重型"两种类型：

```
剩余穿深 = 来袭穿深 − era_hp − 后面主装甲的厚度
```

- 板被引爆的那一发先扣 `era_hp` 毫米；**不管这一发有没有打穿，板都报废**。同一块板的第二发
  面对的是它后面的主装甲。
- 如果来袭穿深**不超过** `era_hp`，这一发被板本身挡下（剩余 0），板同样报废。
- `era_hp` 写在 `hull_side_era` 或 `part_armor` 的板上；写在别处没有用。
- 板的 `thickness` 只是扫描仪和表格的标称值，**不参与这条算术**。默认里两者写成同一个数，
  免得读数与规则打架。
- **串联战斗部不再特殊处理**：前驱装药和主装药算一发，先扣血量，剩下的再去撞后面的装甲。
- v69 及更早的 `"era": "light"|"heavy"` 已移除。升级时旧类型按板的 `thickness` 转成
  `era_hp`：T-64 侧面 500，T-90M 的块 300 / 600，M1 的 ARAT 140 / 290 或 600 / 800，
  VT-5 侧面 300。

#### 谁是多少

| 车 / 板 | `era_hp`（对穿甲弹） | `era_hp`（对破甲弹） | 后面的主装甲 |
|---|---:|---:|---|
| T-64 车体侧面 | 500 | 500 | 车体侧面 200 |
| T-90M `era_1`–`era_5` | 300 | 600 | 车体侧面 80 / 炮塔侧面 250 |
| M1 ARAT 瓦片 | 140（车体）/ 290（炮塔） | 600 / 800 | 车体侧面 200 / 炮塔侧面 400 |
| VT-5 车体侧面 | —（只在 `heat` 表） | 300 | 车体侧面 200 |
| **VT-5 车体正面 `hull_era`** | **200** | **200** | **首下 100 / 首上 200** |
| **VT-4 `hull_era` / `hull_era2`（FY-4E）** | **200** | **200** | **首上 850** |
| **VT-4 `turret_era` / `turret_era2`（FY-4E）** | **200** | **200** | **炮塔正面 850 / 侧面 100** |
| **天马-20 `hull_era_l` / `hull_era_r`（侧裙）** | **200** | **200** | **车体侧面 80 / 150** |
| **天马-20 `turret_era_roof`（炮塔顶）** | **200** | **200** | **炮塔顶部 30 / 55** |

VT-4 的四块板是 2026-11-08 按 VT-5 的机制补的，车体和炮塔都是 FY-4E，抗穿按 **200mm** 算。
它原来的化学表 1050/300 是**含爆反的总数**，现在拆成「板 + 后面的主装甲」：首上
200 + 850 = 1050，炮塔正面 200 + 850 = 1050，炮塔侧面 200 + 100 = 300。**板还在时总数和
以前一样，板被打掉后落到后面的数**——这就是一次性爆反的全部意义。板写在载具自己的
`part_armor` 上（不在 override 里），所以穿甲弹也会先被扣 200：打首上 200 + 600 = 800（v77
起首上顶部那条 800 的跳弹带是 200 + 800 = 1000），打炮塔侧面 200 + 180 = 380，打掉后回落到
板后面的数。`hull_era` 与 `hull_era2` 按高度分工，`turret_era` 与 `turret_era2` 按左右分工，
四块互不重叠。

天马-20 的三块板是 2026-11-15 按同一机制补的：两条车体侧裙（`hull_era_l` / `hull_era_r`，
显示模型里是 `hull_era` / `hull_era2`）和炮塔顶部一整块（`turret_era_roof`，显示模型
`turret_era`）。它们是**侧面和顶面**，不是正面弧——正面的 ERA 仍旧算在正面值里，所以没有
任何旧数字被改动，板是额外的一层。三块都按 **200mm**（和 VT-4 的 FY-4E 同一个假设；朝鲜的
ERA 没有公开数字，进游戏用扫描仪校正）。结构模型给每块一个碰撞盒，并把炮塔原来的一个大盒子
切成 5 块，在顶板上方留出空腔——否则基础模组"最近的 OBB"永远先命中炮塔盒，板永远打不到。

#### BTR-3 的 RK-2S「屏障」

载具包自带的 `vvp_ywzj:rk2s_barrier`（挂在 `turret_missile` 上），800mm，是本模组第一发串联弹，
也是 BTR-3 唯一的反坦克手段。它自带 120 点爆炸，没有顶掉 —— 和 30mm 高爆弹一个道理，这个量级
淹不掉装甲表。（它不是多用途弹：引信不可切换，`multi_purpose` 那一套和它无关。）

打 T-90M 的 `era_3`：第一发 800mm 先扣化学血量 600，剩 200，撞炮塔侧面 250 → **挡下**，板报废。
第二发 800 − 250 = 550 → **打穿**。旧版本里第一发按板的 600mm 厚度结算、能打穿；现在它是
"先扣血再撞侧面"，所以第一发反而被挡下 —— 这是新机制的直接结果，不是数值错误。

打 T-64 的侧面：800 − 500 = 300，撞车体侧面 200 → 100 剩余 → **打穿**；板报废，第二发
800 − 200 = 600。表里 `hull side (reactive) (500mm) > hull` 这一行就是第一发，下面一行
`(spent) > hull` 是第二发。

> T-90M 那条 `side@30` 的格栅裙板**没有** `era_hp`（它是格栅，不是爆反），所以它仍然只有
> `penetration_loss` 400，按普通裙板结算：削减 400，再按裙板本身算。
>
> 侧裙上的 `era_1`/`era_2` 和炮塔上的块一样是爆反；**"板用掉之后落到哪里"由部件在模型里
> 挂在哪棵骨骼上决定**，不是配置写的 —— 侧裙的落回车体侧面，炮塔上的落回炮塔。

#### 怎么验的

规则在**假车**上验（一块 200 血量的炮塔盒和一块 300 血量的侧面爆反，都是编出来的数字），
而且全部走模组自己的 `ArmorSystem.resolve` —— 就是游戏调用的那个方法：

```
=== reactive panels: a single-use layer worth its HP ===
  ok   a round through a panel is measured against the armour behind
  ok     and the panel took exactly its HP
  ok     naming the panel it met
  ok     and spending it
  ok   the next round finds it gone
  ok     and arrives with no panel against it
  ok     still naming the panel it passed
  ok   a round weaker than the panel is stopped by it
  ok     and the panel takes the whole round
  ok     and is spent doing it
  ok   a flank panel is a layer in front of the flank
  ok     and takes its own HP off the round
  ok     and carries that HP on the stopped zone
  ok   ordinary armour has no HP and no panel
```

> 第二发的那几条是**这个机制唯一的坑**：`"一次性"`问的是过去，所以实现必须有记忆。一个无状态
> 的写法会把"第二发打穿"永远算成"第一发被挡下"—— 而其余每一行看起来都完全正确，只有在游戏里
> 对着同一块板打第二发时才看得出来。
>
> 最后一条是**防退化**的：`era_hp` 只在写了的时候才写出，一个"默认打开"的写法会把**普通钢板**
> （炮根、履带条）也变成爆反。所以往返一遍之后它们必须**还是 0**。

### 车体侧面附加装甲（豹2A4 的两块侧裙板）

豹2A4 每侧车体的前半段挂着一组附加装甲板。**它们是两个真正的部件**，不是一层配置层：
结构模型里各有一个文件级根骨骼 `hull_addition_armor` / `hull_addition_armor2`，载具
json 里各有一个 `ywzj_vehicle:generic` 部件。这是 vvp 的 T-90M 用 `era_1` / `era_2` 做
侧裙的同一套形状 —— 一发打在板上，基础模组把它判定到那块部件，附加包再按部件 id 结算。

```
动能弹   part_armor         100 mm，一次性
破甲弹   heat / he 覆写     300 mm，一次性
板后面的车体侧面            60（动能）/ 150（破甲）
```

- **每块板只吃一发。** 穿深不超过板的那一发被整发挡下，不伤车；更大的扣掉板的值，剩下的
  再去撞后面的车体侧面。第二发打在同一处，直接落在车体上。
- **左右完全独立。** 打掉左边，右边的板还在。
- **只覆盖板在的地方**（从显示模型量的：每侧 x ±1.97…±2.31、y 1.17…1.79、z 2.24…4.80，
  即车体前一半）。侧面后半段没有板，打在那里的弹从来没有这一层。
- 配置：`part_armor` 里两条 `new Plate(100, 5).reactiveHp(100)`；化学表（`heat`，
  `he` 经 `thinRoofs` 共用同一张表）两条 `new Plate(300, 4).reactiveHp(300)`。其中的
  `multiplier`（×5 / ×4）是表格和扫描仪的读数，**不参与这条算术**：爆反式面板把穿透的
  弹交给它后面的 zone，伤害倍率用的是后面那个 zone 的。
- **v81 → v82**：v81 的 `hull_side_addon` 三发血池被这套部件取代。升级时，文件里仍是出厂
  写的那一层（150 血、60-40-20%、90/5）会被移除；玩家自己写过的那层保留，日志会说明。
  两块板本身是新的 `part_armor` 键，由 `adoptMissingBoxes` 补进旧文件。
- 扫描仪把两块板当作普通部件显示；`LeopardAddonCheck` 同时检查配置、pack 里的部件 /
  结构盒 / 显示骨，以及上面那几条算术。

> **为什么以前不是这样。** v81 及更早，模型上只有显示骨骼，没有结构骨骼、也没有部件：
> 游戏里没有东西可以把一发判定到"某一块板"上，只能按车体侧面结算。所以当时只能做成
> 一层挂在侧面 zone 上的区域规则（`hull_side_addon`），150 血、三发 60-40-20%、左右
> 共用一个血池，而且整条侧面（包括没有板的后半段）都算。
>
> 那一层机制还留在代码里（`Plate` 的 `addon_hp` / `addon_fractions`），但没有载具再用它。
> 有载具需要"没有部件、只能按侧面结算"的附加层时仍可直接写；有模型部件时用 `part_armor`。

### 破甲弹（HEAT）与溅射

2A46M-1 125mm 破甲弹（`vvp_ywzj:2a46m1_125mm_heat`）穿深 480mm，用 `heat` 这一套厚度。

爆炸反应装甲区是**几何近似**：车体侧面**前半段**（从车头往后 50% 车长）算作有反应装甲覆盖，
后半段算裸露。模组里没有反应装甲的模型可以参照，这个界限是估的，用
`hull_side_era_front_fraction` 调（`1.0` = 整条侧面都有，`0.0` = 都没有）。

**溅射**：破甲弹命中时额外造成 `1.5 ~ 3` 的随机伤害，**无视装甲厚度**，并给车组上 1 秒原版
失明。注意它**未击穿也会触发** —— 起爆的是打在装甲外面的战斗部，不是射流本身。

#### 基础模组的爆炸已经被顶掉

破甲弹打中**任何实体**时，`AmmoEntity` 都会额外生成一个 `VehicleExplosion`（载具包里写的是
`damage: 1500, radius: 4`），而且这个爆炸**完全不看装甲** —— 它是按载具包里的裸数值直接扣血。

之前它一直生效，导致：**不管你把等效厚度设成 880 还是 500，打上去照样掉一千多点血**，装甲表
形同虚设。这就是"等效厚度没有生效"的真正原因 —— 厚度生效了（日志里写得很清楚是 880 / 500），
但那 1500 点爆炸伤害跟厚度无关。

现在破甲弹带 `"replaces_base_explosion": true`：这个爆炸**对配置里登记过的载具不再造成伤害**，
由本模组的溅射数值（1.5~3 + 失明）取而代之。注意：

- 爆炸**本身照常触发** —— 方块照样炸、爆炸半径内的其它实体（包括没有装甲配置的载具、玩家）
  照样受影响，**只有这辆车的伤害被拦下**。
- 想恢复基础模组的行为：把该项改成 `false`。
- 每次拦下都会打一行日志，方便确认：
  ```
  [Vehicle Armor] vvp_ywzj:t64 blast of 1312.5 damage dropped by vvp_ywzj:2a46m1_125mm_heat; this round carries its own
  ```

> ### ⚠️ 另外两点
>
> **1. 1.5~3 的溅射对 T-64 几乎不可见。** 3000 血的车挨 3 点伤害是 0.1%。这个数值是按你说的
> 写的，但如果你想让它有实际手感，得调到几十上百。现在基础模组的 1500 被顶掉了，这个数值就是
> **未击穿时唯一的伤害来源**，所以它到底要多大，值得再想想。
>
> **2. 破甲弹打不穿首上、炮塔正面和反应装甲侧面。** 穿深 480 对 840 / 880 / 500 —— 全部未击穿。
> 正面能打穿的只有**炮根**（300mm，5 发）和**首下**（120mm，3 发）；绕到侧面后半段、后面
> （200mm，3 发）也打得穿。

> ### ⚠️ 这五门机枪现在几乎打不穿任何有装甲配置的车
>
> **对 T-64 / M1A1**：两辆车最薄的装甲都是 **90mm**（各自的车体后部），机枪穿深只有 15 / 30mm，
> 剩余穿深恒为负数 → 未击穿 → **恒定 0 伤害**。
>
> **对 BTR-3**：最薄处 8mm（车顶），15mm 打不穿；**12.7mm 那一档（30mm）反而打得穿**，
> 打顶部是 `(30−8)×5 = 110` 点 —— 薄壳车怕大口径机枪，这是这套数字自然得出的结果。
> BTR-3 自己没有 12.7mm，所以是"别人拿 .50 打它"。
>
> 对比改动之前：五门机枪都走原版管线，每发 10 或 20 点伤害。改完之后它们对有配置的车要么
> 完全无害、要么按装甲结算。
>
> 这是「穿深 15/30 vs 装甲 8/90mm」的直接推论，不是 bug。想让 7.62mm 也能蹭点血，把穿深提到
> 90 以上 —— 例如改成 100mm，打坦克后部就是 `(100−90)×3 = 30` 点。要改就三门一起改。
>
> 另外注意：这套机制**只对配置里 `vehicles` 列出的载具生效**。机枪打其他载具仍然走原版。

### 部件损毁后无法开火

**基础模组没有这个功能。** `WeaponUnit#shoot` 里完全没有 `isDestroyed()` 判定 —— 它只在
`tickRot` 里对损毁部件取消双向稳定器，瞄具叠加层会把损毁部件染成另一种颜色，但**扳机不受影响**。

实现方式是**监听事件**，没有用 Mixin：基础模组的开火决策在客户端做，
`AbstractVehicleWeapon#doClientShoot` 和 `VehicleMultiWeapons#doClientShoot` 都会先投递
`VehicleFireEvent.Pre`，只有没被取消才会调 `sendShoot()` 发包给服务端。在这里取消，炮弹
在发包之前就被拦下了。

被拦下时会在动作栏提示「武器已损毁，无法开火」（1.5 秒内不重复），免得玩家以为是卡了。

> ### ⚠️ 这一条会让 T-64 变得非常脆
>
> 载具包里 T-64 的**炮塔部件血量是 1000**，而按当前数值，任何一发打穿炮塔的炮弹伤害都
> 远超它：
>
> | 打穿炮塔的部位 | 对炮塔部件的伤害 |
> |---|---|
> | 炮根弱点区 | 1285 |
> | 炮塔侧面 | 1535 |
> | 炮塔后部 | 1835 |
>
> 也就是说：**炮塔被击穿一次，主炮就永久报废**，剩下的只有车顶机枪。而车体血量是 3000，
> 意味着炮塔会比整车先「死」很久。
>
> 这个结果完全来自你选定的数值组合，不是 bug。如果觉得太狠，两个方向：
> - 调低炮塔各部位的 `multiplier`（炮根 5 → 2 就变成 514，两发才废）
> - 或者改载具包里 `t64.json` 的 `parts[turret].max_health`（1000 → 4000）
>
> 关掉整个功能：配置里把 `destroyed_parts_cannot_fire` 设为 `false`。

### 开火特效与炮声（仅装甲先锋，20mm 以上火炮）

**基础模组只有「一声通用炮响 + 两团烟」。** 装甲先锋包里的 `cannon_105mm`、`cannon_120mm`、
`cannon_125mm` 三个武器显示文件都指向同一个 `ywzj_vehicle:cannon_125mm_shot`，105mm 和
125mm 开火听起来一模一样；炮口也没有火焰，只有两团不动的烟。这个功能把这三件事都换掉了：

> **只换装甲先锋。** 换声音的理由是那个包自己的武器文件全指向同一条录音；别的包有自己的
> 炮声（坦克突击的 75/88mm、抗战包的 47mm 维克斯、VVP 的 125mm），换掉它们是**拿走**
> 而不是改进。所以 `WeaponEffects.handles()` 多了一道判据：载具 id 的命名空间必须是
> `armor_pioneer`。其他包的 20mm 以上火炮**完全走基础模组自己的声音、烟雾和开火位置**——
> `AbstractVehicleWeaponFireMixin` 只在 `handles()` 为真时才压掉基础模组的炮声、才把
> 烟团挪到前炮口，否则原样把基础模组自己的瞄准上下文还回去。下面这张口径表只在装甲先锋
> 的载具上有意义。

- **炮声按口径分档**，每种都有超音速的脆响、低频压力波和周围环境的反射；
- **炮口焰**：四层**加色混合**——白热火球核心、沿炮管展开的撕裂火舌、从炮口侧面翻出的
  火团、向前飞散的火星；每张火焰随机形状/旋转，按口径决定大小、长度和数量；
- **炮口烟**：按实拍比例重做——大口径主炮 **18–48 团主烟**（白/灰渐变，核心偏暗）、
  **8–30 团近地扬尘环**，寿命 **2–8 秒**；先沿炮管前喷再上升，部分烟团会长时间悬停。
  30mm 自动炮仍然只有几团短烟，不会平白多出一大团；
- **延迟回声和炮闩声**：约 0.7–1.5 秒后从环境里传回来的闷响，加上 0.2 秒左右的一声
  炮闩/后坐金属声（基础模组自己的抛壳声仍然保留）；
- **弹丸激波（声锥）**：炮弹以超音速飞出后，从你身旁掠过时的一声脆响。射手听到的是
  离膛后前方约 32 格的那一下，旁边的人听到的是弹道离自己最近的那一点——它挂在弹丸
  本体上算，不是开火事件的一部分，见下。

| 口径 | 声音 | 装甲先锋里的例子 |
|---|---|---|
| 20–59mm | `autocannon` | QLZ-04 35mm、AGS-30 30mm |
| 60–89mm | `cannon_light` | 这个包没有这一档 |
| 90–109mm | `cannon_medium` | VT-5 / ZTZ-100 的 105mm |
| 110–139mm | `cannon_heavy` | VT-4 / K2 / 10 式 / 豹2A4 的 120mm、VT-4 / ZTZ-100 的 125mm |
| ≥140mm | `cannon_artillery` | 152mm 及以上（这个包没有，留给以后） |

> **电平与破音（2026-10-25 修）。** 早先各层音量是 8–12，report + 回声 + 炮闩 + 激波
> 叠起来约 **16–21% 的样本超过满刻度**，开火瞬间听起来就是糊/破音。现在 report 按
> 3 / 4 / 4.5 / 5 / 5.5（自动炮→大口径），回声、炮闩、激波也都降到背景层；炮闩延后到
> 0.4–0.7 秒，避开最响的那一下。采样同时去掉了过重的软削波，并加了 10kHz 上限。
> 按同样的叠加模拟，新 125mm 在音量 5 下超满刻度约 **6%**；作为参照，基础模组原炮声
> 在音量 4 下约 **29%**。如果觉得整体变轻了，可以把「玩家」音量开大；要改代码里的
> 基准，把 `WeaponEffects.volume()` 抬到 6–6.5 仍比旧版干净。

**触发点在客户端的事件上，不在我们的发包逻辑里。** 玩家扣扳机后，客户端只把射击请求发给
服务端；服务端确认后才把 `ServerVehicleFire` 广播给所有跟踪这辆车的客户端（包括射手自己），
基础模组再把包转成客户端侧的 `VehicleFireEvent.Post`。我们监听的就是这个事件——所以射手和
旁观者看到的特效完全一致，不需要额外的网络包，也不用相信客户端自己算的弹道。

**弹丸激波走的是另一条路：它挂在弹丸本体上。** `BulletEntity` 在客户端是真实实体，
spawn 包带着初始位置、速度和口径，两个端各自按同一速度推进。客户端 Mixin
`BulletEntitySonicBoomMixin` 在这发弹丸的第一个客户端 tick 上把它交给 `ProjectileCrack`：
取弹丸当前位置和前向速度构成的直线，算它离本机玩家最近的一点；弹丸到达该点需要
`沿弹道距离 / 弹速`，激波再从该点传到耳朵需要 `最近距离 / 声速`（343 m/s，即 17.15 格/tick），
两者相加就是要等的时间。射手（离炮口 12 格以内）不按最近点算，而是在弹道前方 32 格
放一声"离膛脆响"，再留 2 tick 余量——否则它会和炮口最响的那一下叠在一起；这也保证了
单机自己开炮时能听见。

只对**口径 ≥ 20mm 且速度 ≥ 12 格/tick** 的 `BulletEntity` 生效：12.7/7.62 机枪被口径
排除，35mm 榴弹发射器（10 格/tick）被速度排除。**60mm 以上放宽到 10 格/tick**——豹式的
75mm 和虎式的 88mm 武器文件根本没写 `velocity`，会落到基础模组默认的 10；现实里这两门
炮都是超音速的，这是数据缺口而不是事实，所以按口径放行。每个客户端自己算自己的，
不需要发包；弹丸的轻微下坠和玩家在飞行途中移动没有建模（飞行通常不到一秒），
这是这条特效的已知误差。

**只对 `VehicleCannon` 且口径 ≥ 20mm 的武器生效。** 导弹、火箭弹、炸弹、榴弹发射器里的
抛射类武器保持原样；7.62mm 和 12.7mm 机枪也保持原样（它们是机枪，不是火炮，载具包自己的
录音本来就合适）。多武器槽位（`VehicleMultiWeapons`）取**当前选中的那一发**来判断口径，
所以 VT-5 切到 105mm 破甲弹或 ATGM 时，声音和火光会跟着变——ATGM 是导弹，回到基础模组。

**基础模组的那一声开火炮响会被拦掉，只拦这一声。** 客户端 Mixin
`AbstractVehicleWeaponFireMixin` 精确重定向 `AbstractVehicleWeapon#onClientFire` 里那一次
`Level#playSound` 调用；开火烟、抛壳声、后坐动画、炮管火焰动画都不动。这样同一发炮弹不会
同时响两套炮声。

**声音是合成的，不是从别的音效包里抄的。** `tools/audio/make_cannon_audio.py` 用
numpy 生成 44.1kHz 单声道 Ogg Vorbis：超音速脆响、低频压力波、爆炸主体、早期反射、
指数衰减的扩散尾音，最后做软削波。`projectile_crack_1..3.ogg` 是弹丸激波，不是缩小版
炮响：几百微秒的宽频冲击 + 中高频鞭响 + 下扫的窄带 + 浅低频 N 波，0.62 秒以内。
改完参数重新运行即可，RNG 种子固定，输出可复现：

```powershell
uv run --with numpy --with soundfile python tools/audio/make_cannon_audio.py
uv run --with numpy --with pillow python tools/audio/make_muzzle_flash_textures.py
```

炮口焰的贴图也是同一个目录下的脚本画出来的：四帧不规则火球、三帧拉长的喷流、一帧
对称火星（白色 + alpha，粒子上色）。

**炮口焰是加色混合的，不是普通的半透明贴图。** 自定义的 `ParticleRenderType` 用
`SRC_ALPHA, ONE` 混合，并关闭深度写入、保留深度测试：同一位置的几张火焰会叠成白热核心，
而不是互相覆盖；墙和车体会正常挡住它。五类粒子的分工：

| 粒子类型 | 作用 |
|---|---|
| `muzzle_flash_small` / `muzzle_flash` / `muzzle_flash_large` | 火球核心，按口径选大小 |
| `muzzle_flash_jet` | 拉长、撕裂的火舌，铺在炮口前方 |
| `muzzle_flash_spark` | 带重力的火星 |

每一张火焰都在出生时随机选帧、随机旋转、随机大小，并且寿命过半时再换一帧，所以连射时
不会像同一枚印章盖出来的。

> **参考实拍。** B 站《【坦克鉴赏】4K原声 | 德国豹2主战坦克开火射击演练合集》
> （[BV1tE421w731](https://www.bilibili.com/video/BV1tE421w731/)）里最抓眼的不是炮口那一下，
> 而是火球之后**几秒才散的白/灰烟团**和车体周围被吹起的地面尘土。现在的主烟团、尘环、
> 长寿命烟团就是按这个比例做的。**体积烟、热浪和动态光照是粒子系统做不到的**；镜头震动
> 也还没做——要的话可以按距离/口径加 3–8 tick 的轻微震屏，但有人会晕，所以没有默认开。

> **炮口位置的坑（2026-10-25 修）。** VT-4 的 `turret_barrel` 在结构模型里是**两个 cube**：
> 后段 30 单位、前段 99 单位。基础模组的 `buildBolts` 每个 cube 生成一个 bolt，
> `getCurrentBolt()` 逐发轮换，所以炮口位置有一半概率落在后段（炮根），特效和基础烟雾
> 都会跟着错。现在 `MuzzleSelect` 把所有 bolt 投影到炮管方向，只取最前面的真实炮口；
> 双联装这类真正并列的炮口投影相同，两个都保留。基础模组自己的烟雾也用**等长重映射**
> 挪到前炮口，`countFire(aimContexts.size())` 的计数不变。
>
> **粒子图集从哪来。** 它不在 `Minecraft` 的 atlas 表里，而是 `ParticleEngine.f_107296_`
> 自己持有的；取贴图要过 `ParticleEngineAtlasAccessor`（`@Accessor`）。用
> `Minecraft#getTextureAtlas(textures/atlas/particles.png)` 会拿到**另一张表**的查找函数，
> 调用时 `Map.get` 返回 null 直接 NPE —— 粒子一创建就崩，游戏里什么都看不到，日志里每个
> tick 一行 `Exception while adding particle`。第一版炮口焰就是这么消失的，现在有访问器和
> 一次性缺失警告兜底。

**想调音量**：没有新增配置项；用的是 Minecraft 的「玩家」音量通道（和基础模组的开火声
同一条通道），在游戏里调「选项 → 音乐和声音 → 玩家」即可。想彻底关掉这个功能，删掉对应的
资源包或卸载本模组；没有半开状态，因为炮声和炮口焰是同一个事件里一起发生的。

**已知限制**：

- 炮口焰是**自发光粒子，不会真的照亮周围方块**（没有动态光源），夜里能看见火焰本身，但
  地面不会跟着亮一下；加色粒子也不写深度，只保证不会挡住自己，仍会被墙和车体遮挡；
- 烟团是**公告板粒子**，不是体积烟，也没有热浪扭曲；大口径主炮的烟团数量是按视频比例
  放的，**光影/低配下可能掉帧**——如果明显卡，把 `BlastScale` 的档位降一档即可；
- 旁观者看到的炮口位置来自**自己客户端**当前的炮塔朝向，网络延迟一两 tick 时可能和实际
  弹道差一点，但闪光只有 0.2 秒，基本看不出来；
- 多武器槽位的**当前选中弹种**通过同步数据到达客户端，切换后的第一个 tick 内如果客户端
  还没收到同步，可能短暂沿用上一发的口径分组（同一辆车的口径通常相同）；
- 这套特效**按载具包的命名空间决定，和装甲配置无关**：`armor_pioneer` 的车用新特效，
  其他包的 20mm 以上火炮一律保持基础模组原样。反过来也成立——装甲先锋里没配装甲表的车
  （如果有）照样用新特效，因为这是"这个包的声音"，不是"这辆车的装甲"。
- **弹丸激波（声锥）仍然对所有包生效。** 它是**叠加**的一声，不替换任何原有声音，所以
  不属于"覆盖"的那一类；要把它也限定在装甲先锋，得按弹丸上的武器 id 判命名空间
  （`AmmoEntity.vehicle` 字段不同步到旁观客户端，看弹丸自身的 `vehicle` 不可靠）。

`tools/EffectsCheck.java`（在 `verify.ps1` 里）把音效、五个粒子类型各自的帧集、烟尘档位、
炮口选择、翻译、客户端接线和**两个 Mixin 的目标**对在一起检查——开火声重定向的
`playSound` 描述符、`aimContext/aimContexts` 的前炮口重定向，以及弹丸激波挂的
`BulletEntity#tickMove`；它还会在内存里故意删掉一个音效事件、截断一个 Ogg，
要求自己的校验必须报错。

### 弹药合集（手持工具）

新增物品 `ywzj_vehicle_armor:ammo_compendium`，中文名「弹药合集」。**右键**打开**目录页**，
**点弹种**进入该类弹药的列表，**Esc 或点「← 返回目录」**回到目录。

弹种分两个维度看：**弹种**（穿甲弹 / 破甲弹 / 高爆弹）和**武器类别**（火炮 / 机炮 / 机枪）。

```
         弹药合集                         ┌──────── 穿甲弹（Esc 返回）────────┐
  分类              数量                  │ 弹药               等效穿深       │
  穿甲弹              8 发                │ ── 火炮 ──                      │
  破甲弹              3 发                │ M829-120mm APFSDS         570mm │
  高爆弹              3 发                │ 3BM42-125mm APFSDS        457mm │
                                          │ ── 机炮 ──                      │
                                          │ MK258-30mm APFSDS         116mm │
                                          │ 3UBR8-30mm APFSDS          90mm │
                                          │ ── 机枪 ──                      │
                                          │ M2HB 12.7mm                30mm │
                                          └─────────────────────────────────┘
```

> 两门 30mm 的钢针各占一行，用它们**真实的型号**（MK258 是 XM813 打的 30×173，3UBR8 是 ZTM-1 打的
> 30×165），而不是弹链名 —— 弹链在游戏里没有名字，链里那两发弹才是能选的东西，见下。

- **两级而不是一长条**：不同架次的弹药之间没有可比性 —— 机枪子弹和坦克炮没法放在一起比 ——
  而按穿深排成一条，恰好会把这两类挨着放，且看不出为什么。
- 第二页里的**武器类别标题只在需要时才画**：一个弹种下只有一类武器时不画（今天的破甲弹全部
  由火炮发射，就没有标题），有两类以上才画。标题是给"需要区分"的地方用的，不是页面的装饰。
- 每一类内部**按穿深从高到低**排；弹种和武器类别的顺序都是枚举里声明的顺序，不是按穿深排的。
- **空分类照常显示并标 0 发**，不会消失 —— 消失会让人以为这个分类不存在。
- **多用途弹显示两个数**（碰炸档 / 近炸档）。今天这两个数相同，但显示两个是有意的：读这一行
  就是想看"两档各能打穿什么"，只给一个数会读成"换引信没有任何区别"。
- 行数多的时候**行高会自动压缩**（下限 6 像素），配置里再加十几发弹也不会撑出面板。
- 只有**能点的行**会高亮：点不动的行跟着亮是在许一个页面不兑现的承诺。

#### 分类是两个维度：弹种 × 武器类别

弹种不是一列平铺的标签，而是**两个正交的问题**：

| 维度 | 取值 | 回答什么 |
|---|---|---|
| `Warhead` 弹种 | 穿甲弹 / 破甲弹 / 高爆弹 | 这发弹到了之后干什么 —— 动能硬顶、射流烧穿、还是炸 |
| `WeaponClass` 武器类别 | 火炮 / 机炮 / 机枪 | 是谁把它打出去的 |

两者分开是因为它们**确实是两件事**：30mm 机炮和 125mm 坦克炮可以打同一种弹头，而书既要能说
"这是动能弹"，也要能说"这不是给你机枪用的"。`AmmoCategory` 是**实际存在的组合**：六种，
而不是理论上九种，因为包里只有六种。

**配置里写的 `category` 字符串一个都没变**（`cannon_ap` / `machine_gun` / …），所以这次拆分
**不需要迁移任何配置文件**。变化只在解释上：`machine_gun` 现在被理解成"穿甲弹，由机枪发射"，
而不是"和三个弹种并列的第四种东西"。

> 机枪子弹归入**穿甲弹**。原来单独成一类，理由是"7.62mm 分穿甲和高爆只差几毫米，分进去没意义"
> —— 那条理由反对的是**把机枪子弹再往下细分**，而不是反对它有个弹种；现在它仍是一格，只是
> 归到了它本来就在的那一格。

**为什么分类存在配置里，不像名字那样问载具包**：

- 载具包能回答"这门炮叫什么"，**回答不了"玩家期望它放在哪一格"** —— 分类是关于这本书怎么读的
  选择，和穿深、溅射一样属于本模组自己那一半。
- 武器数据是**联网同步**到客户端的。书如果必须问载具包才能分类，那它在数据到达之前就是一个空目录。
- 按口径推会有阈值（≥50mm 算火炮？），而**猜错的阈值会静默地把一发弹放到错误的格子上**。

没写 `category` 的条目（手改配置时）按 `profile` 推：`heat`→火炮破甲弹、`he`→火炮高爆弹、
其余→火炮穿甲弹。**弹种不会推错，只有"是什么炮"是猜的，而且猜成火炮** —— 这对本模组
自带的每一发弹都成立，除了机炮和机枪那几发，它们是明写的。

> 升级路径里有一条：旧配置文件（v20 及以前）没有这个字段，**凡是默认值里写了分类的条目，
> 缺就补上**。不补的话机枪会被兜底规则塞进"火炮穿甲弹"。只在文件里没有时才写，手改过的保留。
>
> "要不要画武器类别标题"这条规则（`AmmoCategory.groupsByWeapon`）放在分类这一侧、**吃一串
> `AmmoCategory`**，而不是放在 `AmmoIndex` 上问它。原因很实际：`AmmoIndex` 列弹药时要问载具包
> 要显示名，那一问会把游戏自己的类拖进来 —— 而离线的 `AmmoCompendium` 工具没有游戏，一调用
> 就 `NoClassDefFoundError`。（这不是假设，是这次改的时候真炸了一次。）

#### 名字从哪来：载具包，不是本模组的配置

名字直接问基础模组的武器注册表（`CommonAssetsManager.vehicleWeaponManager()`），
**不是**在这个模组的配置里再存一份。这样书里写的和炮塔选择器里写的**不可能对不上** ——
本模组知道自己那一半（穿深），载具包知道自己那一半（名字），各问各的。

> 问不到的时候显示武器 id 本身。这不是错误路径：武器数据是**联网同步**到客户端的，书比它先打开
> 就会这样。看见 `vvp_ywzj:xxxx` 就说明"没问到"。

#### 图标

原版书（`minecraft:textures/item/book.png`）改色：**把红绿两个通道互换**（仅当 R > G）。
书的封皮是棕色（R > G），换完变绿；纸页是灰的（R == G），一点没动；描边接近黑，也没动。
比"把棕色像素挑出来染绿"可靠，因为它不需要事先知道封皮是哪几个色号。

#### 翻页（`↑` / `↓` 或滚轮）

**弹药多得铺不下一页的时候翻页**，一页固定放下多少就多少。**只有真正的弹种页会翻** ——
目录页只有三行。

> **在这之前是"把行压扁到能塞下"**（最低压到 6 像素一行）。那在弹药少的时候没问题，**弹药一多就正好
> 坏在最有用的地方**：四十发弹的时候字直接画在字上面，整页不是"挤"，是**读不了**。
> 翻页才是老实的答案，也是书本来的做法。

- **`↑` / `↓` 翻页**，和**装甲探测仪翻表格用的是同一对键**（同一个按名字查 GLFW 的 `keyCode`），
  所以"上下键在表之间走"在两个工具里是同一个手势。
- **鼠标滚轮也行**，且**只有指针在面板上时才翻** —— 滚轮往上翻到前一页，和电脑上任何其他列表一致。
- **到头即停，不会绕回**，和方向键调车高同一个道理。
- **页码画在底部**（`第 2 / 3 页`），左半边是提示。**只在不止一页的时候才画**。
- **底部那一条高度是常驻预留的**，不管够不够一页都留着 —— 不然一本从 3 发变成 4 发的书会在
  **点进去的那一下**改变每页容量，整页行跟着跳一下。
- **换车/返回都把页码归零**，所以打开一个弹种永远从第一页开始。
- **窗口变小不会把页码弄丢**：存的页码不动，**显示**的页码按现在装得下的重新算 ——
  窗口再放大还能回到原来那页。

#### 离线预览

`tools/AmmoCompendium.java` 在不开游戏的情况下打印**目录页和每个架子**：读配置拿分类和穿深、
读载具包 zip 拿名字。存在的意义不只是预览：**武器注册表只在运行中的游戏里有**，没有这个工具的话，
"配置里写了一个载具包根本没有的武器 id"（书里显示成一串 id、而且谁也开不了这一炮）就只有打开书
才知道。它先把目录打出来，正是为了**让"放错架子"看得见** —— 一发弹放错架子，只有看它出现在哪个
架子下面才发现。

它还**走一遍翻页**：对每个弹种、在 1 / 4 / 7 / 12 / 40 这几个每页容量下，从第一页翻到最后一页，
断言**每一行恰好被访问一次、而且是按顺序**。这条检查针对的毛病**没有任何症状** ——
三十行的一页少一行，看上去和满页一模一样；分页边界上差一个，要么丢掉跨页那一行、要么两页都显示它，
**不去专门找那一发弹就永远发现不了**。所以查的不是"算式看着对"，是"从头翻到尾，一行不多一行不少"。
顺带还验了几个退化输入：窗口矮到一行都放不下（`perPage` 不能返回 0）、空书是"一页空页"而不是零页、
以及窗口缩小后从大窗口留下的页码会被夹回范围内。

```

  ap                       15
  heat                      6
  he                        5

[cannon_ap]
  M829-120mm APFSDS                    570mm  vvp_ywzj:m256_120mm_apfsds
    M829A1                             600mm

  ...

每个**装填**缩在它所属的那一行下面 —— 装填不是一发独立的弹，把它印成一行等于说 Abrams
带了五种弹，而它带的是一种弹的五个批次。

缩进那行还会印出**这个装填和槽位本身不一样的那些数**（`3OF82 Telnik` 那行的破片范围就是），
槽位本身已经有的数不重复印。这条是补一个**真实的盲区**：高爆弹的第二个装填穿深**一模一样**，
区别全在爆炸上，只看穿深的话"装填生效了"和"装填根本没生效"在输出里长得完全一样。

### 双路供弹：滚轮换链、F 换弹（两门 30mm）

两门 30mm 机炮（BTR-3 的 ZTM-1、M1296 的 XM813）是**双路供弹**，做成了**两条弹链、每条链里两发弹**：

| 操作 | 键 | 说明 |
|---|---|---|
| **换弹链** | **滚轮**（原版的武器切换） | 1 号链 ↔ 2 号链 |
| **换链里的弹** | **`F`**（原版的副武器/多武器切换键） | 钢针 ↔ 榴弹 |
| 选装填（**其它**载具） | 左 Alt | 见下一节 |

- 两条链装的是**同两发弹**，差别只有"刚切过来时手里是哪一发"：1 号链是钢针，2 号链是榴弹。
- 换弹和换链都会**重新装填一次**（基础模组自己的规则：退弹、给回你、新弹上膛），所以都不是白换。

> **为什么不是"装填"**：装填（左 Alt 那一套）换的是**同一门武器打出去的数**，弹丸和爆炸是武器
> 文件定的，装填只能把它们**去掉**、加不回来。而这两发弹的区别恰恰在**弹丸**上 —— 榴弹带着载具包
> 给的那个小爆炸，钢针没有爆炸。所以这一组不能是装填，必须是**两个真正的武器**放在一条链里。
>
> 代价写在前面：**一个组在游戏里没有名字**。按 F 时动作栏报的是**那一发的型号**
> （`MK258-30mm APFSDS` / `XM813 30mm HE`），不是"1 号链"—— 链的名字只活在本文档和
> 载具包的 `save_id` 里。**这两门炮的装填列表因此是空的**（左 Alt 对它们无效）。

包里的样子（`add_shells.ps1` 写的，见「载具包的改动」）：两条链是武器列表里的两个 `ids` 组 ——

```json
"weapons": [
    {"ids": ["vvp_ywzj:xm813_30mm_apfsds", "vvp_ywzj:xm813_30mm"], "save_id": "XM813_1"},
    {"ids": ["vvp_ywzj:xm813_30mm", "vvp_ywzj:xm813_30mm_apfsds"], "save_id": "XM813_2"},
    ...
]
```

> `save_id` 是**必须的**：写成裸数组（`["a", "b"]`）时基础模组把组存成固定的 `multi_weapons`，
> 两条链就会共用一份存档槽，你离开时在 1 号链、回来变成 2 号链。**`F` 这个键是基础模组自己的**
> （`multi_weapon_switch`，默认 `key.keyboard.f`），本模组没有碰它。

### 多弹药槽位：左 Alt 选弹（M829 系列 / 乌克兰 KE-W / 125mm 钢针 / 125mm 高爆弹）

> ⚠️ **选弹不等于装弹：按左键之后，炮要重新装填一次才换上那一发。** 装填期间炮打不响
> （基础模组自己就拦着"正在装填"时的射击），装填结束那一瞬间才会变成新弹，动作栏这时报
> `已装填：<弹名>`。**在此之前打出去的还是原来那一发** —— 这不是延迟，是"弹还没进膛"。
> 左键点下去时会立刻显示一行 `装填中：<弹名>`，免得几秒钟的沉默被当成"点了没反应"。
>
> 装填用的是**基础模组自己的装填**（时长就是武器文件里的 `reload.time`），所以有它的音效、
> 它的 HUD 显示。**弹匣不会被倒空** —— 只有装填本身的花费，也就是那几秒；顺带一提，装填总是
> 会把弹匣补满，所以不满的弹链会在这时补上（这本来就是"装填"在这个模组里的含义）。
> 这条规则**对所有有装填列表的载具一致**，实现只有一处（`RoundReload` + `AbstractVehicleWeaponMixin`）。

> ⚠️ **装填的效果只在"打中本模组管装甲的载具"时看得见。** 这是最初被误报成"切换弹种没有实际
> 效果"的原因：日志里连打了四十发，**一条 `hit on` 都没有** —— 全都打在地面或没配装甲的东西上。
> 而本模组**只在目标是配置过的载具时接管伤害**（`armorFor(vehicle) == null` 就直接返回 false），
> 对其它目标，穿深、弹种表、爆炸全由基础模组按**武器文件**决定，和装填无关 —— 于是两种弹当然
> 一模一样。要看到区别，**对着十四辆车里的任何一辆打**，命中那行会写：
>
> ```
> vvp_ywzj:stryker_m1296 hit on hull front: IMPACT fuze, plate 45.0mm, penetration 116.0mm, …
> vvp_ywzj:stryker_m1296 hit on hull front: IMPACT fuze, plate 45.0mm, penetration 6.0mm, …
> ```
>
> 为了让这个区别**不用打中也能看见**，开火那行现在把装填的**穿深和弹种**一起打出来：
> `fired with MK258-30mm APFSDS - 116.0mm, kinetic` / `fired with XM813 30mm HE - 6.0mm, he`。

**五个槽位**现在装得下一组弹：M1 系列的 M829 家族、乌克兰 M1A1 的 KE-W、T-90M 和 T-72B3M 的
125mm 钢针（各一个武器 id，同一组弹），以及两辆车共用的 **125mm 高爆弹**。
**槽位数量没有增加** —— 载具的武器列表里仍然只有一发钢针，按原版的切换键也只看到一发。区别在于：
**按左 Alt** 会打开一页和弹药合集同款的选弹界面，点其中一发行就换装：

> **两门 30mm 不在这五个里** —— 它们的第二轮是**另一门武器**，不是装填，见上一节。

```
        弹药选择 - M829-120mm APFSDS              弹药选择 - 3BM60-125mm APFSDS
   滚轮选择 · 左键装填并退出 · Esc 取消        滚轮选择 · 左键装填并退出 · Esc 取消
  弹药                        等效穿深        弹药                        等效穿深
▸ M829                            570mm      ▸ 3BM60                           700mm  ← 车实际带的那发
  M829A1                           600mm        3BM46                           600mm
  M829A2                           630mm        3BM42M                          520mm
  M829A3                           700mm        3BM42                           457mm
  M829A4                           780mm

              弹药选择 - 3OF26-125mm HE
   滚轮选择 · 左键装填并退出 · Esc 取消
  弹药                        等效穿深
▸ 3OF26-125mm HE                    60mm  ← 车实际带的那发
  3OF82 Telnik                      60mm  ← 弹一样，破片更重
```

> 三组的方向不一样，因为"默认"指的是**这辆车实际带的那发**：M829 那组从最弱的原装弹往上换，
> T-90M / T-72B3M 那组从**最强**的往下换，高爆弹那组则是**同一发弹的两种引信**（穿深一样，
> 只有爆炸不同）—— 这是第一组"换的不是批次、是另一种炮弹"的装填，也是唯一一组
> **只看穿深看不出区别**的，所以 `AmmoCompendium` 会把破片范围一起印出来。

- **滚轮移动标记，左键确认并退出**。标记打开时就停在**当前装填的那一发**上，所以"打开→直接左键"
  就是"不改"。左键点画面任何地方都一样，取的都是标记那一行。
- **标记同时跟着鼠标**：把鼠标移到某一行也会把标记移过去。但**只在鼠标真的动了的时候**才跟 ——
  否则每帧都按悬停位置重设，滚轮刚滚走就会被鼠标原地拽回来。
- 滚轮**到头就停**，不循环：列表整屏可见，滚过头应该就是到头，而不是跳回开头让人以为滚错了。
- **再次按左 Alt 或 Esc 取消**（进来的键就是出去的键）。
- 装填结果在**动作栏**确认一次（`已装填：M829A3`），屏幕已经关掉了，所以那是唯一的反馈。
- 标记除了颜色还有一个 `▸` 字符，只靠颜色区分对色觉不同的人等于没标。
- **序号 0 就是"载具包给这个槽位的那发弹"**，它的名字来自载具包、穿深来自配置，两者都没有副本。
  A1~A4 是**追加的装填选项**，写在配置的 `variants` 里。所以列表长度是 `1 + variants.Count`。

#### 为什么不做成四个槽位

基础模组里"一个槽位"就是载具武器列表里的一项，而那一项能打什么由它的武器文件决定 ——
**没有第二个弹药列表可以塞**。所以选择放在本模组这一侧：炮手选一发装填，装甲系统按那发的穿深结算。
这也正好是"同一门炮的几种弹"该有的样子：载具是**一种**弹（动能弹），有**几个批次**。

#### ⚠️ 「点了没反应」是怎么发生的（已修）

`OperatedRound.operatingRound()` 是"这个人现在操作的武器是哪一发弹"的唯一入口。这个入口最初
**顺手把结果过滤成了"只有多用途弹才算"**：

```java
return ammo != null && ammo.multiPurpose() ? ammo : null;   // ← 错在这里
```

引信功能时期这是对的 —— 只有多用途弹有引信可切。但左 Alt 装填选择用**同一发弹**去查的时候，
钢针不是多用途弹，于是查出来是 `null`，动作被丢掉。而且**拒绝路径也挂在这同一个过滤后面**
（"车上有没有本模组认识的弹"用的是同一个判定），所以连一行日志都没有 ——
表现就是"点左键确认，什么都没发生，日志里也什么都没有"。

现在：

- **入口只回答"这是不是本模组配置过的弹"**，不再回答"它支持什么"。支持什么是调用方的事：
  引信动作查 `multiPurpose()`，装填动作查 `selectable()`。**一发弹只支持其中一种，不是两种都支持** ——
  用一个"什么都会"的过滤器去选弹，必然让另一种按键彻底失效。
- **拒绝一律记日志**（每位玩家 5 秒一条），理由按动作分：「这发弹没有可切换的引信」/
  「这发弹没有再多的装填选项」/「他操作的武器本模组没有配置」。这样"按了没反应"永远有一条线可查。

> `GunnerCheck` 里加了两条断言把这件事钉住：**装填用的那发弹不是引信用的那发弹**
> （`selectable() && !multiPurpose()`），反过来也成立。哪天两者合成一发，断言会失败 ——
> 那时候才是可以简化查找逻辑的时候，而不是现在靠运气。

#### ⚠️ 「选择成功但炮弹效果没变」是怎么发生的（已修）

还是同一个形状的错，换了层楼。上面那处过滤在**查找入口**，这处在**炮弹认领状态的时候**
（`AmmoEntityStateMixin.ywzjarmor$adopt()`）。它当初是给引信写的，于是开头就是一句引信的门槛：

```java
if (ammo == null || !ammo.multiPurpose()) {
    return;                     // ← 错在这里，装填的赋值在它下面
}
...
ywzjarmor$load = ...;            // 钢针永远走不到这一行
```

钢针不是多用途弹，所以每次都在这里返回，`ywzjarmor$load` 永远是 0 —— 也就是"载具包给这个槽位
的那发弹"。于是：选择界面正常、滚轮正常、左键确认正常、服务端也真的存下了、日志也真的打了
`loaded M829A3 (700.0mm)`，**唯独炮弹打出去还是 570mm**。日志长这样：

```
17:14:13.157 Lang269061 loaded M829A4 (780.0mm)
17:14:20.621 vvp_ywzj:m1a1 hit on hull upper front: IMPACT fuze, plate 800.0mm,
            penetration 570.0mm, residual -230.0mm, damage 0.0
```

选择到了服务端（有 `loaded` 行），但命中仍然报 570 ——这两行之间唯一的距离就是这段提前返回。

现在 `ywzjarmor$adopt()` 的写法是：**先读装填，再问引信**。

```java
if (ammo == null) return;                    // 本模组不认识这发弹，原样不动
ywzjarmor$load = clamped(setting.variant);    // ← 装填在任何能力判断之前就落地
if (!ammo.multiPurpose()) { ...; return; }   // 才轮到引信
```

- 顺序本身就是结论，所以注释里写死了**为什么**是这个顺序，而不只是"这里在做什么"。
- 没引信但有装填的那一发（钢针）**也记一行日志**：`fired with M829A3` 或
  `fired with M829 - nothing was ever selected for <uuid>`。前者说明装填到位，后者说明设置没送达到 ——
  在这行日志之前，"选好了"和"根本没收到"在日志里长得一模一样。
- 机枪那种没有装填、也没有引信的弹**不记日志**，否则每梭子都会刷屏。
- `ArmorSystem.modelFor()` 也跟着补了一句 `.variant(loadOf(shell))`：爆炸伤害那条支路原本只解析引信、
  不解析装填，同一发弹的穿深和爆炸会按两个不同的模型算。

> 教训合并成一句：**为一种能力写的门槛，会静默挡住后来增加的能力。** 已经出现两次了
> （`OperatedRound` 一次、`AmmoEntityStateMixin` 一次），两次的表现都是"功能看起来全对、
> 就是没效果"，两次的原因都是提前返回写在赋值前面。所以凡是写出"能力判断 → 提前返回"的地方，
> 都要回头看一遍**返回之前该做的事做完了没有**；做没做完这件事，最好由日志而不是由玩家来回答。

#### 装填是炮手的设置，不是炮弹的

和引信一样按玩家存在服务端（`GunnerSettings`），开炮时**冻结到弹丸上**
（`ShellState.ywzjarmor$load()`）—— 打出去之后再换弹，不该改变已经在空中的那一发。

> **索引是每个玩家一个数**，不是每个槽位一个。这够用，因为游戏里只有一个槽位提供选择；
> 它会按**当前操作的槽位**的列表长度钳位，所以万一将来出现第二个，两边也只会共用这一个选择，
> 而不会有人越界读到数组外面去。

### 液气悬挂（`↑` `↓` 调车高、`Alt+W` / `Alt+S` 调俯仰、K2 / 10 式的 `←` / `→` 调左右侧倾）

**基础模组本来就有整套每轮弹簧悬挂，而且轮式车全都在用。** 每个轮子是一个
`ywzj_vehicle:suspension` 部件，带自己的刚度、阻尼和静止长度；`PhysicsEngine.motionBySuspension()`
每 tick 跑 8 子步 × 16 迭代的求解器，解 **竖直 + 俯仰 + 侧倾**三个自由度，然后把结果直接写回实体
（位置、`xRot`、`zRot`）。所以这里要做的**不是造一套悬挂，而是给已有的那套一个可控的设定值**。

那个设定值就是**静止长度**。弹簧的力是 `刚度 × 压缩量`，而压缩量 = `静止长度 − 触地长度` ——
所以把静止长度拉长多少，车体就抬高多少；把前轮拉长、后轮缩短，车就低头。

#### 哪九辆车有，以及为什么是这九辆

名单按**"现实里真有液气悬挂"**挑，不是按"模型里有弹簧"：

| 车 | 依据 |
|---|---|
| **BMP-3**、**BRM-3K**、**9K123「菊花」** | 同一个底盘的三辆车。BMP-3 的悬挂就是**车高由驾驶员选**的液气悬挂，是这个包里唯一有据可查的"车组可操作"悬挂 |
| **挑战者 2** | Horstman Hydrostrut 液气悬挂，Horstman 自己也做配套的车高控制系统 |
| **美洲狮** | 液气悬挂 |
| **K2 黑豹**（`armor_pioneer:k2`） | 每根负重轮一个**内臂式液气悬挂**，车组可选车高、可让车体前倾/后坐，也能左右两侧单独升降。它是九辆里**同时**有装甲条目的两辆之一 |
| **10 式**（`armor_pioneer:type10`） | 液气悬挂 + 主动姿态控制，JGSDF 公开展示车体下蹲和前后俯仰。v63 起它也开左右侧倾，范围和 K2 完全一样（±4°）；另一辆同时有装甲条目的 |
| **M1296「龙骑兵」** | 轮式那一辆，八轮八簧，v38 起就有 |

> ⚠️ **T-64、T-72B3M、三辆 T-90M、四辆 M1 刻意不在名单里。** 0.6.1 的包给它们的模型也加了悬挂部件
> （每辆 10~14 个），所以给它们配上块，按键真的会答应、车体真的会动 —— 但**这九辆在现实里全是扭杆悬挂**。
> "模型上有弹簧"和"这辆车有车高调节"不是同一句话，配上就是凭空发明了一个功能，而不是还原一个功能。
> 装甲先锋的 **VT-5、VT-4** 同样不在名单里：它们也是扭杆悬挂，模型里有十二个弹簧不等于有车高控制。
> **K2 和 10 式是例外** —— 其他载具包的载具这次没有动。

**这八辆履带车（加上轮式那辆）里，只有 K2 和 10 式在本模组的装甲表里有条目。** 其余六辆没有装甲条目，
所以 `suspension` 从 `VehicleArmor` 里搬了出来，变成配置根下自己的一张表 ——
「有没有可调悬挂」和「装甲多厚」是两件不一样的事，硬要挂在装甲块上，等于为了让 BMP-3 能升降车体，
先得告诉本模组"BMP-3 的炮塔正面是 480mm"，而这个假数字会被后面每一张装甲表照抄一遍。

> ⚠️ **0.6.0 里有"两个"静止长度，名字最像的那个恰恰是没用的那个。** 一个轮子不是一个点，是一小块
> **接触面**：`buildSupportOffsets` 会把支撑点铺在轮子的方块上（铺法按尺寸定，本模组的车都是单点），
> `simulate` 为每个支撑点按 **`supportRestLengths[i]`** 造一个 `SupportContact`，而
> `PhysicsEngine.motionBySuspension` 读的就是这串 contact —— **只写 `restLength` 字段的话，动到的
> 是压缩量夹取范围和轮子的显示偏移，弹簧本体一动不动：按键有回应、轮子微微动、车身不动。**
> 字段是那个数组的**平均值**，本模组两个一起写（同一个偏置加到每个支撑点，平均值自然同增，字段就
> 按 `原值 + 偏置` 写，省得两处各自取平均后对不上最后几位）。两个基准值是**同时**记下来的。

- **车高按 `↑` / `↓`**，**一个键一个方向**，档位按每辆车的行程分（步进 0.05 格）：
  - **M1296（轮式）**：静止高度到 **+0.15 格**，4 档。**只有升高，没有降低** —— 它的碰撞盒底边
    和轮子底边一样高，静止时离地只有 1 厘米，**没有往下走的余量**（见下）。
  - **八辆履带车**：**−0.20 到 +0.20 格**，9 档，静止档在正中间。往下就是"趴下来"，
    车底离地 0.443~0.756 格（10 式最矮，0.443；K2 是 0.619），降 0.20 仍有余量（见下）。
- **俯仰按 `Alt+W`（低头）/ `Alt+S`（抬头）**：六辆 vvp 履带车是 −2° 到 +2° 分 9 档；
  **K2 和 10 式是 −5° 到 +5° 分 21 档**（`max_pitch = 5.0`）。W 在前、S 在后，低头就是
  **把车头按下去**，所以 W 是低头、S 是抬头。**低头能压低炮口**（炮塔的俯仰是相对车体的，
  车体低 5°，可用俯角就多 5°），抬头能提高仰角。
- **K2 和 10 式的侧倾按 `←`（左倾）/ `→`（右倾）**：−4° 到 +4° 分 17 档（`max_roll = 4.0`，
  步进 0.5°）。按 `←` 左半边下沉、右半边抬起，按 `→` 反过来 —— 也就是**单独升降左右两侧的
  悬挂**：绕横向平衡点转动，两侧的静止长度一增一减，所以车高不变。只有这两辆有这个轴；
  其他车 `max_roll = 0`，`←` / `→` 仍然是炮手的引信键（见下）。
- **方向键就是方向**：到头即停，**不会绕回另一端**。按着"升"却掉到最低位是方向键唯一不能犯的错，
  所以"往哪走"跟着消息发给服务端，由服务端算出落在哪一档（`SuspensionActionMessage`）。
- **三个轴独立（K2、10 式）**：调车高不会动俯仰或侧倾，反之亦然。档位**不存档**，重登回水平位。
- **不是瞬间跳档，是液压作动。** 按键只改目标档位；每个轮子的静止长度按 `actuationRate`
  （默认 **0.0125 格/tick，即 0.25 格/秒**）逐 tick 追过去 —— 0.20 格满行程约 16 tick，
  一次 0.5° 俯仰约 2 tick。三个轴共用一个速率，因为三者都是同一份静止长度偏置。
  `actuationRate` 在 `suspensions` 条目里；**0 或负值读作瞬时**，不会把车冻住。
  每个轮子还会把目标夹到 `max_droop − 0.01` 以内，所以手改配置把行程调超了，
  也只是到不了目标，不会让轮子悬空。
- **履带也跟着一起动（K2 起）。** 0.6.2 的 `TrackUnit` 会按悬挂的 `trackFloatingPoint`
  生成一条浮动路径；K2 现在用 link model 画履带，所以升降、俯仰、单轮压缩时，链节会跟着
  轮子一起起伏。旧的显示履带动画没有这条信息，只会停在固定环上。
- **装甲跟着车身走。** 这不是额外做的：碰撞盒每 tick 由实体位置和朝重重算
  （`VehicleCubeOBB.update`），渲染也把整个模型按同一套变换摆（`VehicleRender`），而
  `ArmorSystem` 的命中位置又是拿 `mainCubeOBB` 归一化的。所以**低头时首上会更正对来弹、抬起时
  车底会露出来、打中的面和角度全都跟着变**，一行新代码都不用写。
- **只有在配置的 `suspensions` 表里的车才有这组键。** 不在表里的车一切照旧，轮子还是按包里的弹簧走。

> **为什么是这几个键，以及它们跟谁共用。** 方向键 `↑ ↓` 对地面载具是空的：基础模组把它们读成
> `functionalUp/Down`，但只有**旋翼机和固定翼**会拿去用（油门/总距），**地面车一点反应都没有**。
> 同一个键还挂在 JEI 的翻页、卓越前线的灵敏度、装甲扫描仪的翻页上，但它们各自有前提
> ——**装甲扫描仪拿在手里时，方向键归扫描仪**，本模组这时不动车（不然一边翻装甲表一边上下颠车）。
> 俯仰那一对不受这个限制：扫描仪不读 W / S。
>
> **`←` / `→` 在 K2 / 10 式驾驶位是侧倾，在别处仍然是引信。** 左右方向键本来就是炮手的换引信 /
> 调延时键，基础模组也读它们（`functionalLeft/Right`）；本模组按"这辆车有没有侧倾轴 **且** 按的人
> 是不是驾驶员"分流，两者都成立才发侧倾消息 —— 所以 K2 / 10 式的炮手照样能换引信，其他车也照旧。
>
> 俯仰是**组合键**，因为 W 和 S 本身是基础模组的**油门**（前进 / 倒车），不能独占 —— 按住了是
> "一边前进一边压车头"。**`Alt` 单独按仍然是"选择装填"**，只是触发点从"按下"变成了"松开"：
> 按下的那一刻就弹界面的话，界面一开本模组的按键处理整个停摆，紧跟其后的 W 会被吞掉，
> **俯仰组合键会在恰恰有装填可选的那些车上变成死的**。所以 `Alt` 按住后按别的东西就不再开界面。
>
> **原来那对 M / P 撤了**：`P` 是**原版"社交界面"的默认键**（`options.txt` 里的
> `key.socialInteractions`），按一次弹一个界面；`M` 则是按下去毫无提示地什么都不做的那个。

> **每按一次键，日志里有两三行**，是给"键有反应但车不动"准备的：
>
> ```
> [Vehicle Armor] suspension mixin running on vvp_ywzj:stryker_m1296: 8 suspension unit(s), suspension block found
> [Vehicle Armor] suspension on vvp_ywzj:stryker_m1296: 0.05 blocks / 0.0 degrees,
>                 8 of 8 wheels on the ground, bias spread 0.050 to 0.050, hull y 63.42
> [Vehicle Armor]   suspension_wheelL0Turn rest length 0.0617 -> 0.1117 (spring 0.0617 -> 0.1117),
>                  compression 0.0512 within [-0.10, 0.40], grounded true,
>                  1 support point(s), first at compression 0.0512 within [-0.10, 0.40]
> ```
>
> 第一行是**这个 mixin 到底有没有在跑**（只写一次）；第二行给出姿态、**八个轮子里有几个真的
> 踩在地上**、**偏置在轮子之间的分布**（这就是俯仰梯度在真实模型上到底存不存在）和**当时车体的 Y**；
> 第三行是这个轮子被写进去的长度和求解器真正读的那几个数。
> 车体的 Y 是**按下的瞬间**读的，也就是"上一个姿态稳定后的高度" —— 连着按两次而 Y 不动，
> 说明写进去的数根本没到求解器，那是跟"车动了但模型没跟上"完全不同的另一种毛病。
> **每个姿态只写一次**，不会刷屏。

> ⚠️ **车为什么不水平（2026-10-09 修）。** 症状是**所有**有悬挂的车都车头朝下趴着、车身还矮一截，
> 而按键有反应、动作栏也在报数。原因：v43 → v44 把 `suspension` 从装甲块搬到
> `Profile.suspensions` 时，`AbstractVehicleSuspensionMixin` 里那行查找**没跟着改** ——
> 它还在读那个留作兼容的旧字段，而那个字段**永远是 null**。
>
> 于是每辆车的 `settings` 都是 null，姿态落到 `Pose.NONE`，**而那个常量读作 `(0, 0)`，
> 三个轴上都是最低档**（`height()` 是从 `-max_drop` 往上数的），也就是**低 0.2 格 + 低头 2°**。
> 轮子那侧是好的（另一个 mixin 改了），所以车真的在动、动作栏真的在报 ——
> **但报的是"这次按键要求的位置"，不是"车现在的位置"**，所以按多少次都回不到水平。
>
> 三件事值得记下来：
> 1. **`Pose.LEVEL` 这个名字本身就是错的**，它读起来就像"水平位"，所以从来没人问它到底是什么。
>    现在改叫 `Pose.NONE`，注释里写死"这不是水平位、也不是静止位"。
> 2. **`@Deprecated` 挡不住这类错误**：`javac` 只给一条提示，游戏运行时一句话都不说。
>    `MixinCheck` 因此多了一张 `MOVED_FIELDS` 表，专门查"还有没有人在读已经搬走的字段"。
>    这张表要**手动加** —— 没有任何东西能推导出"这个字段是搬走的"，`@Deprecated` 也没这么说。
> 3. **搬家式迁移和加值/删值不是一回事。** 加值、删值那两种，旧的键留在文件里也没人读；
>    搬走的这种，旧字段**还在、还能读、永远是 null**，编译器不拦，运行时不报。

> ⚠️ **车高、俯仰和侧倾共用一份行程预算，几个数不能各调各的。** 弹簧能拉长的余量 = 包的
> `max_droop` 减去静止时已经吃掉的那 1 厘米；而最吃行程的是**同一个轮子**：它同时拿到
> "整车升高"、"低头时前端的那一份"和"侧倾时外侧的那一份"。M1296 出厂的两个数加起来 0.23，
> 卡在 0.25 里 —— **第一版写的是 0.20 + 2.5°，加起来 0.30，被工具直接判不合格**（车头轮子会
> 离地，而游戏里那只会表现成"这车开起来有点怪"）。六辆 vvp 履带车里最长的是挑战者 2：
> 0.20 + tan(2°)×2.531 = 0.288，卡在 0.31 里。**K2 是 ±5° 俯仰 + ±4° 侧倾**，最远纵轮 2.859、
> 最远横轮 1.684：0.20 + tan(5°)×2.859 + tan(4°)×1.684 = **0.568**，所以包里把
> `max_droop/max_extension` 抬到 **0.60**，预算 0.59，留 0.022 余量。**10 式从 v63 起是同一套
> ±5° 俯仰 + ±4° 侧倾**，最远纵轮 2.781、最远横轮 1.544：0.20 + tan(5°)×2.781 + tan(4°)×1.544
> = **0.551**，它的包也已经是 0.60，留 0.039。
> `SuspensionCheck` 会把这几项从载具包里重新推一遍。

> ⚠️ **`max_drop` 别乱填，而它管的是另一件事。** 它不是 `max_rise` 的负数：**往上走**受弹簧行程
> 限制，**往下走**受车体离地间隙限制 —— 压缩弹簧做得到，把车体按进地面就不行。
> M1296 的车体盒底边和轮子底边一样高，所以它的 `max_drop` 是 **0**；八辆履带车的车体盒在
> 负重轮上方 **0.443~0.756 格**（10 式最矮，**0.443**；K2 是 **0.619**），降 0.20 仍有余量。换一辆车要往下调之前，先量车底离地多少 ——
> `SuspensionCheck` 会从结构模型里把这两个数都量出来（结构模型里 `main_structure` 的最低点到
> 所有悬挂部件最低点的高度差）。

> ⚠️ **履带车的行程要打补丁才够用，这是 `add_suspension.ps1` 存在的唯一原因。**
> 一个轮子的探针能伸到挂点下方多远，算出来**恰好就是 `max_droop`**
> （`getMinCompression` = `max(-max_extension, 静止长度 − max_droop)`，而探针远端是
> `静止长度 − minCompression`），所以 `max_droop` 就是全部行程预算。**而 vvp 包里这 28 辆履带车
> 大多写成 0.1（K2 出厂是 0.123）**（轮式 M1296 是 0.26），扣掉那 1 厘米只剩 0.09~0.11 格 ——
> 在三格高的坦克上什么都看不出来。所以 vvp 六辆抬到 **0.32**，K2 和 10 式因为 ±5° 俯仰 + ±4° 侧倾
> 抬到 **0.60**，`max_extension` 与 `max_droop` 同步（vvp 六辆走 `add_suspension.ps1`，
> K2 / 10 式直接改 `armor_pioneer` 包里的车辆 JSON）：
> 这样探针远端就是 `max_droop` 本身，而不是 `静止长度 + max_extension` ——
> **静止长度是初始化时按车重重新解出来的**（`calibrateRestLengths`），脚本和工具都读不到，
> 两个数一起写才能让"行程 = max_droop"成为可以推导的事实，而不是碰运气。
> M1296 的 `max_droop` **没动**（0.26 本来就是履带车的两倍多，也已经出货了），
> 只把它的 `max_extension` 从 0.22 提到 0.26 —— 补上的是这个保证，不是行程。

- **状态不存档**，和涉水套件、一次性爆反同一个取舍。
- **只有驾驶员能按**：车高、俯仰和侧倾都是驾驶操作，座位的判定在服务端（见「乘员分工」）。
- **服务端没装本模组时**，按键会在 1.5 秒后提示"服务器没有装" —— 和 K 键同一条链路。

### 乘员分工（谁在干什么）

座位的职责不是在本模组里另立一张表，而是从**基础模组已有的座位**和**炮的口径**推出来的：

| 岗位 | 怎么认 | 能做什么 |
|---|---|---|
| **驾驶员** | 座位 0，也就是基础模组的 control unit 操作者 | 开车；**`↑` / `↓` 调车高，`Alt+W` / `Alt+S` 调俯仰，K2 / 10 式的 `←` / `→` 调侧倾，`K` 收放涉水套件** |
| **炮手** | 车上**口径最大的那门炮**的操作者 | 瞄准、开火；左方向键换引信、右方向键调延时、左 Alt 选装填 |
| **车长** | **口径第二大的武器站**的操作者（通常是 12.7mm 遥控武器站） | 操作自己的武器站；**没有额外的接管键**（基础模组操控） |
| **乘员** | 其他所有座位（包括装填手那挺 7.62mm） | 坐车；开火/换弹仍按基础模组自己的规则 |

- **按口径而不是按部件名**：装填手那挺 M240 和车长的 M2HB 都是"不是主炮的武器站"，只有口径大的那个是车长。
  这样换包、改部件名都不会把角色悄悄认错 —— 认错的后果是**车长键发给了错误的人**，而画面上看不出来。
- **进座/换座时动作栏会显示岗位**。没有第二个武器站的车（比如 BTR-3、M1296 的 30mm）
  **没有车长这个岗位**；这个岗位只用于显示和乘员伤亡，不再有任何接管键。
- **所有判定都在服务端**：客户端只发送"我按了哪个键"，服务器用自己的座位表回答"你是不是这个岗位"。
- **装甲先锋七辆车的主炮炮塔是座位 0**：所以**炮手同时也是驾驶员**，`CrewRoles` 让驾驶员优先，
  HUD 把这一席显示为**驾驶员**；主炮的引信/装填键照常可用。车长仍是遥控武器站（座位 1），
  原 `driver_seat_2`（座位 2）是乘客座。详见下面的「座位顺序」。
- **装甲先锋的七辆车现在采用默认包 99A 的座位顺序：主炮炮塔排在第一位。** 基础模组按
  `parts` 数组里**座位部件的出现顺序**编号，并把 control unit 交给座位 0。默认包的 99A
  把 `turret` 放在第一位，所以**炮塔里的那名乘员既开车又打主炮** —— 一个乘员控制整车，
  车体里的 `seat` 只是乘客座。装甲先锋现在也改成
  `turret → commander_machine_gun → driver_seat_2`（豹2A4 的 `loader_seat` 排第四）：
  **座位 0 = 炮塔（主炮 + 驾驶），1 = 车长（遥控武器站），2 = 乘客（原 `driver_seat_2`），
  3 = 装填手（仅豹2A4）**。
  - **这一席同时是驾驶员和炮手。** `↑` / `↓`、`Alt+W` / `Alt+S`、`←` / `→`、`K` 这些
    **驾驶员专属**键对他可用，主炮的引信/装填键也照常可用；`CrewRoles` 按「驾驶员优先」
    把 HUD 这一席显示为**驾驶员**。
  - **部件状态按 id 存档**，包里的引用也全是 id，所以只改顺序不会把血量/弹药/装填错位；
    只有座位索引是运行时的。已经开着的车请**下车再上车**一次（或重新放置）。
  - `CrewOrderCheck`（`verify.ps1` 里的一个工具）直接读包里**七辆**装甲先锋车的载具 json，
    要求座位顺序都是 `turret, commander_machine_gun, driver_seat_2`（豹2A4 多一个
    `loader_seat`）；`LoaderCheck` 也钉住豹2A4 的第四个座位是装填手。这一项错了游戏里
    不会报错，只会表现成“方向盘在错误的人手里”。
  - 备份：`armor_pioneer-1.1.0-0.6.2.zip.before_99a_control.bak`，以及每个载具 json 旁的
    `*.json.before_99a_control.bak`。
  - **早先 2026-10-26 的那次改动（`driver_seat_2` 移到第一位）已被这次改回 99A 顺序取代**；
    下面的历史记录仍然保留，阅读时以本节为准。

#### 操控：完全使用基础模组

**本模组不改基础模组的载具操控。** 座位 0 的乘员就是 `controlUnit` 操作者（开车）；每个座位操作自己的武器；**基础模组的滚轮**切换当前座位自己武器的弹种/武器槽；想用别的武器就按基础模组的换座键过去。

- **开车**：座位 0 的乘员用基础模组的 WASD/空格驾驶。装甲先锋七辆车按 99A 座位顺序，座位 0 是主炮炮塔，所以**炮塔乘员开车 + 打主炮**；车长是遥控武器站（座位 1），原 `driver_seat_2`（座位 2）是乘客；豹2A4 的装填手在座位 3。
- **武器**：每个座位只操作自己的武器站；车长、炮手、装填手各自开火。基础模组的滚轮/换武器键按当前座位自己的武器工作，和默认包一样。
- **已移除**：本模组以前的 `M` 指示目标、左 Ctrl 车长全权、左 Shift 驾驶接管、T/F 全权换武器都不再发送；服务端也不再执行。`CrewActionMessage`（id 6）仍然注册，但收到旧客户端发来的这类旧报文时直接丢弃，避免旧客户端/新服务端混用时出问题。
- **保留的附加功能**（不改变基础操控）：乘员岗位/装填手/伤亡、可调悬挂、涉水套件、混动、夜视、舱盖潜望镜、装甲探测仪等；这些是按各自座位的键，和驾驶/开火权分开。

#### 乘员伤亡

- **击穿后会伤到命中舱室里的人**：打中炮塔就伤炮塔里的人（炮手、车长），打车体就伤车体里的人（驾驶员）。
  如果命中的部件正好有主人（比如打中遥控武器站），优先伤那个人。
- **伤害按穿深和弹的威力缩放，并按口径分档**：125mm 钢针/高爆弹打进舱室是重伤，
  30mm 穿甲弹打穿薄顶只是轻伤，步枪弹基本不算。
- **重伤（主炮口径、伤害达到门槛）会让该乘员失能 7~10 秒**：
  - 炮手不能开火（客户端拦一次，服务端再拦一次；改过的客户端也打不出去）；
  - 车长不能操作自己的武器站（遥控武器站的扳机也会被拒绝）；
  - 驾驶员的方向盘被服务端锁住：`controlUnit` 的操作者被暂时取下并清空输入，车会停下；
  - 所有岗位键（悬挂、涉水、引信、装填）在这段时间里都被拒绝并提示原因。
  - 失能结束自动恢复，驾驶员的操作者会被放回原位（前提是他仍在座位 0）。
- 伤害是**真实的玩家伤害**：血掉光就会死、会被弹出车外，岗位自然也没了。
- 离开载具（下车、死亡、车被摧毁）会清掉伤口，不会带回重生点。

> 技术上：`CrewFireMixin` 在服务端拦住失能操作者的开火。旧的 `CrewShotMixin` / `RotatableUnitClientMixin`
> 全权瞄准路径还在代码里，但没有任何客户端按键会创建状态，所以不会再改基础模组的瞄准。

### TACZ（枪械模组）的子弹也走这套装甲

装了 **TACZ（永恒枪械工坊：零）** 的话，它打出来的子弹和本模组自己的炮弹**走同一条结算路径** ——
同样是「查 mm 穿深 → 比装甲厚度 → 剩余穿深 × 倍率」，同样吃爆反、裙板、串联弹那几条规则。

> **接点比想象的好，一个 mixin 都没加。** TACZ 的子弹最后调的是 `Entity.hurt`
> （`EntityKineticBullet.tacAttackEntity` 里那句 `parts.hitPart().m_6469_(source, damage)`），
> 而 `AbstractVehicle.m_6469_` 会走到 `DamageSystem.hurt` —— **那正是本模组 `DamageSystemMixin`
> 已经插着的地方**。插桩点、取消逻辑、车辆被打爆的后续流程全是现成的。
> 命中点也是精确的：`onBulletTick` 里 `startVec = 子弹当前位置`、
> `endVec = startVec + 子弹当前速度`，所以事件触发时**子弹的 `position()` 就是射线起点**，
> 拿它跑本模组原来那条 `closestHitObbPosition` 就行。

**怎么认出这是 TACZ 的一发弹**：看**伤害类型**（`tacz:bullet` / `tacz:bullet_ignore_armor`），
而不是看实体类。伤害类型是原版的 `DamageSource` API，读它**一个 TACZ 类名都不用写** ——
没装 TACZ 时那两个 id 就是普通的不匹配。

#### ⚠️ 一次命中是**两次** hurt 调用，只能结算一次

`tacAttackEntity` 把一发弹的伤害拆成两半分别打：先是 `tacz:bullet`（普通部分），
再是 `tacz:bullet_ignore_armor`（穿甲部分），比例来自 TACZ 自己的 `extra_damage.armor_ignore`。
**两次是同一发弹打在同一块板上**，所以本模组只在**前一次**做结算，**后一次直接吞掉不结算**。
两半都结算的话同一块装甲会被推两遍，伤害翻倍 —— 和「带战斗部的爆炸」那次重复命中是同一类问题。

> TACZ 那个 `armor_ignore` 拆分本模组**不用**：一个弹种一个穿深数，这才是等效装甲该有的粒度。
> 那个字段说的是原版护甲点，不是毫米。

#### 穿深数值：查真实资料，不按 TACZ 的伤害调

**TACZ 自己没有任何穿深概念** —— 它只有 `damage`（一个手感数字）、`armor_ignore`（原版护甲点）
和一条随距离衰减的曲线。所以那张表就是全部建模工作，**每个数都是真实世界的 RHA 数据，不是从
TACZ 的 `damage` 换算来的**：

| 弹种 | mm | 说明 |
|---|---|---|
| `22wmr` 2、`9mm` 3、`45acp` 3、`357mag` 4、`45_70` 4、`50ae` 4、`500mag` 5、`762x25` 5 | 2–5 | 手枪/转轮口径。打钢板是"打个坑"，不是"打个洞" |
| `46x30` 5、`57x28` 7 | 5–7 | 个人防卫武器弹。设计目标是打**防弹衣**，不是打钢 |
| `762x39` 10、`545x39` 10、`58x42` 10、`556x45` 12、`68x51fury` 14、`300blk` 9 | 9–14 | 中间威力步枪弹，**整件事的分界线**。`300blk` 是估的：超音速装药在 7.62×39 之下，亚音速更低，这里取一个数 |
| `308` 8、`762x54` 10、`30_06` 13、`792x57` 13 | 8–13 | 全威力步枪弹（.308 的普通弹是这里面最弱的） |
| `338` 15、`50bmg` 20 | 15–20 | 狙击/反器材。`50bmg` 是唯一能从任何角度打穿轻装甲车的动能弹 |
| `12g` 5 | 5 | 独头弹：大而慢的一坨铅 |
| `40mm` 50、`rpg_rocket` 330 | 50 / 330 | **破甲弹**，`profile: "heat"`，所以按**破甲那张表**量 |

> ⚠️ **这套数会和 TACZ 自己的平衡打架，而且这里它赢。** TACZ 的 `damage` 是按"这把枪手感该多强"
> 调的，这里的 mm 是按"这发弹打钢板能打多深"给的。结果就是：
> **`7.62×39` 和 `5.56×45` 打不穿本模组任何一辆车的侧面**（全是 35mm 起），
> **连 MBT 的顶盖都打不穿**（90mm 起）—— 对装甲，它们什么也做不了，这是设计也是现实。
> 能威胁装甲车的只剩 `.50 BMG`（打轻装甲车的顶/底）、反器材枪，和 **RPG**（打 T-64 首上是 130mm
> 剩余，打侧面被裙板挡住）。
> **没配装甲的载具，以及这张表里没有的弹种，一概不受影响** —— 照旧吃 TACZ 原版伤害。

#### 弹药图鉴里能查到 TACZ 的弹

装了 TACZ 时，**弹药合集**（手持弹药合集右键）会在原来的三档 `Warhead × WeaponClass` 之外多出
一个 **「枪械 / Small arms」** 分类，把 `tacz_rounds` 里的 25 个弹种按**弹种本身**列出来：

- 步枪弹、手枪弹、霰弹按**穿甲弹**那一页，`40mm` 和 `rpg_rocket` 按**破甲弹**那一页 ——
  归档用的是弹种的 `profile`，所以破甲弹不会跑到动能弹的表上去量；
- 名字用弹种代号（`7.62×39 mm`、`12.7×99 mm (.50 BMG)`、`RPG-7 rocket`），不是 TACZ 的武器名 ——
  弹是弹，枪是枪；
- **没装 TACZ 就不显示这些行**。配置里的数值仍然在，只是书里不列一把找不到的枪的弹。

新增一个枪包的弹种时，只要在 `tacz_rounds` 里加一条，图鉴会自动多一行；名字没有对应代号的
会退回显示 id，而不是消失。

#### 爆炸弹：直击只结算一次

TACZ 的爆炸弹（`40mm`、`rpg_rocket`）在打中实体之后会**先**走一次 `Entity.hurt`（直击），
**再**生成它自己的 `ProjectileExplosion`。直击已经由本模组按装甲表结算过了，所以
**`TaczExplosions` 会在爆炸事件里把“被这发弹直接命中的那辆载具”从受影响列表里拿掉** ——
同一块装甲不会被推两遍，也不会在原版爆炸伤害里再吃一次无视装甲的伤害。

- 只拿掉**被直击的那一辆**：旁边没被击中的车仍然吃 TACZ 的溅射；
- 只对**本模组评过级、并且配了装甲**的弹种/载具生效；没配装甲的车和没评级的弹照旧走 TACZ 原版爆炸；
- 没有 mixin、没有 TACZ 类名：爆炸事件把**弹丸实体**作为直接来源，`TaczBridge` 从它读出弹种，
  其余全是配置里那张表。`TaczCheck` 会检查这个处理器还挂在 `ExplosionEvent.Detonate` 上。

#### 在载具里用 TACZ 枪

基础模组 0.6.2.1 自己带了 TACZ 支持：坐在座位上时，**座位部件的 `passenger_can_use_item` 决定
玩家能不能扣扳机**。装甲先锋的七辆车现在给**非武器座位**打开了这个开关：

| 载具 | 可开枪的座位 |
|---|---|
| VT-5 / VT-4 / K2 / 10 式 / 天马-20 / ZTZ-100 | `driver_seat_2`（座位 2，乘客） |
| 豹2A4 | `driver_seat_2`（座位 2，乘客）、`loader_seat`（装填手） |

**车长（`commander_machine_gun`）和主炮炮塔（`turret`，座位 0，同时是驾驶席）的座位故意不开**：
他们的左键是载具武器的扳机，同时放开会变成“一按左键，车顶机枪/主炮和手里的步枪各打一发”。
默认模组里也只有直升机的敞开侧座开了这个开关；装甲先锋这次是第一次给封闭车体开，标准是
“这个座位没有自己的武器”。

#### ⚠️ 软依赖：没装 TACZ 也必须能进游戏

TACZ 是**可选**依赖。**任何无条件加载的类只要引用了 `com.tacz.*`，没装 TACZ 的玩家就会在
加载那个类时崩**，而且崩在进主菜单之前，报的还是 `NoClassDefFoundError` —— 既看不出是本模组，
也看不出缺的是什么。

所以**整个模组只有 `TaczBridge.java` 一个文件允许出现 `com.tacz`**，而且它自己还分两层：
外层一个 TACZ 类名都不写（这样加载它永远安全），真正碰 TACZ 的两个方法在**嵌套类**里，
只有 `loaded()` 答"装了"之后才会被执行到。

> `TaczCheck` 会把 `build/classes` 下**每一个** `.class` 的常量池翻一遍，除 `TaczBridge`
> 和它的嵌套类以外，任何类出现 `com/tacz/` 就 FAIL 并点名。这条规则**不靠自觉** ——
> 这个错误在装了 TACZ 的机器上（也就是开发机的每一台）根本复现不出来。
> 它是**被弄红验证过的**：临时在一个普通类里写一句 `com.tacz.guns.GunMod.class`，工具立刻点名。

> **构建脚本也变了**：`build.ps1` / `verify.ps1` 现在会挑 `mods/` 里最新的 TACZ jar 上编译
> classpath（`TACZ_JAR` 可覆盖），并且**每次构建都把它打印出来**。挑的时候是**打开 jar 确认**
> 而不是看名字 —— `mods/` 里有两个 jar 带 `tacz` 前缀（枪械模组本身，和一个叫
> `tacz-mesh-loader` 的无关项目）。
> 顺带记一笔：那个 jar 的文件名以 `[永恒枪械工坊：零]` 开头，而 **`Test-Path` 会把 `[ ]` 当通配符**，
> 所以必须写 `-LiteralPath`，否则一个明明存在的文件会被判成不存在。

#### 还没做的

- **TACZ 的 `pierce`（一发穿多个）不参与**：本模组只结算一次命中，能穿几个还是 TACZ 说了算。
- **`68x51fury` 和 `300blk` 是估的**：6.8×51 太新、.300 BLK 的 RHA 数据很少，这里分别按同级弹推
  了 14mm 和 9mm。
- **第三方枪包的命名空间不一定叫 `tacz`**：目前只评了 TACZ 自带的 25 个弹种；枪包如果注册自己的
  命名空间（`某枪包:762x39`），那些弹仍然走 TACZ 原版伤害，直到把 id 加进 `tacz_rounds`。

### 原版武器（剑、斧、弓、三叉戟和小口径弹丸）也走这套装甲

**这是原版武器最后一条后门。** 以前一箭射在坦克上，基础模组的 `DamageSystem` 不知道装甲表，
直接把血扣掉；剑和斧在基础模组 `allowMeleeDamageVehicle=false`（默认值）时连碰都碰不到车。
现在这些命中由 `VanillaWeapon` 认出来，走和炮弹**同一条** `resolveHit`：查穿深 → 比装甲厚度
→ 剩余穿深 × 倍率，爆反、裙板、炮根、履带/轮胎区的规则一个不少。

**认的是伤害类型，不是物品或实体类**（所以没有一行 `SwordItem` / `Arrow.class` 判断）：

| 伤害类型 | 来源 |
|---|---|
| `minecraft:player_attack` | 玩家挥剑 / 斧 / 镐 / 锹 / 空手 |
| `minecraft:mob_attack` / `minecraft:mob_attack_no_aggro` | 生物近战 |
| `minecraft:arrow` | 弓、弩、发射器；光灵箭也是这个类型 |
| `minecraft:trident` | 投掷三叉戟（拿在手里砍是 `player_attack`） |
| `minecraft:fireball` / `minecraft:unattributed_fireball` | 烈焰人小火球、恶魂大火球、发射器火焰弹；**只算直击**，爆炸另由下一节处理 |
| `minecraft:wither_skull` | 凋灵之首 |
| `minecraft:mob_projectile` | 潜影贝子弹、羊驼口水 |
| `minecraft:thrown` | 雪球、鸡蛋、末影珍珠；原版伤害 0 → **0 穿深跳弹** |

**`thrown` 是专门堵洞的**：它原版伤害是 0，但基础模组会把低于阈值的伤害压成 **0.1**，于是以前
雪球 / 鸡蛋 / 末影珍珠可以无视装甲把坦克慢慢刮死。现在它走 0 穿深，直接被装甲表判成跳弹，
连 0.1 都不掉。

**穿深不是一张表，是一条换算**：`伤害点 × penetration_per_damage`，再夹到 `max_penetration`。
伤害点里已经包含物品攻击力、锋利、力量药水和暴击，所以原版每一把剑都不需要单独登记。出厂的
`0.4 mm/点` 下：钻石剑 7 点 → **2.8mm**，满蓄力弓约 6 点 → **2.4mm**，下界合金斧 10 点 →
**4.0mm**。**这连本配置里最薄的一块装甲（BTR-3 的 8mm 顶/底）都不到**，所以普通原版武器打这些车
就是跳弹 —— 这是设计，也是现实：一把剑不该打得穿坦克。**唯一能摸到那 8mm 的是力量 V + 暴击的
满蓄力弓**：约 23 点伤害换算 9.2mm，刚好击穿、掉不到 1 点血；再往上就打不动了。想把某把模组武器
单独评高，见下面的 `overrides`。

**近战的射线**：弹丸用自己的 `position()` 和 `deltaMovement()`；近战没有弹丸，用攻击者眼睛到
**车体主盒中心**的一条线，再往车体里多走 1 格。瞄车体中心而不是包围盒最近点，是因为包围盒里
可能全是空的，射线打不到任何 OBB，最后又会退回基础模组的无装甲伤害 —— 那正是这个类要堵的洞。

> **玩家近战仍受基础模组 `allowMeleeDamageVehicle` 开关控制**，默认 `false`。本模组**不覆盖**
> 这个开关：关着时剑根本到不了装甲表（和以前完全一样）；要在游戏里测试剑 / 斧，先把
> `config/ywzj_vehicle-common.toml` 里的 `allowMeleeDamageVehicle` 改成 `true`。箭、三叉戟和
> 生物近战不受这个开关影响。

**不覆盖的东西**：火焰、岩浆、闪电、药水。它们不是「武器打在一块板上」，继续走基础模组原来的
处理（见「还没覆盖的」）。**爆炸已经单独接管**，见下一节；**烟花火箭本来就不伤载具**（原版只伤
乘载它的玩家和附近的 `LivingEntity`）。**只对 `vehicles` 里配置过的载具生效** —— 没配装甲的车
照旧吃基础模组伤害，和 TACZ 那条回退是同一个原则。

#### 单独评级：`vanilla_weapons.overrides`

键是**近战物品 id**，或**弹丸的伤害类型 id**（`minecraft:arrow` / `minecraft:trident`，正好
也是物品 id）。每一项都是一个**完整的弹药条目**，`penetration` / `profile` / `multiplier` /
溅射都能用，而且**整条覆盖换算**（不是往上打补丁）：

```json
"vanilla_weapons": {
  "enabled": true,
  "penetration_per_damage": 0.4,
  "max_penetration": 10.0,
  "damage_multiplier": 0.5,
  "overrides": {
    "some_mod:greatsword": { "penetration": 25.0, "multiplier": 1.0 }
  }
}
```

#### 怎么在游戏里确认

拿弓射坦克：应该听见**跳弹音**、准星有命中提示、**车血不变**。把 `max_penetration` 临时调到
`200` 再射一发，应该能击穿并掉血 —— 这是最快的正反验证。日志**不会**为箭写 INFO 行（骷髅
每两秒一箭，会把坦克炮弹的日志淹掉）；近战和弹丸都只走声音和命中提示。

### 原版爆炸（TNT、苦力怕、末地水晶…）也走装甲表

**爆炸不是弹丸，所以它单独一组。** 原版 `Explosion` 对每个实体算一个伤害数字，然后调
`Entity.hurt`；这个数字已经包含距离和遮挡衰减，但和装甲完全没有关系。以前一块 TNT 放在坦克
旁边，扣的血和放在木箱旁边一样。现在三种原版爆炸伤害类型会被认出来：
`minecraft:explosion`、`minecraft:player_explosion`、`minecraft:bad_respawn_point`。

覆盖的爆炸：TNT / TNT 矿车、苦力怕（含高压）、末地水晶、床 / 重生锚、恶魂火球爆炸、充能凋灵
之首爆炸、凋灵生成爆炸。

**怎么算**：`爆炸伤害 × 0.5 = 等效穿深（mm）`，上限 80；然后走和炮弹同一条 `resolveHit`：
「爆心 → 车体主盒中心」的射线决定命中面，剩余穿深 × 被击穿那块板自己的倍率（除非
`damage_multiplier` 另写）。出厂值下的量级（理论最大、点对点无遮挡）：

| 爆炸 | 原版伤害 | 等效穿深 | 打 20mm 车顶 | 打 8mm 轻车顶 |
|---|---|---|---|---|
| TNT | 29 | 14.5mm | 跳弹 | 击穿，(14.5−8)×5 ≈ **33** |
| 苦力怕 | 22 | 11mm | 跳弹 | 击穿，≈ **15** |
| 高压苦力怕 / 末地水晶 | 43 | 21.5mm | 击穿，≈ **8** | 击穿，≈ **68** |
| 床 / 重生锚 | 36 | 18mm | 跳弹 | 击穿，≈ **50** |
| 恶魂火球爆炸 | 8 | 4mm | 跳弹 | 跳弹 |
| 凋灵生成 | 50 | 25mm | 击穿，≈ **25** | 击穿，≈ **85** |

> 这是**等效**模型：现实中的爆炸不是靠“穿深”杀人，但这样至少让装甲的厚度、倾角、爆反和
> 倍率表都参与进来，而不是让一块 TNT 对坦克和木箱一视同仁。

**只对配置过的载具生效**；没配装甲的车和以前一样。**飞机不覆盖**：蒙皮模型讲的是穿透，近失弹
本来就应该按基础模组的爆炸来算 —— 和带战斗部炮弹的规则一致。

**不覆盖基础模组自己的爆炸**：`ywzj_vehicle.explosion` 还是由原来那条分支处理（已评级的、
自带爆炸的炮弹会被顶掉；没评级的不动）。

**爆心从哪来**：`ExplosionMixin` 在 `Explosion.explode()` 的头尾压栈 / 弹栈爆心。伤害源本身
只带 TNT / 苦力怕实体，床和重生锚甚至没有直接实体；没有爆心就没有方向，也就没有命中面。
嵌套爆炸（连锁 TNT）用栈，内层不会偷外层的爆心。

**`damage_threshold` 的 0.1 刮伤不再适用**：爆炸伤害在 `DamageSystem` 的阈值判断之前就被接管了；
装甲表说挡得住就是 0，挡不住就是上面那张表。爆炸的**击退和方块破坏不受影响**，只是伤害改走装甲。

#### 单独评级：`vanilla_explosions.overrides`

键是**爆炸直接实体的类型 id**（`minecraft:tnt`、`minecraft:creeper`、`minecraft:end_crystal`、
`minecraft:fireball`、`minecraft:wither_skull`…），或者没有直接实体时的**伤害类型 id**
（`minecraft:bad_respawn_point`）。每一项都是完整弹药条目，整条覆盖换算：

```json
"vanilla_explosions": {
  "enabled": true,
  "penetration_per_damage": 0.5,
  "max_penetration": 80.0,
  "overrides": {
    "minecraft:tnt": { "penetration": 18.0 },
    "minecraft:end_crystal": { "penetration": 45.0, "multiplier": 3.0 }
  }
}
```

（`damage_multiplier` 默认不写 = 用被击中那块板自己的倍率。）

#### 怎么在游戏里确认

在轻装甲车（BTR-3、Sd.Kfz.251 之类）旁边点一块 TNT：按上表应该掉血。在主战坦克旁边点同样一块：
应该只有击退和爆炸音、**车血不变**。把 `max_penetration` 临时调到 `0` 应该让所有爆炸都变跳弹；
日志会为每次爆炸写一行 `... blast fuze, plate ...`。

### 碰撞伤害（撞墙、追尾、硬着陆）也走装甲表

**这是最直观的一条无装甲伤害。** 基础模组的 `PhysicsEngine.motionByImpact` 比较撞击前后速度，
损失超过 0.5 格/tick 就按 `0.5 × 吨位 × (Δv×20)² × 0.1` 扣血 —— 不管撞的是哪块板，正面和屁股
一样疼。现在伤害类型 `ywzj_vehicle:vehicle_collision` 由 `VehicleCollision` 接管，走和炮弹同一条
`resolveHit`：换算穿深 → 比装甲 → 剩余穿深 × 被击中那块板的倍率（爆反、裙板、炮根、履带区的规则
一个不少）。

**换算**：`原始碰撞伤害 × 0.1 = 等效穿深（mm）`，上限 500。40 吨坦克 36 km/h（200 伤害）→ **20mm**，
72 km/h（800）→ **80mm**：主战坦克 100mm 以上的侧面两种都挡得住，BTR-3 的 16mm 侧面挡不住，
轻车的 8mm 车顶高速一撞就穿。`damage_multiplier` 可以覆盖板自己的倍率。

**命中哪一面**：伤害源里**没有撞击位置**，所以方向是推出来的 —— 撞方块 / 地形时用
`deltaMovementO`（这一 tick 开始、碰撞解决之前的速度）；撞另一辆车时用两车连线的方向（直接实体
就是对方）。射线从那一侧外面射向车体主盒中心，所以车头撞墙按首上算、倒车追尾按尾板算、
硬着陆按底盘算。

**0 伤害也是跳弹**：`roundFor` 永远返回一发弹药（0 穿深），所以低于基础模组阈值的碰撞不会
再落回「压成 0.1 刮伤」那条路。

**乘员冲击**：撞击被装甲挡住也会晃一下。原始伤害从 20 起算，200 到顶：最多 **2 秒反胃 + 1 秒
缓慢**，给车上的乘客和驾驶员各挂一次，按强度缩放（`max_nausea_ticks` / `max_slowness_ticks`）。
刻意做得很轻 —— 击穿本身还会通过 `CrewState` 真的伤到乘员，震晕只是「挨了一下」的反馈。

**飞机不覆盖**，和爆炸一致；**只对 `vehicle_collisions.vehicles` 里的车生效**（出厂：装甲先锋七辆）。

#### 高速碾方块（方案 B）

现实里坦克能推开、碾碎矮墙和栅栏；基础模组默认不做这件事 —— 载具的 `physics_info.can_destroy_block`
出厂是 `false`，就算打开也只按「硬度 0–50 的 3×3」破坏，**完全不看车的重量和速度**。所以给装甲
先锋七辆车加了 `VehicleRamming`：它监听基础模组每 tick 已经算好的 `VehicleCollectCollisionEvent`
接触点，满足下面条件才动手：

- 载具在 `vehicle_ramming.vehicles` 名单里，且速度 ≥ `speed_threshold`（默认 0.15 格/tick，
  **约 10.8 km/h**）；
- **只处理迎头一侧**：方块相对车体中心、沿速度方向的投影 > 0，且接触面不是顶面 / 底面；
- **天然地面永不破坏**：石系、泥土系、沙、雪、冰、陶瓦这类「世界自己的地面」在硬度判断之前就被
  挡掉，跑多快都不会挖出坑。判定用原版自己的地形标签 —— `base_stone_overworld`（石头 / 花岗岩 /
  闪长岩 / 安山岩 / 凝灰岩 / 深板岩）、`base_stone_nether`（下界岩 / 玄武岩 / 黑石）、`dirt`、
  `sand`、`snow`、`ice`、`terracotta` —— 再加一批没有标签的自然方块（砂砾、黏土、末地石、
  砂岩、方解石、滴水石、紫水晶、幽匿、灵魂沙 / 灵魂土、菌岩……）。被模组正确打上这些标签的
  地形方块不用登记也会被保护。
- 硬度上限 = `base_hardness + hardness_per_speed × 速度 × √(吨位 / mass_reference_tons)`，
  默认 `0.4 + 10 × v × √(m/40)`：
  - 40 吨、0.5 格/tick（36 km/h）→ **5.4**：原木、木板、圆石；
  - 40 吨、1.0 格/tick（72 km/h）→ **10.4**：连石砖、砖块、铁块也能碾；
  - 2 吨的吉普、0.5 格/tick → **1.52**：只够压碎花草和玻璃。
- 跳过空气、跳过硬度 < 0 或 ≥ 50 的方块（黑曜石 50、基岩 −1 永远挡下）、跳过方块实体
  （箱子、熔炉、告示牌……`skip_block_entities`）；
- 每个接触点取水平 3×3，每 tick 最多破坏 `max_blocks_per_tick`（默认 12）块；
- **尊重基础模组自己的两个开关**：这辆车的 `can_destroy_block` 为 `false`，或者全局的
  `config/ywzj_vehicle-common.toml` 里 `canDestroyBlock = false`，就一块都不动。装甲先锋七辆
  出厂都是 `true`。

> **这是按材料分的规则，不是按「谁放的」分的。** Minecraft 不记录方块是谁放的，所以玩家用泥土
> 垒的墙和天然山坡一样受保护；反过来，圆石、石砖、木板、原木、羊毛、玻璃都没有自然标签，
> 仍然能撞碎 —— 坦克可以推平木屋和碎石墙，但不会啃山体。想让某辆车的碾压完全不看这条规则，
> 把 `vehicle_ramming.protect_natural_ground` 设成 `false`；模组地形没有被正确打标签时，把它的
> 方块 id 加进 `vehicle_ramming.natural_ground_blocks`（每项一个命名空间 id）。

#### 怎么在游戏里确认

- 开 VT-5 以 40 km/h 撞石墙或另一辆车：应该听见撞击、掉一点血；侧面薄的轻车被高速追尾应该
  明显更疼。把 `penetration_per_damage` 设成 `0`：撞什么都是跳弹，血不掉。
- 开 VT-5 以 72 km/h 冲进泥土山坡或天然石壁：**一块都不掉**，车被挡住、乘员震晕，但地面不会
  被挖开。同样的车冲进一座木板房或圆石墙：应该推平。
- 低于 10.8 km/h 只被挡住、不破坏方块；冲到黑曜石墙前应该完全停住。
- 想验证保护确实生效：把 `protect_natural_ground` 临时设成 `false`，同一面土坡应该又能被铲开。
- 车上的人撞完应该短暂反胃、走得慢一点（最多 2 秒 / 1 秒），而不是被直接打晕。

### 涉水套件（OPVT 通气管，按 K）

T-64 一下水就熄火。这**不是**本模组加的：基础模组的 `AbstractVehicle.tickPower()` 在车体中心检测到
**任意流体**、且 `canWade` 为假时，直接把 `power` 清零；`hasPower()` 随即为假，`TrackedVehicle.tickMove()`
就返回零位移 —— 坦克变成河底的一块死重，**开不出来**。

`canWade` 来自载具包的 `can_wade` 键：包里 BMP / BTR 那一批两栖车都写了 `true`，T-64 没写。
现实里 T-64 也确实不能浮渡 —— 它能做的是**潜渡**：车组把车体密封、竖起 OPVT 通气管，然后**沿着
河床开过去**。所以这里做的是一件可开关的装备，而不是给坦克加浮力：

- **按 K 展开 / 收起**。展开后泡在水里不熄火、能沿河床开；收起后立刻恢复成现在的行为。
- **管子会从炮塔顶升起来**（约 1.2 秒），收起时缩回炮塔内部；它挂在炮塔骨上，所以**跟着炮塔一起转**。
  这一半在载具包里，由 `add_snorkel.ps1` 补上（见下文「通气管的模型与动画」）。
- **深度上限 5 格**（真实 OPVT 的 5 米），是从**车底**量到水面的水深。超过上限 → 发动机进水熄火，
  和没展开一样。
- **到上限的 80% 会提醒一次。** 这是唯一能救命的提示：超过上限就开不动了，警告必须在还有余地的时候到，
  而不是等车已经沉到底。
- **展开期间乘员不淹死。** 车体是密封的，所以车上所有人获得水下呼吸 —— 否则开进河底就是玩家自己在
  掉血，这个机制根本没法用。HUD 上会多一个水下呼吸图标，那正好也是"密封生效了"的可见反馈。
- **只对水有效。** 岩浆照旧熄火 —— 通气管救不了岩浆。

> ⚠️ **超过深度上限会被困住。** 熄火之后 `TrackedVehicle` 零位移，车会留在河底：不损坏、不丢数据，
> 但**开不出来**。这是刻意的失败模式（真实的潜渡就是这样失败的），靠上面那条 80% 的警告给提前量。
> 觉得太狠就调大 `max_depth`，想整辆车关掉就删掉那个 `fording` 块。

- **状态不存档。** 套件标记挂在载具实体上，重开世界恢复成"收起" —— 和一次性爆反同一个取舍。
- **只有驾驶员能按。** 涉水是驾驶决定：它改变这辆车能过什么，做这个决定的人应该是握着方向的那个。
  服务端按座位判定；乘客按 K 会收到"只有驾驶员可以操作"的提示，而不是让车突然展开通气管。
- **没打补丁的载具包也能用**，只是看不见管子 —— 这时按 K 的回复后面会跟一句
  「（这辆车的模型里没有通气管部件，看不到变化）」，日志里那一行也会写 `snorkel part: NO`。
  不会出现"按了没反应、也不知道为什么"。

#### 通气管的模型与动画（`add_snorkel.ps1`）

模型那一半在载具包里，和工作区根目录那三个补丁脚本一样是**声明式补丁 + 读回校验**，
四者共用同一个 `.bak`。**跑之前先关游戏**（脚本会就地改写同一个 zip），从零开始的顺序是
`add_shells.ps1` → `add_snorkel.ps1` → `split_rear_armor.ps1` → `add_suspension.ps1`。

它做四件事，每一件都对应一个**静默失效**：

| 改动 | 不做会怎样 |
|---|---|
| 渲染模型里加一根 `snorkel` 骨（挂在炮塔骨 `cannon` 下，一个方块） | 部件切换了，但没有东西可以动 |
| 动画文件里加 `snorkel_switch`（位置关键帧，0 → 升高） | **烘焙器会把没被动画点名的骨并进父骨的静态网格** —— 骨在，但永远动不了 |
| 控制器里加 `switchable_animations` 和一条 graph 输入 | 部件切了也没有动画被播放 |
| 载具 json 末尾加一个 `ywzj_vehicle:switchable` 部件（**没有 `structure_bone`**） | 按键没人接收，套件的状态没有东西可以镜像 |
| 贴图集空着的角落画一小块管子材质 | 管子会升起来，但是**透明的** |

几个刻意的选择：

- **静止姿态 = 收起**：方块是照着"藏在炮塔和车体内部"的位置建的，展开是**向上平移**。
  这样即使动画因为任何原因没播（部件不在、控制器编译失败、动画文件丢了），最坏结果都是
  **看不见**，而不是"永远竖着"。反过来建（站着建模、往下藏）会让任何一种断链都留下一根
  永远收不回去的管子。
- **管子长度是从模型里量出来的**，不是写死的：脚本量出炮塔顶（y≈46.3）和车体底板（y≈9.9），
  长度取两者之差 —— 于是收起时它刚好整根藏住，升起后露出炮塔顶约 2 格。模型一变，
  脚本会**报错停下**而不是默默让管子戳出车底。
- **只加不改**：模型插一根骨、动画加一条、部件追加在 `parts` 末尾（同步消息里带的是部件下标）。
  控制器是最危险的一个 —— **控制器一旦编译不过，基础模组会吞掉异常，整辆 T-64 的动画全部消失**
  （炮塔不转、轮子不滚、后坐也没了）。所以它是插入而不是重写，而且脚本读回时会**逐个对比原有的
  `part_bindings` 和事件动画**，并检查 pose graph 里那四种节点（`bone_binding` / `track_animation` /
  `event_animation` / `additive`）都还在。
- **贴图是画在没人用的角落**：x ≥ 466 那条竖带没有任何 UV 用到（最远的右边缘是 465）。脚本在落笔前
  会确认那片像素要么是空的、要么正是它自己上次画的颜色 —— 所以重复运行安全，也**不可能**糊掉别人画的
  东西。实体模型不做 mipmap，所以紧贴透明区域不会有边缘渗色。

> 通气管这个部件**没有 `structure_bone`**，因此它**没有碰撞箱、不会被炮弹命中、不参与装甲结算** ——
> 这一点是刻意的（真被打掉一根通气管要改的东西太多），由 `FordingCheck` 断言。

#### 状态到底是哪一个（部件还是布尔）

套件"已展开"只有**一个**状态：本模组自己那个布尔（`FordingState`）。**部件是它的镜像，不是第二个
说法** —— 每 tick 把布尔推给部件，部件再让模型动起来（基础模组自己同步开关部件、并在状态翻转时播放
动画）。

方向是刻意选的：部件**会存进 NBT**，而布尔不会。如果反过来让部件当权威，同一个按键在打了补丁的包里
会跨存档保留、在没打补丁的包里不会 —— 同一件事在不同安装上有两种行为，而且是没人能一眼看出来的那种。
现在的做法是"重开世界一律收起"，和一次性爆反同一个取舍；每 tick 重新对齐那一次，正是为了把
"存档里那根还竖着的管子"按回去。

> 已知的小毛病：基础模组给**任何**开关部件都配了一声原版拉杆音效，所以按 K 会听见"咔哒"一声 ——
> 那是按钮的声音，不是通气管的声音。要改得动基础模组，先留着。

#### 为什么改的是 `canWade`，而不是那三处判断

基础模组问同一个问题问了**三次**：`tickPower` 一次、`TrackedVehicle` 和 `WheeledVehicle` 的
`tickMove` 各一次，读的都是 `canWade` 这个字段。逐个去改就是**三次漏掉一个的机会**，而漏掉哪一次都
不报错：要么发动机转着但车不动，要么车能开但发动机是死的。

所以本模组在**源头**回答它：每 tick 在 `tickPower` 开头，按套件状态重写这个字段。`tickPower` 在同一
tick 里跑在那三个读取点**之前**，一次写入三处生效。包里原本的值在第一次 tick 时记下来，收起或超限时
原样还回去 —— **包里 BMP / BTR 这些本来就写了两栖的车一点没变**。

> 这里刻意用 `@Inject` + 写字段，而不是 `@Redirect` 去重定向字段读取：**继承字段在子类字节码里的 owner
> 是子类**，所以照 `AbstractVehicle` 写的重定向能匹配上一处、在另外两处静默匹配不上 —— 正是上面说的
> "三次漏掉一个"。
>
> `FordingCheck` 能测的是**判断本身**（真值表、边界、每个 verdict 的文案键在不在两种语言里、
> mixin 有没有被列进 `mixins.json`）；**"注入有没有真的生效"只能靠游戏加载**：`mixins.json` 是
> `required: true` + `defaultRequire: 1`，注入对不上会在加载期直接崩并指出是哪个 mixin，
> 而不是静默失效。

### 装甲探测仪（手持工具）

新增物品 `ywzj_vehicle_armor:armor_scanner`，中文名「装甲探测仪」，图标是改装工具图标的**灰度版**（16×16，
由模组原贴图去色而来）。

**拿在主手**、准星对准载具时，准星旁会显示所指部位的**等效厚度和倍率**。不需要右键，握着就生效。

- 瞄线不是对实体的碰撞箱做的，而是对**伤害系统用的同一批 OBB** 做的 —— 所以它回答的是「沿这条
  线打过去会命中哪块板」，而不是「射线碰到了哪个方块」。
- 部位判定调用 `ArmorSystem.plateFor`，和伤害结算**共用同一份代码**，屏幕上的数字不可能和实战
  用的数字漂移。
- **一次只显示一套装甲表，用上下方向键切换。** 载具自带数值排在第 1 项，之后是 `overrides`
  里的每一套。下方灰色小字标明当前是哪一套、第几项、总数，以及切换方式：
  ```
  hull upper front  840mm  x45.0
  破甲弹   2/3   Up/Down
  ```
- **表名显示的是弹种，不是配置里的键名。** 一套装甲表由弹药的 `profile` 选中，而本模组自带的
  profile 就是按弹种命名的，所以底部读作 **穿甲弹 / 破甲弹 / 高爆弹**，而不是 `default` / `heat` /
  `he`。载具自带的那套没有 profile，它就是**不写 profile 的弹**（所有动能弹：钢针和机枪）所对照的
  那一套，所以也叫穿甲弹 —— 和 `AmmoCategory.derivedFrom` 给出同一个答案是同一个道理。
  名字走翻译键，客户端换语言会跟着变。
  > 配置文件里写了一个**不叫弹种名**的 profile（比如 `era`）时，底部就照原样显示那个名字。
  > 把弹种名安到一个不是弹种的表上，是**把猜测当事实印出来**，而玩家没有任何办法分辨这两者。
- 切换只是翻页，**不改动任何配置**；事件也没有取消，所以方向键原本的功能照常。
- 换一辆载具时会按新载具的表数量取模，不会越界。
- 探测距离 128 格。

获取方式：创造模式物品栏里和改装工具、修理工具同在 **ywzj_vehicle 的杂项页**
（`ywzj_vehicle:tab_misc`）；也可以用 `/give @s ywzj_vehicle_armor:armor_scanner`。
弹药合集也在同一页，`/give @s ywzj_vehicle_armor:ammo_compendium`。

#### 为什么放弃了「改装工具预览悬停」那一版

前一版是在改装工具的 3D 预览里用鼠标悬停显示。桩打得很深：要用反射读那个界面的私有视角状态、
照抄它的正交相机矩阵、求逆反推射线，最后还卡在 **ApricityUI 残留在 pose stack 上的变换**上 ——
读数会被推到界面外，像「没显示」一样。

换成手持工具后，渲染走的是**原版 HUD**（`RenderGuiEvent.Post`），不再依赖任何第三方 UI 框架的
渲染状态和私有字段，整条链路都是标准 Forge 的东西。所以这一版也**不再是无法验证的功能**了。

### 首上 / 首下

> **几辆车的首上/首下比例差很远，因为真车就是这样：**
>
> | | 首上（glacis） | 首下（lower plate） | `split` |
> |---|---|---|---|
> | T-64 | 上面 50% | 下面 50% | `0.0` |
> | T-90M 三兄弟 / T-72B3M | 上面 50% | 下面 50% | `0.0` |
> | M1A1 | 上面 **30%** | 下面 **70%** | `0.4` |
>
> Abrams 的首下之所以占大头：那辆车的复合装甲阵列装在**首下**，而首上只是一块倾角很大的
> 普通钢（也正是这个倾角给了它抗动能弹的能力）。倾斜很平的板在正面投影上占的高度本来就小。
>
> **模型帮不上忙**：碰撞盒固然是一个平盒子，但**视觉模型的前面也是近乎垂直的一整块**
> （把所有车体方块连同旋转一起投影，正面在 y 0.46~1.94 之间一整段 z ≈ 5.05，没有斜面可量）。
> 所以这个比例是在配置里写死的真车数值，不是从模型量出来的。
>
> **比例改过两次**（`0.0` → `0.6` → `0.4`），所以升级路径里有一条专门**改写这两个旧值**的迁移：
> 只在你文件里的值还正好等于旧默认值时才动，手改成第三个数就会保留。日志会写明
> `Abrams hull front split 0.6 -> 0.4 (glacis 20% -> 30% of the front face)`。

真实的 T-64 有倾斜的首上（glacis）和较低的首下，但**模组碰撞体是一整块平盒子**，没有斜面
几何可以识别，所以是按**命中高度**做虚拟切分。分界线由 `hull_front_split.split` 控制：
`+1` = 车体盒顶，`0` = 正中，`-1` = 底。

所有垂直/横向参考系都锚在 `mainCubeOBB`（`main_structure` 骨骼里最大的立方体）上 —— 它正好是
**纯车体**，不含炮塔，所以转炮塔不会让任何分界线漂移。
