# 适配一辆新载具

> 返回 [项目首页](../README.md) · [文档索引](README.md)

**适配载具不需要改代码，也不需要重新构建。** 载具表整张都在 `config/ywzj_vehicle_armor.json`
里，加一辆车就是往里加一段 `vehicles` 条目和几条 `ammo_penetration`。Java 里那三个
`addT64` / `addAbrams` / `addBtr3` 只负责把默认值**发出去**，不影响你能不能加车。

整个流程就是**一张表**：

```powershell
powershell -ExecutionPolicy Bypass -File add_vehicle.ps1            # 列出每个包里的车，哪几辆已配
powershell -ExecutionPolicy Bypass -File add_vehicle.ps1 panther form   # 出这张表（几何已填好）
powershell -ExecutionPolicy Bypass -File add_vehicle.ps1 panther        # 出粘贴用的 JSON
powershell -ExecutionPolicy Bypass -File add_vehicle.ps1 check      # 校验这套推导本身（遍历所有包）
```

`form` 打印的是一份 Markdown 工单，可以直接存成文件、贴进 issue 或笔记。它的结构是固定的：

| 节 | 内容 | 谁填 |
|---|---|---|
| **一、要求** | 开始之前的检查项、六条硬性要求（见下） | — |
| **2.1 载具身份** | `vehicles` 的键、载具类型 | 工具 |
| **2.2 几何** | 炮塔部件、炮管偏移、履带内缘 / 轮胎顶、车体与炮塔盒尺寸 | **工具**（照抄，别改） |
| **2.3 装甲数值** | `turret.*` / `hull.*` 各五个面 | **人** |
| **2.4 伤害倍率** | `damage_multiplier.*`，选填 | **人** |
| **2.5 可选区域** | 炮根弱点、首上机枪口、首上首下、履带区、轮胎区、反应装甲（含削减 / 角度门槛）、按部件记值 | **人**（不填整块不生效） |
| **2.6 破甲弹表** | `overrides.heat` / `.he`，字段同上 | **人** |
| **2.7 弹药** | 这辆车带的每种武器、建议货架、要填的字段 | 半自动 |
| **三、填完之后** | 验收清单 | — |

### 六条硬性要求

写在表里的原因和这里一样：**每一条被违反时都不会报错**，只会让数字悄悄是错的。

| # | 要求 | 不满足会怎样 |
|---|---|---|
| R1 | `turret` 和 `hull` 的五个面都要给值 | 缺的面取默认 90 —— 不报错，只是数字是错的 |
| R2 | 弹药的 `profile` 必须是本车 `overrides` 里存在的名字 | **静默**退回载具自己的装甲表，日志里什么都没有 |
| R3 | `ammo_penetration` 的键必须是载具包里真实存在的武器 id | 配了也永远不生效，同样没有日志 |
| R4 | 2.2 节量出来的数字一律不要改 | 它们是量出来的，改了就是错的 |
| R5 | `penetration_damage` 一旦填了，就**取代** `剩余穿深 × 倍率` | 高爆弹那种「不看得穿多少」的弹才该填 |
| R6 | `overrides.he` 只写和 `overrides.heat` **不同**的面 | 写全了容易和 heat 漂移，漏写才是正常用法 |

### 工具填的那一半，和它填不了的

| 数字 | 是什么 | 怎么来的 |
|---|---|---|
| `turret_part_ids` | 哪些部件算炮塔 | 骨骼树：挂在炮塔骨骼下、且不是座位 |
| `turret_weak_spot.offset_x/y` | 炮管轴线偏离炮塔盒中心多少 | 炮管立方体中心与炮塔盒中心之差 |
| `hull_weak_spot.offset_x/y` | 机枪口在首上哪里 | 车体机枪立方体中心与车体盒中心之差 |
| `track_ends.inner_edge` | 履带内侧在车体半宽的哪里 | 履带立方体内侧面；这是**上限**，只能填更小 |
| `road_wheels.top` | 轮胎到车体归一化高度的哪里为止 | 轮子立方体顶面 |
| `hull_front_split.split` | 首上 / 首下的分界 | **量不出** —— 见下 |

`hull_front_split.split` 是唯一量不出来的：模组碰撞体是一整块平盒子、视觉模型也没有斜面几何可读，
只能看车定。T-64、T-90M 三兄弟和 T-72B3M 都用 `0.0`（对半），Abrams 用 `0.4`（首下占大头）。
要写"首上占上 2/3"就得写**负数** —— 见下，这条编码到现在也没有哪辆车在用了，但它是记录在案的
一次踩坑。

> ⚠️ **它是带符号的，`+1` 是车体盒的顶。** 想写"首上占上面 2/3"就要写**负数**。写成正的
> （`+0.33`）薄的那块就盖住下面 2/3，正面装甲只剩该有的四分之一 —— 而表上两行都印着像模像样的
> 厚度，**只有覆盖率那一行看得出来**。填完记得看 `check` 输出的 `glacis = upper N%`。

### 空白那一栏是刻意的

- **装甲数值一律留 `0`**。工具不知道一辆 T-72 的首上对 APFSDS 等效多少毫米，也不该猜 ——
  而一个看起来填好了的条目，是没人会去填完的条目。
- **没有载具包文件的武器**不会进 `ammo_penetration`（基础模组自己的，比如烟雾弹发射器），
  工具会在表里标成「不配」：配了也永远不生效，这正是弹药合集工具从另一头报告的那件事。
- 表的 2.2 / 2.3 两节是**分开写的**，就是为了让"哪些是抄的、哪些是想的"一眼可见。

### 工具凭什么可信

它自己验证自己。`check` 模式把**每一辆已经在配置里的车**（跨所有已安装的包，zip 或解包文件夹）
重新量一遍，和配置里写的比：

```
vvp_ywzj:t64
  turret part ids  : [turret, turret_machine_gun, turret_smoke_grenade, commander_machine_gun]
  ok   matches the config
  track_ends.inner : derived inner face 0.742, config 0.640 (config is at or below it)
  gun mount offset : derived (+0.142, -0.062) from turret_barrel, config (+0.000, +0.000)
  ok   within a fifth of a block
vvp_ywzj:m1a1
  turret part ids  : [turret, turret_machine_gun, turret_smoke_grenade, turret_mg2, turret_mg3, hatch_1, hatch_2]
  ok   matches the config
  gun mount offset : derived (-0.096, -0.100) from turret_barrel, config (-0.100, -0.100)
```

两条断言都写在这里，是因为两条都是**真的踩过坑**：

- **炮塔部件按骨骼树推**，不按名字。而且「部件指向的骨骼」在模型里往往根本不是一个骨骼 ——
  模型把关节和几何分开了，`turret_mg` 只以 `turret_mg_barrel` 的形式存在，所以要顺着 `_` 后缀往下找。
  第一版没做这件事，三辆车的部件表全错。
- **要排掉座位。** Abrams 的驾驶员座位在模型里是挂在**炮塔骨骼**下面的，照着骨骼树走会把它算成炮塔装甲 ——
  于是打在驾驶员头上的那一发会去和炮塔正面比厚度。这条是真从数据里看出来的，不是想当然。
- **炮管取"炮塔下方最长的那根立方体"**，不取体积最大的、也不找叫 `barrel` 的骨骼：
  Abrams 炮塔下体积最大的是一块舱盖（是炮管的三倍），而炮管在长度上比其它所有东西长四倍。
  取长度之后，Abrams 量出 `(-0.096, -0.100)`，配置里人手量的是 `(-0.100, -0.100)`。
- **货架分类也对着配置验**：配置里每一条弹，规则必须条条对得上。它是**逐包**打印的
  （`0/0`、`0/0`、`0/0`、`3/3`、`19/19`，五个包合计 `22/22`）——只报一个总数会掩盖"某个包
  整个没验"这件事。
  - 这条规则抓到过第二次：RK-2S 的名字里**没有任何一个弹药代号**（`RK-2S Barrier ATGM`），
    于是它一路掉到默认分支、被归成**穿甲弹** —— 一发破甲战斗部被摆到钢针那一栏。补的词是
    `atgm`：反坦克导弹在现实里几乎都是破甲战斗部，而这个字是它的名字里唯一的线索。
  这条同样抓到过 bug —— 载具包把**每一件武器**都标成 `type=ywzj_vehicle:cannon`，
  从 125mm 坦克炮到 7.62mm 并列机枪都是，所以 `type` 一个字都不能信，只能看口径和型号名；
  而且必须先判 "heat" 再判 "he"，否则每一发破甲弹都会被归成榴弹。

> 这正是这个工具存在的意义：**量错一个数字，游戏里不会报错**，只会在几个月后某次对炮时
> 让人觉得"打炮塔怎么不掉血"。所以量出来的东西必须有个不靠眼睛的裁判。

### 载具包那侧什么时候要动

**只有当这辆车需要新弹药时**才动。如果它现有的弹都能用（比如 T-72B3M 的 `2a46m5_125mm_*` 包里就有），
那就只是配置文件的改动，`add_shells.ps1` 一行都不用碰。

需要新弹时，`add_shells.ps1` 的 `$rounds` 表加一行（`Id` / `Name` / `Vehicle` / `ArrayHead` / `Kind` /
口径 / 显示名），跑一遍即可 —— 它自己会回读校验。**M1296 的钢针就是这么加的**（见下），
而它同时暴露了两件值得先知道的事：

- **`ArrayHead` 要照文件里的排版写**：`[` 和 id 之间有没有换行由载具文件自己的格式决定。
- **30mm 机炮的射速和弹匣是「炮」的属性，不是「弹」的**：`New-AutoCannon` 里那几个数现在是参数，
  加第二门 30mm 时必须填它自己的（否则换一发弹会让弹匣从 120 变成 300）。

详见下文「载具包的改动」。

### 完整流程

1. `add_vehicle.ps1 list` —— 看每个包里有哪些车、哪几辆已经配了。
2. `add_vehicle.ps1 <id> form` —— 出表。**存成文件再填**（`> t90a.md`），表里的几何是量出来的，
   照抄。
3. 填 2.3 ~ 2.7。**没有捷径**，这是设计意图：等效厚度是判断，不是测量。
4. `add_vehicle.ps1 <id>` —— 拿两段粘贴用的 JSON，把填好的数字敲进去，粘进
   `config/ywzj_vehicle_armor.json`。
5. `powershell -File verify.ps1` —— `PenetrationTable` 会把这辆新车的每个部位、每种弹的
   伤害表打出来，逐行核对。这一步是替代"进游戏打一炮看看"的。
6. 重启游戏（配置在启动时读）。**不需要重新构建。**

> 第 3 步填完之后，如果这套数值值得发给别人，再把它挪进 `ArmorConfig.defaultProfile()` 的
> 一个 `addXxx(p)` 方法里，并把 `CONFIG_VERSION` +1 走一次升级路径 —— 那时候才需要重新构建。
> 换句话说：**自己用是配置，发给别人才是代码。**
