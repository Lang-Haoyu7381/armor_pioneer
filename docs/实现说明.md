# 实现说明

> 返回 [项目首页](../README.md) · [文档索引](README.md)

- 通过 Mixin 注入 `org.ywzj.vehicle.vehicle.DamageSystem#hurt` 的 HEAD 并取消，因此原版的
  部件损坏、音效、击毁殉爆等逻辑全部保留。
- 判定命中面用 `OBB#embeddingFace`。部件 OBB 的世界旋转已包含炮塔自身转角，所以炮塔转到侧面
  时判定跟着炮塔走，而不是跟着车体。
- 炮根弱点以 `PartUnit#getLargestCube()`（炮塔本体盒子）为基准做圆盘判定。
- 履带区、首上/首下、反应装甲区都以 `mainCubeOBB` 为基准；三者共用同一个局部坐标函数。
- **装甲结算是无状态的，只有一个例外**：爆反被用掉之后要记住。那份状态是
  `ArmorSystem` 里一个 `WeakHashMap<AbstractVehicle, Set<String>>`，键是这个载具实体本身、
  值是**用掉的板的名字**（盒子的 `PartUnit#getId()`；几何划出来的裙板没有 id，就用它自己的
  名字，一侧一个）。弱引用是**故意选的，不是随手写的**：本模组拿不到"这辆载具卸载了"的通知，
  用强引用的话玩家打过的每一辆车都会在内存里留到退出游戏。
- **两趟判定住在 `ArmorSystem.resolve` 里，不在 `tryHandle` 里** —— 因为工具要能调它。
  `PenetrationTable` 的每一行都走 `resolve`（不是 `resolveZone`），所以表里印的就是游戏里跑的
  那条路径；`tryHandle` 只负责把"这块板用过了"记下来和写日志。
  `Hit` 也因此多了一个 `throughLayers` 和 `pastLayers()`：**同一次命中问第二遍**时，几何一个数
  都不重算，只是把外层去掉 —— 两次调用描述的是同一次撞击，这是结构上的保证，不是纪律。
- 模型坐标系为 **+Z = 车头**（由 `turret_barrel` 的 Z 轴正向、驾驶员座位 `+1.7`、发动机位置
  `-3.88` 三方交叉验证）。反应装甲区因此取 `localZ >= 1 - 2 × front_fraction`。
- 爆炸伤害在 `tryHandle` 开头按 `DamageSource#getMsgId() == "ywzj_vehicle.explosion"` 单独处理。
  `VehicleExplosion` 构造时把**弹丸实体**当作爆炸伤害的 direct entity（`AmmoEntity` 第 118 行
  传的是 `this`），所以这个来源能查到是哪发弹药的爆炸：绝不当作穿甲结算（否则同一块装甲算两次），
  再按该弹药的 `replaces_base_explosion` 决定是放行还是拦下。
- **弹种分层时，`overrides.turret` 只能给炮塔用、`overrides.hull` 只能给车体用**，两者不能互相
  顶替 —— 早期版本写成 `pick(override.turret, turret ? armor.turret : armor.hull)`，于是车体命中
  会拿到炮塔的厚度（表现为车体侧面后半段显示 300mm 而不是 200mm）。
- **击穿判定是「剩余 ≥ 0」而不是「> 0」**。高爆弹的顶部/底部厚度和它的穿深都是 60，用 `>` 会判成
  未击穿，2000 那条永远走不到。改成 `≥` 之后，走剩余穿深公式的弹药在相等时伤害是 0（`0 × 倍率`），
  所以对它们没有可见影响。
- **命中面就是结算面**：`plateFor` → `resolveZone`，用 `OBB#embeddingFace` 定面，不做任何
  "绕过去找更薄的板"的处理。曾经有一版半径 4 格的球面做这件事，已移除，原因见上文。
- 车体在模型里是**两个前表面共面的盒子**（`main_structure` 是整个车体，`vehicle_body` 是更宽的
  上部车身，y 范围 0.59~1.93）。`FaceProbe` 用模组自己的 `hitOBB` + `embeddingFace` 从各种俯仰角
  验证过：首上稳定判成 `face +3`，不会被这两个盒子的顶部/底部面抢走。
- 探测仪的翻页用 `InputEvent.Key`，**只在主手拿着探测仪、且没有打开任何界面时**才动作，按下的
  那一刻（`action == 1`）才算一次。方向键的键码**不用 GLFW 常量**（那需要往编译类路径里再加一个
  jar），而是走 `InputConstants.getKey("key.keyboard.up")` 查 Mojang 自己的键名表 —— 查不到就返回
  `-1`，永远匹配不上真实按键，翻页静默失效而不会崩。
- 翻页的序号存的是**一个累加计数**而不是取过模的下标，绘制时才按当前载具的表数量 `Math.floorMod`；
  这样从 3 套表的载具看向 2 套表的载具时不会越界，也不用在按键时就知道正瞄着谁。
- `ArmorOverride` 里没写的字段**继承的是载具自带的值，不是另一个 profile 的值** —— profile 之间
  不互相继承。所以 `he` 只能照抄一份 `heat` 的表再改顶部/底部；默认值由 `chemicalProfile(...)`
  一个方法生成，保证这两份不会漂移，但写进配置文件之后就是两份独立的表了。
- `overrides.<name>.turret` / `.hull` 是 `ArmorSet`，字段是**基本类型 float**，所以这两块必须**写全
  五个面**：只写 `roof` 的话其余四面会变成 `ArmorSet` 的类默认值 90mm，而不是继承载具的值。
- 失明效果用 `ForgeRegistries.MOB_EFFECTS.getValue(new ResourceLocation("blindness"))` 查表，
  **不用 `MobEffects.BLINDNESS`** —— SRG 化之后 `MobEffects` 的字段编号和源码声明顺序不一致，
  按位置猜会拿到别的效果。
- `instanceof X x` 模式里**模式类型不能和表达式类型相同**（例如 `getDriver()` 已经返回
  `LivingEntity`，再写 `instanceof LivingEntity x` 会报「-source 17 不支持类型模式」）。
  这种「恒真模式」要到 source 21 才允许，报文里的版本号是字面意思，不是类路径问题。
- 炮弹引信用 **`AmmoEntityStateMixin` + 一个 `ShellState` 接口（duck typing）**实现，而不是维护
  一张"某发弹现在是什么引信"的旁表。旁表会被两个同时开炮的玩家撞车，而**炮弹本身是唯一真正
  知道自己装了什么的东西**。读取方只写 `shell instanceof ShellState`，所以没被 Mixin 碰过的
  弹丸一律落到 `IMPACT`。
- **私有字段走 `@Shadow`，不走反射**：`AmmoEntity.discard` 是私有的、有没 getter 也没 setter，
  而强制起爆要靠它把弹丸标记成待删除（`AmmoEntity.tick` 下一 tick 才会真的 `discard()`）。
  Mixin 允许直接 shadow 目标的私有成员，`life` 和 `explosion` 也是同样处理的。
- **`@Redirect` 的目标串必须和字节码完全一致**。这里是
  `Lnet/minecraft/world/level/Level;m_45547_(Lnet/minecraft/world/level/ClipContext;)Lnet/minecraft/world/phys/BlockHitResult;`
  —— 从 `AmmoEntity.tickHit` 的 `javap -c` 输出里抄来的。`"required": true` + `defaultRequire: 1`
  会让注入失败在**加载期**就炸，而不是静默失效，这是想要的行为。
- **网络消息用 netty 的 `writeByte` / `readByte`，不用 `writeVarInt`**：`FriendlyByteBuf` 自己
  声明的方法是 Minecraft 的，在 SRG jar 里变成了 `m_xxxxx_`；从 `ByteBuf` 继承来的方法则是 netty
  的，名字不变。三个字节够装下引信、延时（≤100）和一个标志位。
- **加 netty 到编译类路径**：`FriendlyByteBuf` 的读写方法继承自 `io.netty.buffer.ByteBuf`，
  不把 `netty-buffer` 放上去，连 `writeByte` 都不解析。
- 客户端的 `TickEvent` / `InputEvent` 处理**全部放在 `ClientSetup` 注册的 `FuzeKeyHandler` 里**，
  网络消息类里**不出现任何客户端类** —— 它在专用服务器上同样会被注册和发送，一引用
  `LocalPlayer` 就会在服务端加载期炸。动作栏文字先在 `FuzeSettings` 里拼好挂着，由客户端
  tick 取走显示。
- `PenetrationTable` 的 `signature()` 现在**把 `proximity` 也算进去**：多用途弹的碰炸档和普通
  破甲弹的数字一模一样，不区分就会被分到同一组，**第二张表永远打不出来** —— 而那张表才是这颗弹
  存在的理由。（上一轮刚修过同类问题：两发"高爆弹"因为 profile + 穿深相同被并成一组。）
- **一个概念换了名字就要跟着换类名。** 引信状态里后来又装进了"装填哪一发"，于是 `FuzeSettings`
  / `FuzeActionMessage` / `FuzeStateMessage` / `FuzeKeyHandler` / `FuzeHolder` / `FuzeControl` /
  `FuzeSessionHandler` / `AmmoEntityFuzeMixin` 一起改名成 `GunnerSettings` / `GunnerActionMessage`
  / `GunnerStateMessage` / `WeaponKeyHandler` / `ShellState` / `OperatedRound` /
  `GunnerSessionHandler` / `AmmoEntityStateMixin`，验证工具 `FuzeCheck` → `GunnerCheck`。
  留着旧名字、往里塞不相干的字段，下一个人读到的就是一句谎话；改名贵一次，说谎一直贵。
- **给已有的车加一个新区域，光写进 `defaultProfile()` 是不够的 —— 它到不了任何人的配置里。**
  升级路径里那段"补上缺失的可选块"原本是手写的三个 `if (xxx == null)`，加 `hull_weak_spot` 时
  没有加第四个，于是机枪口**在代码里、不在游戏里**，而症状只是"打不到"：文件里没有这个键、
  代码读到 null、区域静默不存在，**没有任何报错**。
  现在那段改成了一张**列表**（`inherit(...)` × 7），新加一个块就是加一行，忘不了。
  同一条还解释了另一半症状：`hull_front_split` 只在**为 null** 时才补，所以**改了默认值也不会
  生效** —— 文件里已经有那个块了。改默认值必须配一条迁移（只在文件里还是那个旧数字时才动）。
  这两件事都是"用户在跑旧文件"这一类，而它们的共同点是**沉默**。
- **改名要一次改干净，包括那些"反正没人看见"的地方**：`t64_armor` → `ywzj_vehicle_armor` 这一轮
  连 mixin 的 `@Unique` 前缀（`t64armor$` → `ywzjarmor$`）、日志前缀、jar 名、脚本里的字符串
  全都跟着变了。留着旧前缀不是"省事"，而是让下一个人在日志里看到两个名字、然后花时间确认
  它们是不是同一个东西。**只有一处必须保留旧名**：`PREVIOUS_CONFIG_NAME`，因为它的作用就是
  指认旧文件——所以验证脚本最后会扫一遍全树，只允许这两个常量命中。
- **改名不能动玩家的数据。** 物品 id 和配置文件路径都带着名字，改名必然会碰到它们。物品没法救
  （只能重新给一次，README 里写清楚），但配置文件可以：启动时把旧文件**移动**成新名字。
  两个必须写死的条件——**新文件不存在**才动，且**只移动一次**——否则改名就等于静默回滚玩家
  之后所有的调参。`UpgradeCheck` 用三个用例把这两条钉住。
- **一个"查找"入口不要顺手替调用方过滤。** 见上文「点了没反应」那一节：把"是哪发弹"和
  "这发弹支持什么"揉进同一个函数，等于给第二种用途判了死刑，而且**失败时两边都不出声**。
  查找返回事实，能力由调用方判断。
- **为一种能力写的门槛，会静默挡住后来增加的能力 —— 这个错已经犯了两次。** 第一次在查找入口
  （`OperatedRound` 里的 `multiPurpose()` 过滤），第二次在炮弹认领状态时
  （`AmmoEntityStateMixin.ywzjarmor$adopt()` 开头同样一句 `!ammo.multiPurpose() → return`，
  而装填的赋值就写在它下面）。两次的症状一模一样：**界面、按键、服务端、日志全都正常，
  只有效果不对**。凡是写出「能力判断 → 提前返回」，都要回头确认**返回之前该做的事做完了没有**。
  参见上文「选择成功但炮弹效果没变」那一节。
- **装填选择做在槽位上，不是做成更多槽位**：基础模组里"一个槽位"就是载具武器列表的一项，
  那一项能打什么由它的武器文件决定 —— **没有第二个弹药列表可以塞**。所以选择放在本模组这一侧。
  序号 0 定义为"载具包给这个槽位的那发弹"，`variants` 只放**追加**选项，这样
  `penetration` 不会变成第二个真相，也不需要一条"两处必须相等"的断言去兜。
- **"谁说了算"要放在唯一知道答案的那一侧。** 引信按键最初让**客户端**判断"当前武器是不是多用途弹"，
  还要求它先收到过服务端消息才肯发包 —— 两条都是客户端在猜，而且**都只能猜错成"不发"**；
  一旦猜错，功能整个死掉且**日志里没有任何痕迹**。现在客户端只判断"我坐在载具上没有"（它唯一
  确定知道的事），其余全部交给有座位表的服务端。凡是"猜错了就静默失效"的判断，都不该放在
  信息不全的那一侧。
- 同理，**"证明对方存在"的凭据不能是收包**。用"收到过服务端消息"当作"服务端装了本模组"的证明，
  等于要求先收包才能发包 —— 而那个包正是被这个前提挡住的。现在的凭据是**回包**：发出去，
  回不来才说明对面没有。1.5 秒超时，比"永远不发"多一条出路。
