# 改名与配置迁移

> 返回 [项目首页](../README.md) · [文档索引](README.md)

原来叫 `t64_armor`，因为那时只管一辆 T-64。后来管的车越来越多（现在 11 辆、跨两个包），
名字跟着改成 `ywzj_vehicle_armor`：
**modid、Java 包名、物品 id、贴图命名空间、翻译键、配方文件、mixin 配置、日志前缀、jar 名**
全部一起改。改一半的代价比全改高——留着旧名字的 id、往里塞不相干的东西，下一个人读到的就是一句谎话。

唯一**不能**跟着改的是玩家已经写好的那份配置，所以启动时有一段认领逻辑：

```java
Path previous = configDir.resolve("t64_armor.json");   // 旧名
Path current  = configDir.resolve("ywzj_vehicle_armor.json");
if (Files.exists(current) || !Files.exists(previous)) return;
Files.move(previous, current);
```

- **移动，不是复制。** 复制会在 config 目录里留下一份永不更新的僵尸文件，下次有人误删新文件，
  游戏会悄悄回退到几个月前的数值。
- **新文件已存在就什么都不做。** 这条才是关键：改名后你已经调过新文件的话，旧文件绝不能盖回去，
  否则改名的代价是**悄悄回滚你之后的所有修改**。
- **内容不需要翻译。** 文件是按载具 id / 武器 id 索引的，里面没有任何一处带本模组的名字；
  版本号也跟改名无关，所以认领之后走的还是原来那条升级路径。
- 旧文件在、新文件也在、但旧文件更新？不动。**认领只发生一次**，就是改名后的第一次启动。

> `UpgradeCheck` 里对这段逻辑有三个用例（这个工具本身也用反射直接调它，不需要开游戏）：
> 只有旧文件 → 认领；两个都在 → **新文件原封不动**；一个都没有 → 什么都不做也不报错。
> 第二条例外值得单独说：没有它，改名就是一次静默的配置回滚。
