# 基础模组兼容性说明

> 返回 [项目首页](../README.md) · [文档索引](README.md)

本页记录每一代基础模组（ywzj_vehicle）升级时附属模组所做的适配。0.6.3 是当前支持的最低版本。

## 适配 ywzj_vehicle 0.6.3（2.0.1，当前）

本版针对 **ywzj_vehicle 0.6.3**，`mods.toml` 的依赖范围改成 `[0.6.3,)`。0.6.3 改了 16 个类，
其中**只有一处对附属模组是破坏性的**；载具包格式没有变化，只是新增了一个可选字段。

### 附属模组：悬挂的"支撑面"变成"单个支撑中心"

0.6.2 的 `SuspensionUnit` 把一只轮子当成一小片接触面：`buildSupportOffsets` 在骨骼的方块上
铺开若干支撑点，`simulate` 按 `supportRestLengths[i]` 逐点生成 `SupportContact`，
`PhysicsEngine.motionBySuspension` 读这些接触点。`restLength` 只是它们的**平均值**。

0.6.3 把这块整个换掉了：

- `supportRestLengths` / `supportMaxCompressions` **两个数组被删除**；
- 每套悬挂只有一个支撑中心 `supportCenter`（支撑方块包围盒的 x/z 中点、y 最低点）；
- `findContactLength` 直接拿 `restLength` 去量；
- 静态标定 `calibrateRestLengths` 也**直接写 `restLength`**，不再求平均。

所以 `SuspensionUnitMixin` 原来 `@Shadow` 的 `double[] supportRestLengths` 在 0.6.3 里不存在。
Mixin 配置是 `required: true`，`@Shadow` 找不到字段会在**类转换阶段**抛错，整个模组停在主菜单
之前。现在这个 mixin 只 shadow `restLength`，按"标定值 + 偏置"写一个数即可 ——
也就是 0.6.2 里写了两个、现在写一个。

> 旧版在 0.6.2 上必须两个都写，是因为物理读数组、界面读字段。0.6.3 两者合一。
> 这个类现在的注释记的就是这条，避免以后有人按旧结论加回数组。

### 新增 `center_offset`：只影响履带视觉，不影响物理

`SuspensionUnitPojo` 新增 `center_offset`（`Vec3`，默认 0），全模组只有两处读它：
`getTrackCenterZ()` 和 `getTrackFloatingReference()` —— 都是**履带/负重轮视觉路径**。
`simulate` 里的接触点仍然是 `supportCenter`，没有加这个偏移。

0.6.3 自带的 `default_vehicle` 给 99A / M1A2 的四个悬挂加了 z 方向的 `center_offset`
（这些车的支撑方块在 z 上不对称）。装甲先锋的七辆车**不需要**：实测所有悬挂立方体的
**z 中心都在枢轴上（dz = 0.0000）**，只有 K2 / 10 式 / 天马-20 / ZTZ-100 的 x 有 ±0.3 格的
左右对称偏移，左右抵消，履带中心不变。所以包里没有加这个字段。

### 其他 0.6.3 变化（已核对，无需改动）

- **远距离渲染**：新增 `DistantVehicleRenderHandler` / `DistantVehicleState` / `ServerBroadcastEntities`，
  `AbstractVehicle` 新增 `serializeDistantRenderData` / `deserializeDistantRenderData` 和
  `renderBeyondRenderDistance`（固定翼 / 旋翼机置 true）。全部是新增成员，没有动旧方法。
- **固定翼失速尾旋**：`FixedWingVehicle.tickMove` 重写，新增 `stallSpinDirection`。附属模组不涉及。
- **物理**：`PhysicsEngine` 的非悬挂方块碰撞多了一次 `m_60812_` 包围盒判断（防站在台阶边缘被弹飞）。
  附属模组不涉及。
- **导弹**：`MissileEntity` 的发射尘土只在发动机燃烧时生成。
- **渲染**：火箭发动机火焰改为 cutout、按喷口直径缩放；`AllConfigs` 的注释补了英文。
  `LevelRendererMixin` 新增远处载具的渲染钩子。
- `AllEvents` 的超视距实体广播改用 `ServerBroadcastEntities.broadcast`。
- 载具包加载器、结构模型、武器、部件、悬挂数据格式**没有变**。

### 载具包：1.1.6，文件夹改名，主炮塔与车长武器站都打开稳定器

- `vehicle_pack.meta.json`：依赖 `[0.6.2,)` → **`[0.6.3,)`**，版本
  **1.1.3 → 1.1.4 → 1.1.5 → 1.1.6**，日期 2026-11-17；描述补上 **豹2A4**（包里早就有，
  元数据一直没写）。
- **1.1.4 → 1.1.5：七辆车的主炮塔 `turret` 把 `with_stabilizer` 从 `false` 改成 `true`；
  1.1.5 → 1.1.6：车长武器站 `commander_machine_gun` 也改成 `true`。**
  之前炮塔是纯车体随动：车体一转，炮塔跟着转。基础模组 `WeaponUnit.tickRot` 只在这个标记
  为真、炮手/车长在座、且车体转向造成的偏差小于 5° 时，才把**世界瞄准方向**换算回本地角并
  反向补偿；关着就永远随车体。0.6.3 的默认包只稳定主炮塔；这里按用户要求把车长武器站也
  稳定（同轴机枪与烟雾发射器没有这个开关，保持默认）。
- 文件夹 `armor_pioneer-1.1.0-0.6.2\` → **`armor_pioneer-1.1.6-0.6.3\`**。基础模组按目录扫描，
  不看文件夹名；改名只是让磁盘上的名字和元数据一致。**不能同时留两个文件夹**，否则第二个只会
  打一行 `Duplicated namespace`。
- 包里**没有一个 JSON 需要为 0.6.3 改动**：格式没变，`center_offset` 不需要（见上）。
  改动前的元数据备份在 `vehicle_pack.meta.json.before_063.bak`。

### 验证

`verify.ps1` 仍是 **34 项检查（35 个源文件）**，对着 0.6.3 编译并运行。32 项通过；
`PeriscopeCheck` 与 `VehicleScaffold` 的两项失败是**本次适配之前就存在的**（见下），
与 0.6.3 无关，本次没有动它们：

- `PeriscopeCheck`：VT-5 车长潜望镜 ±10° 锥内 81 条射线有 3 条被挡住（中心射线是通的）。
- `VehicleScaffold`：K2 的 `turret_part_ids` 少了 `door_gunner` / `door_commander`
  （门是后来加进包里的部件）；`tank_assault:panther` 的机枪口配置 y 是 0.700，包里的
  `mg_barrel` 现在量出来是 0.415。

## 适配 ywzj_vehicle 0.6.2.1（2.0.0）

本版现在只针对 **ywzj_vehicle 0.6.2.1**，`mods.toml` 的依赖范围是 `[0.6.2.1,)`。0.6.2.1 对附属
模组**只有一处破坏性改动**，其余都是新增能力；载具包格式没有变化。

### 附属模组：开火音效与瞄准上下文被拆开

0.6.2 的 `AbstractVehicleWeapon.onClientFire` 自己既播开火音效，又自己调用
`WeaponUnit.aimContext()` / `aimContexts()` 取炮口位置。0.6.2.1 把这两件事拆成了两个方法：

- 音效移进 **`playFireSounds()`**（里面的 `Level#playLocalSound` 还是原来那一句）；
- 上下文选择移进 **`getFiringAimContexts()`**（RIPPLE 一支、SALVO / FULL_SALVO 一整排）。

`AbstractVehicleWeaponFireMixin` 原来的三个 `@Redirect` 因此全部找不到目标。Mixin 配置是
`required: true` + `defaultRequire: 1`，找不到目标的后果不是"静默失效"，而是**启动阶段直接崩**。
现在的做法：

- 音效重定向跟着调用搬进 `playFireSounds`；
- 瞄准上下文重定向留在 `onClientFire`，只包住它对 `getFiringAimContexts()` 的那一次调用。

第二条是刻意的：`getFiringAimContexts()` 同时被 `doClientShoot()` 用来生成**发给服务端的**
射击上下文，在那里面重定向会把服务端收到的弹道也改掉；附属模组只想移动客户端炮口特效，
所以只包 `onClientFire` 里的那一次调用。弹道、服务端校验和弹药消耗都不受影响。

### 其他 0.6.2.1 变化（已核对，无需改动）

- `Reload` 新增 `unload_on_switch`，**默认 true**，与 0.6.2 行为一致；本包没有写这个键。
- 新增 `fire_loop` / `fire_loop_start` 音效节点；没写就不循环，旧写法照常工作。装甲先锋的
  自动炮没有加，保持原有的单发音效。
- `WeaponUnit.toAimPosition()` 换成 `aimAtPosition(partialTick)`，`worldBoltPosition` 改为
  private。附属模组没有调用这两个方法，编译通过。
- 履带/车轮动画改由 `TrackedVehicleContext` 统一推进，`TrackUnit` 从动画上下文取每帧位移。
  装甲先锋的七辆车都同时有 `animation_controller` 和 `track_config`，路径完整；没有控制器的
  车才会停止履带动画，本包不存在这种车。
- 牵引从 `PhysicsEngine.transferEnergyTo` 换成 `applyTowImpulse`，新增 `VehicleThrower` /
  `AmmoEntity#setWeaponId`。附属模组没有引用这些 API。

### 载具包：零改动

`vehicle_pack.meta.json` 的依赖本来就写的是 `[0.6.2,)`，0.6.2.1 满足；文件格式、结构模型、
控制器、配方都没有变。包版本升到 **1.1.1**（2026-11-06），只是这次交付的标记。

### VT-5 显示模型回退

2026-11-06 19:29 的一次 `vt5.json` 保存把**整车显示模型**相对实体平移了
(+0.30, −1.30, −13.80) 模型单位（约 0.86 格），并给 `cannon_tube` 加了 17 个方块（形状像圆柱
生成器的测试结果）。结构模型和碰撞箱没有跟着动，`SmokeCheck` 因此报出三处烟雾发射器位置不符。
按用户决定，`vt5.json` 已回退到 **2026-11-05 10:47** 的版本，结构/碰撞箱保持原样，28 项检查
全部恢复通过。回退前的文件保留在同目录的
`vt5.json.before_0621_model.bak`，需要找回那次编辑时可以直接替换回来。

> **注意：**附属 jar 现在**不能**在 0.6.2 上加载 —— 新的 mixin 目标 `playFireSounds` /
> `getFiringAimContexts` 在 0.6.2 里不存在。`mods.toml` 的 `[0.6.2.1,)` 就是拦这个的。

## 适配 ywzj_vehicle 0.6.2（2.0.0）

本版当时只针对 **ywzj_vehicle 0.6.2**，`mods.toml` 的依赖范围也改成了 `[0.6.2,)`。0.6.2 不是一次小
更新：它重写了 HUD、履带、悬挂的视觉路径和物理碰撞，下面每一条都是量出来的，不是照版本号猜的。

### 载具包：四个补丁要重新打

0.6.2 的新 VVP 包会覆盖掉旧包上的补丁（这是老问题，补丁本身是幂等的），四个都要重跑：

```powershell
powershell -File add_shells.ps1          # 30mm 钢针、HE 等包里没有的弹
powershell -File add_snorkel.ps1         # T-64 的通气管
powershell -File split_rear_armor.ps1    # T-90M 炮塔后装甲独立成 part
powershell -File add_suspension.ps1      # 履带车 0.1 -> 0.32 的悬挂行程
```

`add_snorkel.ps1` 的读回检查改了一处：它以前硬编码“姿态图里必须有 `track_animation`”，而
0.6.2 把这个节点从**每一个 VVP 控制器**里删掉了（履带链现在按结构模型画）。现在它从 `.bak`
里的原控制器读出节点类型，再要求“原控制器有的，一个都不能少”——版本无关，也不会放过真正被
删掉的节点。

> **K2 不在 `add_suspension.ps1` 里。** 它在装甲先锋包中，行程是直接改
> `armor_pioneer-1.1.0-0.6.2\data\armor_pioneer\vehicles\k2.json`（当时还是 zip）：
> 12 个悬挂件的 `max_droop` 0.123 与 `max_extension` 0.2705 一起到 **0.60**
> （先到 0.32，俯仰改成 ±5° 后抬到 0.50，加上 ±4° 侧倾后再抬到 0.60；备份
> `armor_pioneer-1.1.0-0.6.2.zip.before_k2susp.bak` / `.before_k2pitch5.bak` /
> `.before_k2roll.bak`）。只换这两个数值，其他字节一个都不动。
> **其他载具包的载具这次没有适配。**

### 装甲先锋包：履带跟着悬挂动

0.6.2 给 track part 增加了 `suspensions` 表：

```json
"id": "track_left",
"structure_bone": "suspension_track_left",
"suspensions": {
  "track_left": ["suspension_left_1", "...", "suspension_left_6"]
}
```

键是**结构骨架上履带路径的名字**，值是**悬挂 part 的 id**；`TrackUnitData` 会检查两者的数量，
对不上直接抛异常（不是静默忽略）。VT-5 / VT-4 / K2 的左右履带各自一个 key，六个负重轮各自
绑定。包的 `vehicle_pack.meta.json` 升到 **1.1.0**，依赖改成 `[0.6.2,)`。

**K2 这次才真正接上这条浮动路径。** 原来的装甲先锋模型把履带画在显示模型的 61 节
`vt5_tread_*` 上，由 `vt5_tread_l/r_move` 沿一条固定的环播放；`suspensions` 表虽然绑了，
`TrackUnit` 却因为 `track_config.model = effect/none` 没有 link model 可画，所以悬挂动、
履带不动。现在的做法和 0.6.2 官方包一致：

- `track_config.model` 指向新生成的 `effect/k2_track_link`。这个 link model 是从 **K2 自己的
  第一节履带** 生成的（方块相对骨骼 pivot 取出），宽 0.654 格、长度 0.269 格，UV 也是 K2 的，
  不是 VT-5 的；
- 显示模型里 **122 个 `vt5_tread_*` 骨骼的方块清空**（骨骼和动画保留，方便以后恢复）；
  `animation_controller` 的 `track_animation` 节点去掉，`track_config` 的
  `left_track` / `right_track` 也去掉，不创建显示履带动画实例；
- 结构模型的履带路径整条换成显示模型的 **61 节链节中心环**（补上闭合点，共 **62** 个路径点）：
  x **±1.704**、y **0.196..1.581**、z **−3.799..4.711**（结构坐标是显示坐标的 x 镜像、z 取反，
  y 相同）。旧路径的 y 比显示环低约 **0.34 格**、而且整体按 **1.14 倍**缩放，所以 link model
  的下边一段正好埋进地面——这是上一张截图里的现象。track part 的 `partCubeOBBs` 是空表，
  移动的只是路径，不动任何碰撞箱；
- **闭合缝挪到了直线段。** 路径原先从显示链节 1（前主动轮曲线，rest 36°）开始，`TrackUnit`
  的采样缝也落在那里，link model 在前后端曲线上会显得一坨。现在起点是链节 **20**（直线段，
  rest 0°），缝藏在车体下面的直线上，前后端曲线只由路径切线正常转过；
- `TrackUnit` 每帧 `updateFloatingPoints`，把路径经过 12 个悬挂的 `trackFloatingPoint`；
  车高、俯仰、单轮压缩变化时，履带链节跟着轮子一起起伏。
- **左右两条路径曾经是反的（这次修）。** 结构坐标是显示坐标的 **x 镜像**，所以把显示环的 x
  原样抄进结构模型，`track_left` 的链节会落到车体**右侧** —— 而它的 `suspensions` 表绑的是
  左侧弹簧。车高和俯仰时两侧一起动，看不出来；加上 ±4° 侧倾后，左侧履带就会跟着右侧弹簧走。
  现在把 `suspension_track_*` / `track_*` 两个骨骼的 pivot x 和 62 个链节 cube 的 x 一起镜像
  回来：`track_left` 的链节在引擎 x **−1.704**、左侧弹簧在 **−1.685**，对上了。备份
  `armor_pioneer-1.1.0-0.6.2.zip.before_k2trackx.bak`；`SuspensionCheck` 现在会验这一条
  （K2 专用：vvp 包的弹簧原始 x 符号相反、两条路径共用一个 `tracks` 骨骼，同样的比较会误报）。

K2 的 `track_ends.inner_edge` 也从 **1.56** 改到 **1.00**（v54 迁移只动出厂值）：
结构路径收到 1.704 后，1.56 会漏掉链节内侧约 0.18 格；1.00 以 1.37 格的内侧面为准，
正好覆盖整个 link model。（当时 VT-5 / VT-4 仍然是旧的显示履带动画，2026-11-01 才换，
见下一节。）

还有一处是**模型专用**的：K2 的悬挂支撑盒底面在**轮底**，比显示链节中心低 **0.0654 格**。
`SuspensionUnit.calculateTrackBounds` 的浮动参考正是从支撑盒底面起的，所以 link model 的下沿
会跟着沉下去、有一段一直在地里。`Suspension.Settings.trackCenterOffset`（默认 **0**；K2 设
**0.0654**，10 式按同一个方法量到 **0.0543**）在 `calculateTrackBounds` 返回时把这个参考点抬高；
履带顶面和前后两端不动，
只修正下沿。v53 写下的配置没有这个字段，v54 的迁移会补上。

**10 式（2026-10-28）原来和 K2 切换前一模一样。** 显示配置还是
`track_config.model = effect/none`，显示模型自带 122 节 `vt5_tread_*`，由
`vt5_tread_l/r_move` 沿固定环播放；悬挂把车体和轮子抬起来，`TrackUnit` 也算出了浮动路径，
但 `effect/none` 解析不出模型，所以**履带在画面上完全不动**。按 K2 的同一套办法换了：

- 新建 `effect/type10_track_link`，从 **10 式自己的第一节履带**（`vt5_tread_l_1`，7 个方块）
  生成，宽 9.5911 模型单位 = **0.599 格**，UV 也是 10 式的；
- 显示模型 122 个 `vt5_tread_*` 骨骼的方块清空（骨骼和动画保留），`left_track` /
  `right_track` 去掉，控制器的 `track_animation` 节点删除；
- **不用改结构路径**：10 式的 `suspension_track_*` → `track_left` / `track_right` 本来就是
  显示链节中心（61 个方块，pivot x **±24.99 模型单位 = ±1.562 格**，和显示链节的 **±1.5615**
  对得上），`trackCenterOffset` 也已经是量好的 **0.0543**。

`SuspensionCheck` 现在对 **K2 和 10 式**都验同一组事：`track_config.model` 指向的 link model
存在且 `track_link_0` 有方块、显示模型里没有带方块的 `vt5_tread_*`、`track_config` 没有
`left_track`/`right_track`、控制器里没有 `track_animation`。这四件漏掉任何一件，画面上都是
“悬挂动了、履带没动”，而日志里没有一个字。

包的两个备份：`.before_k2track.bak`（link model 切换之前）和
`.before_k2trackloop.bak`（把结构路径换成显示链节环之前）。更早的
`.before_k2susp.bak` / `.before_treadfix.bak` 也都还在。10 式这次是直接改文件夹包，整包快照是
`limitless_vehicle/armor_pioneer-1.1.0-0.6.2.before_type10track.zip.bak`。

### 装甲先锋包：另外五辆也换成链接履带（2026-11-01）

### 牵引钩（0.6.2）

**0.6.2 的基础模组有完整的牵引（tow）功能，但装甲先锋包里一个钩子都没有。** 官方包
（vvp / dragonrise）给每辆车都配了 `hook_front` / `hook_rear` 两个 `ywzj_vehicle:hook`
部件；VT-5 / VT-4 / K2 原来既没有 part，也没有结构骨骼，所以按“这辆车没有牵引点”处理
—— 不是按键没绑，是车上根本没有可以被链子挂住的地方。

现在三辆车各补了一对：

| 车 | 前钩 z（格） | 后钩 z（格） | 高度 |
|---|---|---|---|
| VT-5 | +4.55 | −3.35 | 1.00 |
| VT-4 | +4.506 | −3.739 | 1.00 |
| K2 | +4.670 | −4.385 | 1.00 |

- 结构模型里是两个**文件级根骨骼** `hook_front` / `hook_rear`，各带一个
  **8×8×6（0.5×0.5×0.375 格）** 的方块，落在 `main_structure` 的前/后表面中心线 x = 0；
  钩子的锚点就是骨骼 pivot。和官方包一样，钩子**本身不画模型**（没有 display 骨骼），
  靠这个方块做交互判定。

  照官方包那样直接写会显示原始键名。
- 用法（基础模组自己的逻辑，本模组没加代码）：主手拿 **铁链（`minecraft:chain`）**，

  `tips.hook.*` 提示面板。
- 两端都必须是 `ywzj_vehicle:hook`；装甲先锋的三辆车现在既能拖别人，也能被拖。

### 装填时间（现实数据）

基础模组里 `reload.time` 的单位是 **tick**（20 tick = 1 秒），不是毫秒：`AbstractVehicleWeapon.tickReload`
每 tick 减一，减到 0 时 `reload()` 一次把弹匣补满。**旁边的 `shoot_interval` 才是毫秒**
（它和 `System.currentTimeMillis()` 比），两个数并排放在同一个武器文件里，单位写错一次就差
20 倍。弹匣打空才会开始装填，所以对单发炮来说这个数**就是自动装弹机的循环时间**。

装甲先锋的六门主炮原来全是 **100 tick（5 秒）**，和默认包一模一样，是平衡值。现在按各自的
自动装弹机改成：

| 车 | 主炮 / 供弹 | 每发循环 | `reload.time` | 折算 | 来源 |
|---|---|---|---|---|---|
| VT-5 / Type 15 | 105mm 线膛，**尾舱式**自动装弹机 | **4.0 s** | **80** | 15 发/分 | [WT 论坛 VT-5 建议帖](https://forum.warthunder.com/t/vt-5-bangladesh/202183)：整装 105mm 弹，自动装弹机重装 **4 秒**，38 发 |
| VT-4 | 125mm ZPT-98，**转盘式** | **6.67 s** | **134** | 9 发/分 | **泰军 VT-4 乘员手册**（[泄露本](https://www.china-arms.com/2023/12/china-vt4-tank-leakage/)，和倒车 17 km/h 同一份）：最快 **9 发/分** |
| K2 黑豹 | 120mm CN08，尾舱式 | **4.0 s** | **80** | 15 发/分 | [MilitaryFactory：ROTEM K2](https://www.militaryfactory.com/armor/detail.php?armor_id=289)：自动装弹机**最高 15 发/分** |

**2026-11-16 起，所有主炮都是「一次装填一发」。** `reload()` 是一步把 `remainAmmo` 填到
`max_capacity`，所以原来的 4 发一匣炮射导弹会连发 4 发再装填。现在每门主炮的
`max_capacity` 都是 **1**，`reload.time` 就是每发循环本身：

| 弹 | 车 | 容量 | `reload.time` | 每发 |
|---|---|---|---|---|
| GP105 炮射导弹 | VT-5 / ZTZ-100 | 1 | **80** | 4 s |
| GP125 炮射导弹 | VT-4 | 1 | **134** | 6.7 s |
| KSTAM | K2 | 1 | **80** | 4 s |

- 原来的整匣时间（320 / 536 / 160）按发数除开，否则改成一次一发后每发会慢 4 倍。
  `ReloadCheck` 现在要求主炮 `max_capacity == 1`，并直接用 `CYCLE`（秒/发）算期望 tick。

- **K2 取 15 发/分（4.0 s）**：MilitaryFactory 写的是“最高 15 发/分”，另有资料写 10 发/分
  （6.0 s，`reload.time` 120）。取的是公开指标的上限；觉得太快的把 `cannon_120mm` / `_he` /
  `_heat` 改成 120、KSTAM 改成 120 即可，`ReloadCheck` 的 `CYCLE` 也要跟着改。
- **VT-4 取 134 tick，不是 133。** 9 发/分 = 每发 6.667 s = 133.33 tick。取整 133（6.65 s）是
  9.02 发/分，略微超过手册写的“最快 9 发”，而且引擎开火后还要多走 1 tick 才起装填。取
  **134（6.70 s，8.96 发/分）** 保证不超。Military Periscope 对同一门炮写 8 发/分；手册更具体，
  按手册。
- **天马-20 是估计**：炮是 2A46 派生，朝鲜没有任何射速数字，按同类转盘装弹机取和 VT-4 一样的
  7.5 s。这是**估计，不是引文**，和它的钢针穿深（630，非引文）同一个性质。
- **10 式的 3.5 秒比 K2 的 4 秒还快，这不是笔误**：10 式的尾舱式自动装弹机公开资料给的射击
  间隔就是 3.5 秒，而 K2 的 15 发/分换算下来是 4.0 秒。
- **机枪、榴弹发射器和烟幕发射器没动，还是 100 tick（5 秒）。** 它们不是自动装弹机：120 发的
  弹链、30 发的弹鼓、12 根手动装填的烟幕管，5 秒本来就是一个游戏抽象。`ReloadCheck` 把这 6 件
  列成 `ACCESSORY` 行，**把“没改”写下来是一个决定，不是漏改**。
- **副作用：左 Alt 换弹也变慢了。** 本模组的装填选择走的就是基础模组的 `startReload()`，时长
  就是这里的 `reload.time`，所以 VT-4 选一发旧钢针现在要等 6.7 秒、10 式 3.5 秒。这是同一个
  数字的同一段代码，不是两处设定。
- **`ReloadCheck`（tools/）** 把这张表和包里的每个武器文件逐个对：主炮按 `CYCLE`（秒/发）
  × 20 算期望值，并要求 `max_capacity == 1`；配件按表里记的 100 验。它还会读六辆车的 JSON，
  **车上挂了表里没有的武器就 FAIL，表里有的武器在包里消失也 FAIL**。它同时打印每门炮的折算
  射速（8.0 / 15.0 / 17.1 发/分），进游戏前就能看出写没写对。
- 备份：本次会话工作区 `reload_work\weapons_before_reload\` 里是 25 个武器文件改动前的原字节
  （含 BOM / 行尾 / 末尾换行的状态；改完逐个核对过，`qlz_04_35mm.json` 本来就没有末尾换行，
  现在也没有）。

### 炮塔转速（方向机 / 高低机）

基础模组的 `rot_info` 两个字段是**速度**，不是角度：`x_rot_speed` 管俯仰（高低机），
`y_rot_speed` 管炮塔回转（方向机）。`WeaponUnit.tickRot` 用 `Mth.m_14148_`

- **吨马力是公开值，不是从包的重量现算的。** 公开的 hp/t 是按某个战斗全重引用的；包的
  `physics_info.mass` 不一定是那个重量。VT-5 是典型：1000 hp 在 33 t 基本型上是 **30.3**，
  而包的 42.9 t 模型算出 **23.3** —— 差的 11 吨是包的质量，不是发动机。所以两个字段分开写，
  HUD 显示公开的 30.3；只有 `horsepower_per_ton == 0` 时才退回用 `curbWeight` 现算。
- **HUD**：车内常驻状态条在岗位下面多一行 `发动机 / 1000 hp · 30.3 hp/t`（中英都是这行，
  单位不翻译），再下面一行 `加速 / ×1.21` —— 这是吨马力换出来的**物理倍率**，不是 hp/t
  本身。只对 `engine_horsepower > 0` 的车显示；别的载具是 0，两行都不出现。开镜时整条 HUD
  隐藏，和原来一样。
- **物理效果**：`mixin/AbstractVehiclePowerMixin` 注入基础模组
  `AbstractVehicle#getSuspensionPowerScale()` 的 **RETURN**，把返回值再乘上发动机倍率。
  这个方法是基础模组 `TrackedVehicle#tickMove` 自己读的那个 `powerScale`：
  `forwardAcceleration`、`backwardAcceleration`、`maxTurn` 和 `turnAcceleration` 都乘它，
  所以倍率改变的是**加速快慢和转向快慢**；`forwardSpeed` 在写回前就被
  `clamp(-maxSpeedBackward, maxSpeedForward)` 夹住，**最高速不变**，刹车/换向的
  `brakeAcceleration` 也不乘它。注入只在服务端生效（`level.isClientSide` 时直接返回，
  而且基础模组本来也只在服务端跑 `tickMove`），所以不会一个端算一个样。
- **倍率公式**：`clamp((hp/t ÷ engine_reference_hp_per_ton) ^ engine_power_exponent,
  0.5, 2.0)`。两个新字段在配置**根部**（不在每辆车里）：
  - `engine_reference_hp_per_ton` 默认 **25.0**（VT-4 的公开值），所以包里中等的那辆
    保持原样，另外两辆相对它变化。调小 → 差异变大；`≤ 0` 读作 25。
  - `engine_power_exponent` 默认 **1.0**（物理上加速度与功率/质量成正比）。`0` = **完全
    关闭**这个效果（所有车倍率 1.0）；大于 1 夸张差异，小于 1 压平。负值读作 0。
  - 按出厂值：VT-5 `30.3 ÷ 25 = 1.212`，VT-4 `1.000`，K2 `27.3 ÷ 25 = 1.092`，
    ZTZ-100 `37.5 ÷ 25 = 1.500`（纯电模式再乘 **0.8**，见下一节）。
    `engine_horsepower == 0` 的车（以及本模组没配置的车）倍率恒为 1.0，原样不动。
  - 上限 2.0 / 下限 **0.2** 是**防手滑**的夹子。下限原来是 0.5，那是只有现代车时定的；
    二战车全部低于它，整代人被压成同一个数。现在最低的玛蒂尔达 I 是 6.3 hp/t，正好是
    基准的 0.25，0.2 在所有配置值之下，所以倍率就是物理值本身：玛蒂尔达 ×0.25、瓦伦丁
    ×0.33、丘吉尔 ×0.34、斐迪南 ×0.37、T-26 ×0.38、突击虎 ×0.43、虎式 ×0.46、
    Sd.Kfz.251 ×0.47、四号 ×0.48。上限 2.0 不变。
- **v58 / v59 迁移**：v58 给三辆车加了 `engine_horsepower` / `horsepower_per_ton`

### 油箱容量（`energy_info.energy_capacity`）

七辆车的 `energy_capacity` 原来是统一的 **1000**（占位值）。现在按公开油箱数据改为：

| 车 | 油箱 | 依据 |
|---|---:|---|
| VT-5 / Type 15 | **700 L** | 估计。469 km 行程（无外挂油桶）[Type 15, Wikipedia](https://en.wikipedia.org/wiki/Type_15_tank)，33–36 t；按约 1.49 L/km 反推 |

| 10 式 | **880 L** | [Type 10, Weaponsystems.net](https://weaponsystems.net/system/269-Type%2010)：Fuel 880 L，440 km |
| 天马-20 / Cheonma-2 | **1200 L** | 估计。50–55 t、1200 hp 柴油，按 T-90 / 豹2 同量级 |

- **只改了容量，没有改 `energy_consumption_per_tick`。** 七辆车的油耗仍是同一个占位值
  0.002444444（满功率约 176 L/h），所以满油续航会随容量按比例变化。要按现实续航逐车调油耗，
  那是另一件事；现在先让 HUD / 加油量按真实油箱走。

  不要把估计当厂家数据。后四辆有公开行程但没有公开油箱；估计值按同级车的 L/km 反推。

### 混动（ZTZ-100，按 G）

**现实里的 ZTZ-100 是混动/电驱**：公开报道写的是约 **1500 马力** 的混合动力、公路最高
**85 km/h**（`SpeedCheck` / `EngineCheck` 都按这两个数登记）。基础模组没有“电动机”这个部件，
只有一条由发动机状态驱动的 `power` 和 `getSuspensionPowerScale()` 的倍率，所以这里把它做成
**柴油机 + 电池 + 纯电模式**，而不是伪造一个新的动力求解器：

- **`G` 切换。** 只有**驾驶员**（0 号座）能切；服务端看座位，客户端只发意图。按一下进纯电，
  再按一下回柴油。**只在本地配置里真有混动系统的车上发报文**，所以其它车（包括飞机）的 `G`
  仍然是基础模组的起落架键。
- **电池。** 电量按 **百分比** 显示（`battery_capacity` 默认 100）。柴油机在**柴油模式**下
  以 `charge_per_tick = 0.06 %/tick`（约 83 秒充满）充电；纯电模式下**踩油门**
  `0.15 %/tick`（满电约 33 秒）、**原地** `0.01 %/tick`，**无油门滑行**按
  `regen_per_tick = 0.03 %/tick` **回充**。电量低于 `min_start_percent = 10%` 时拒绝切入；
  用光自动切回柴油并给驾驶员一行提示。
- **纯电是真正的熄火。** 进入纯电时 `vehicle.toggleEngine(false)` 把柴油机真正关掉；
  `AbstractVehicleHybridMixin` 取消 `tickEnergy`（不烧油），并在 `tickPower` 里**用电池
  接管那个唯一的 `power` 数**：按基础模组同样的斜坡补到 100，同时保留涉水熄火和残骸掉电
  的判定。**油箱空了也能用电**：纯电时既不看 `getEnergy()`，也不用柴油，没油的车可以靠
  电池开出去。电池用光或驾驶员切回柴油时 `toggleEngine(true)` 重新点火。
- **动力与限速。** 纯电的加速/转向倍率是柴油的 `electric_power_scale = 0.8`
  （ZTZ-100 柴油倍率 1.5 × 0.8 = **1.2**，还是比基准车快，但比柴油慢）；最高速被压到
  `electric_speed_fraction = 0.55`（约 47 km/h）。这是“低速静音模式”，不是第二台柴油机。
  `TrackedVehicleElectricMixin` 只在 `tickMove` 调用期间改 `maxSpeedForward/Backward`，
  调用结束就还回去，所以 HUD、履带粒子和声音仍然读包里的原值。
- **静音。** 纯电时客户端把 `getEngineIdleSound` / `getEngineRunSound` / `getEngineStartSound`
  返回 `null`，并截掉 `spawnEngineSmoke` 的排气；**履带声和扬尘照旧**，因为那是一辆还在动的
  坦克。附近没有乘车的客户端也会收到状态（报文广播给跟踪这辆车的客户端），所以外面听也是静的。
- **HUD。** 常驻状态条多一行 `混动 / 纯电 82%`（或 `充电 64%`）；电量低于切入阈值变橙色。
  发动机下面那行 `加速 ×…` 已经把纯电的 0.8 乘进去，显示的是**当前生效**的倍率。
- **配置**：`Profile.hybrids`，一个和 `suspensions` 一样的根级 map，**存在即开关**。
  出厂只有 `armor_pioneer:ztz100`：

  | 字段 | 默认 | 含义 |
  |---|---|---|
  | `battery_capacity` | 100 | 电量上限（百分比） |
  | `initial_charge` | 100 | 新车开局电量；**不存档**，重新载入的坦克按满电算 |
  | `charge_per_tick` | 0.06 | 柴油模式充电速度 |
  | `idle_drain_per_tick` | 0.01 | 纯电原地耗电 |
  | `drive_drain_per_tick` | 0.15 | 纯电带油门耗电 |
  | `regen_per_tick` | 0.03 | 无油门滑行回充 |
  | `min_start_percent` | 10 | 切入纯电的最低电量 |
  | `electric_power_scale` | 0.8 | 纯电加速/转向倍率（再乘柴油倍率） |
  | `electric_speed_fraction` | 0.55 | 纯电最高速占变速箱最高速的比例 |

- **网络**：`HybridActionMessage`（C2S id **10**，只有 `TOGGLE`）与
  `HybridStateMessage`（S2C id **11**，车实体 id / 是否装了混动 / 是否纯电 / 电量比例 /
  切入阈值 / 提示码 / 是否播报）；协议版本升到 **12**。服务端在按键、自动切回、入座和每 10 tick
  广播状态；只有按键的人收到动作栏文字。
- **不存档**：电量、纯电模式都挂在实体上，不写 NBT——和涉水套件、悬挂姿态一样。重新载入的
  坦克回到满电、柴油模式；这是刻意的，不是漏写。
- **`HybridCheck`（tools/）** 验：出厂配置和两个派生时长、`batteryTick` 的七种状态
  （驱动/原地/滑行/耗尽/充电/无油/熄火）、切入阈值、报文往返、混动的四个 mixin 是否在正确的
  列表里、`G` 键与两个 message id、HUD 的两个读取点。`UpgradeCheck` 另测 v64 → v65：
  ZTZ-100 整车和混动条目会补进老文件，手改的 150 / 0.30 保留。
- **已知限制**：纯电时基础模组的 `power` 数仍由本模组补着，所以读 `hasPower()` 而不是
  点火标志的少数原版逻辑（例如开火）仍认为车是“有动力”的，这正是它还能开的原因；HUD 的
  倍率是客户端的配置，专用服务器配置不同时数值和物理会有出入（物理以服务端为准）；
  电池不存档；纯电时按基础模组的 `I` 键也打不着火（下一 tick 会被本模组关掉），
  要回柴油请按 `G`。

### 尾气（七辆车都有，纯电不排）

**尾气不是部件，也没有自己的名字**：基础模组的 `TrackedVehicle.tickParticle` 在 `hasPower()`
时调用 `ParticleUtil.spawnEngineSmoke`，位置来自载具定义根部的
`energy_info.engine_particle_offsets`（一串 `[x, y, z]`，载具本地坐标，`+z` 是车头、`+x` 是
右侧，烟整体往后甩）。**这个键缺失时基础模组不报错，只是永远不冒烟**——装甲先锋的七辆
车原来都没有它，所以一直没尾气。

- **七辆车现在各有两个镜像点**，位置不是抄默认包的，是按各自的 structure 模型量出来的：
  车体尾面内 **0.10 格**（`main_structure` 的 z 最小值 + 0.10）、**车顶抬高 0.25 格**
  （0.3 格大小的烟团半径为 0.15，贴面出生会半截埋在甲板里）、横向 **±62% 车体半宽**。
  每个点都对着模型做过“不在任何立方体里”的检查（`vehicle_body` 是碰撞盒，不算实体）。
- 出厂值（`data/armor_pioneer/vehicles/*.json` → `energy_info.engine_particle_offsets`）：

  | 载具 | 尾气点 |
  |---|---|
  | VT-5 | `[-0.961, 2.26, -3.25] / [0.961, 2.26, -3.25]` |
  | VT-4 | `[-1.105, 2.325, -3.639] / [1.105, 2.325, -3.639]` |
  | K2 | `[-0.846, 2.472, -4.284] / [0.846, 2.472, -4.284]` |
  | 10 式 | `[-1.138, 2.53, -3.565] / [1.138, 2.53, -3.565]` |
  | 天马-20 | `[-1.249, 2.283, -3.714] / [1.249, 2.283, -3.714]` |
  | ZTZ-100 | `[-0.81, 2.655, -3.588] / [0.81, 2.655, -3.588]` |
  | 豹 2A4 | `[-0.833, 2.78, -4.092] / [0.833, 2.78, -4.092]` |

- **ZTZ-100 纯电时不排。** 纯电是真正的熄火，但基础模组读的 `hasPower()` 仍由本模组用电

  `TrackedVehicleElectricSmokeMixin`（客户端，注册在 `client` 列表里）**重定向

- **`ExhaustCheck`（tools/）** 验：七辆车的定义都在、每辆都有 `engine_particle_offsets`、
  每个点是三个数字、`z < 0`（车尾）、`y` 在甲板高度区间、`|x|` 不超过车宽、两个点

  冒烟）、mixin 重定向的是 `spawnEngineSmoke` 而不是整个 `tickParticle`，且先判
  `HybridClientState.isElectric` 再调用。把 VT-5 那行删掉，工具会红。

### 炮镜：热成像与夜视（装甲先锋，按 4 / 5）

装甲先锋的七辆车**都有炮手镜**，但基础模组的热成像只在**开镜（`X`）+ `optical_sight_type`
为 `crt` + 武器单元 `with_thermal_imager: true`** 三个条件同时成立时才画；夜视基础模组
**完全没有**，所以这两件事分开做：

- **热成像（基础模组的功能，包里的数据）**：七辆车的 `turret` 部件原来是
  `"with_thermal_imager": false`，现在全是 `true`。开镜后按 **4** 切换，和默认包里的
  99A / M1A2 一样。**车长武器站没有开**：它的 `optical_sight_type` 是 `operator`，基础
  模组的热成像路径只走 CRT，打开只会是一段“看起来配了、实际不生效”的死数据。
- **夜视（本模组的补充）**：基础模组没有夜视镜头，所以这里是 `client/NightVisionHandler`
  自己的一条后处理链，**按 5** 开关。它只在**装甲先锋载具 + 炮手镜 `SCOPE` + CRT 瞄具**
  里生效；按一下开，再按一下关，离开载具自动关。`5` 是标准 `KeyMapping`
  （`key.ywzj_vehicle_armor.night_vision`），可以在“按键设置 → 装甲附属”里改绑。
- **和热成像互斥**：开夜视会把基础模组的 `thermalImaging` 清掉；开着热成像时按 5 会切回
  夜视。两套滤镜不会叠在一起。夜视是**纯客户端画面**，不开镜、不开 CRT、或开着热成像时
  后处理链不跑；服务端不参与，也没有新报文。
- **热成像烟雾（光影兼容）**：本体自己的热成像烟雾通道
  （`ThermalHandler.renderSmokeCloudParticles`）在世界后处理里；本机启用 **Oculus + Sundial
  Lite** 时，光影接管最终合成，这条路会被覆盖或不再被采样——这就是之前“烟挡不住热成像”的
  原因，不是载具包缺烟雾字段。`client/ThermalSmokeOverlay` 改在 **`RenderGuiEvent.Pre`**：
  世界和光影最终合成已经完成、HUD 尚未绘制时，用本体 `VectorUtil.worldToScreen` 把每个
  `SmokeCloudParticle` 投影到屏幕，画一张白色柔边烟团
  （`assets/ywzj_vehicle_armor/textures/gui/thermal_smoke.png`）。它只在本体热成像激活时运行；
  瞄准镜和 HUD 在它之后绘制，仍然在最上层。GUI 层没有世界深度，所以烟团不参与墙体遮挡——
  本体热成像本来就是透视传感器，这个取舍与它一致。没有光影时同样有效，可见光和夜视不受影响。
  这是屏幕空间近似，不是世界空间烟体；`SightCheck` 会确认烟团贴图和 overlay 类都打进了 jar。
- **画面**：`assets/ywzj_vehicle_armor/shaders/post/night_vision.json` 把主画面交给
  `program/night_vision.fsh`，做亮度提升、绿色荧光、轻噪点和暗角；**黑场映射到黑**
  （不做“最低亮度”底），所以基础模组 CRT 的黑色镜筒边框不会被染成绿边。
- **热成像的键**是基础模组的 `4`（`key.ywzj_vehicle.toggle_thermal_imaging`）；夜视的键
  是本模组的 `5`。两个键都只在开镜时有用，动作栏会说明当前状态。
- **验证**：新增 `tools/SightCheck.java`，逐辆检查七辆车的炮塔是 CRT、`with_thermal_imager`
  为真、车长站仍是 `operator` 且没有热成像；再检查夜视的后处理描述、程序、两个 shader
  是否都打进了 jar，以及热成像烟团贴图和 `ThermalSmokeOverlay` 是否存在。`UiCheck` 同时
  要求两个语言文件里都有按键名和五条提示。热成像烟雾由 GUI 层 overlay 负责，另有两个
  client-only 的粒子位置/尺寸 accessor mixin；`MixinCheck` 现在列出 **24 个 mixin（9 个
  client-only）**并确认它们都在 jar 里、不读已搬走的字段。

  0.200 格。选外侧而不是舱盖中心，是因为遥控武器站就在舱盖中左上方；这个点刚好在武器站
  枪管的左外侧。用显示模型的全部 cube 做过射线：中心射线和 ±10° 的 81 条射线全部不命中
  自身；±20° 会扫到武器站/炮塔顶，这是正常的。
- **跟炮塔的偏航，不跟主炮的俯仰。** 基础模组的 `worldPositionWithBaseRot` 会把父级
  （炮塔组）的**整个**旋转都算进去，而 `RotatableUnit.updateRot` 的旋转同时含偏航和主炮
  俯仰——直接用它，主炮压低 13° 时相机会离舱盖约 0.3 格、还可能钻进炮塔顶。所以这里只取
  炮塔的 **yaw**（`yaw_part_id`）来转位置；炮塔转动时视野方向也按同一个角度增量跟着转，
  这样炮塔在脚下转时潜望镜里的画面会一起转，而不是钉在世界方向上。
- **只对车长席开放。** 其他座位按 `Y` 只会收到“只有车长席可以使用舱盖潜望镜”；没配置的载具
  会收到“没有配置”。键是标准 `KeyMapping`（`key.ywzj_vehicle_armor.periscope`，默认 Y），
  可以在“按键设置 → 装甲附属”里改绑。
- **它替换的是相机点，不是视角行为。** 仍然是基础模组的 `OPERATOR` 视图：鼠标自由看、俯仰
  限制、FOV、车长武器站跟随视线瞄准都保持原样；所以开火仍然打在准星指向的位置。按 `Y` 再
  退出，或按 `V` / `X` 切换到基础模组的其他视角，也会自动退出；换座位、下车、死亡同样清掉。
- **纯客户端，没有新报文。** 配置在两边都会读，但视角本身不经过服务端；玩家朝向仍然是原版
  骑乘时就同步的那一个。
- **验证**：新增 `tools/PeriscopeCheck.java`，从默认配置读这条 entry，读包里的载具/结构/显示
  模型，验证车长在左、炮手在右、炮手 CRT 瞄具也在右、车长舱门是 `turret_door`、炮手舱门
  是 `turret_door2`、seat part、`turret_st` 的父级是 `turret`、相机在舱盖和炮塔盒之上、
  中心射线和 ±10° 锥全空，以及两个语言文件的按键和提示都在。`UpgradeCheck` 增加了
  v71 → v72 的补全用例，以及 v72 → v73 的两个用例：出厂点从右舱盖移到左舱盖，手改点保留。
  `verify.ps1` 现在是 **36 项检查**（37 个源文件）。

### 悬挂姿态必须同步到客户端

这是 0.6.2 真正会**改变画面**的一处。0.6.1 的客户端自己从地面探针算负重轮的视觉行程，所以姿态
不同步也看不出来；0.6.2 删掉了那个探针，改成直接用**服务端同步下来的压缩量**画轮子——而抬高车身
改变的是**静止长度**，压缩量本身不变。结果就是：**驾驶自己按了键的客户端轮子会悬空，其他乘员
也是**。

现在 `SuspensionStateMessage` 带上**载具实体 id + 两个档位索引**，服务端在按键后**广播给车上
所有人**（只有按键的人看到动作栏文字），并在玩家**入座**时补发一次当前姿态。这条报文当时
把网络协议升到 **8**；烟雾分组报文是 id **9**；车长接管动作值 4/5、混动 id 10/11、全权状态位
和 T/F 动作值 6/7 曾把协议升到 **15**。**现在这些车长接管功能已移除**：`CrewActionMessage`（id 6）
保留原来的布局但服务端直接丢弃，`CrewStateMessage` 的 solo/slaved 位仍然存在并恒为 false；
协议版本仍是 **15**，旧的客户端不会因为报文 id 不认识而断开。
`UiCheck` 逐字段验证这条报文的编解码，并检查“档位”和“上报的测量值”描述的是同一个姿态。

### 界面：跟 0.6.2 的 HUD 走

0.6.2 的本体 HUD 是 **480 高度虚拟布局 + 近白细描边 + 半透明深灰面板**，附属原来那套固定
250px 的墨绿“绿皮书”已经对不上了。这一版全部改到同一套语言：

- **弹药合集**：自适应宽度（240–420 虚拟单位），目录页加一行用途说明；弹药行带一条按本类
  最大穿深归一化的条；可切换引信的两种穿深写成 `480 / 520mm` 并在页脚解释；分组、缩进、
  翻页、滚轮/方向键行为不变。
- **装填选择**：同一套面板；每行一条穿深条；`装填` 标出**当前在炮膛里**的那一发，和光标
  （下一发要装的）分开，因为重新供弹要几秒；支持 1–30 个候选自动压缩行高。
- **装甲探测仪**：读数改成十字准星右侧的固定面板，部位名**本地化并带朝向**（“炮塔正面”
  而不是 `turret`），大号等效厚度、倍率、反应装甲/穿深损耗单独一行，底部是装甲表与页码。
- **车内常驻状态条**（新增，左上角）：岗位、**发动机马力与吨马力**、当前弹种/引信、悬挂姿态
  （服务端最后一次上报）、涉水套件状态与实时水深（客户端每 5 tick 探一次）。
  **只对本模组配置过的载具显示**；开镜时隐藏。它替代的是“按一次键闪一下动作栏”的旧做法——
  常驻状态不该靠记忆。
